# Research Findings

## Q1: How is app startup/initialization wired in iOS and macOS, and which target owns each entry point?

### Findings
- One SwiftUI `@main struct SingleThreadApp: App` (SingleThread/SingleThreadApp.swift:10) is the single entry point, compiled for both iOS and macOS; the platform split is entirely `#if os(iOS)`/`#if os(macOS)` inside one body (`SingleThreadApp.swift:13-45` builds `WindowGroup { ContentView(viewModel:appViewModel:) }`, plus macOS-only `.commands`, About `.sheet`, `MenuBarExtra` at :25-45).
- The earliest app-authored Swift code is `@State private var viewModel = AppViewModel()` (SingleThreadApp.swift:55), initialized before any scene appears. The App struct has no custom `init`.
- The composition root is `@MainActor @Observable final class AppViewModel` (SingleThread/AppViewModel.swift:19-24); its `init` (AppViewModel.swift:27-73) builds `ReminderStore` (`Self.makeStore(arguments:)`), `SortOptionStore`, `Self.registerDefaults()`, `AISortCoordinator`, `BackgroundImageStore`, and (iOS-only) `SkippedReminderSyncService` + entitlement observation.
- Delegate bridging, both appearance/orientation seams only (neither does library/session init):
  - `@UIApplicationDelegateAdaptor(AppDelegate.self)` iOS (SingleThreadApp.swift:65-66), `@NSApplicationDelegateAdaptor(MacAppDelegate.self)` macOS (:69-70).
  - SingleThread/AppDelegate.swift holds two classes under independent platform `#if`:
    - iOS `AppDelegate` (:9-52) — `applicationDidBecomeActive` (:40-44), `supportedInterfaceOrientationsFor` (:46-52), orientation-lock + appearance.
    - macOS `MacAppDelegate` (:56-84) — `applicationDidFinishLaunching` (:66-68), `applicationDidBecomeActive`, `applyLaunchAppearance()`.
- Contrast (separate `@main`, own targets): watch `SingleThreadWatch/SingleThreadWatchApp.swift:4` `SingleThreadWatchApp: App` has custom `init()` (:7-9) constructing `WatchAppViewModel()`; widget `SingleThreadWidget/SingleThreadWidgetBundle.swift:4` independent bundle entry.
- Candidate library-level-init hook points (Q1 report): (1) `AppViewModel.init` (AppViewModel.swift:27) — `@MainActor`, first app-side construction; (2) the `@State viewModel` property init (SingleThreadApp.swift:55); (3) delegate lifecycle callbacks — later, currently appearance-only.

## Q2: What is the app's privacy and data-flow disclosure surface?

### Findings
- `SingleThread/PrivacySettingsContent.swift` is the single source of truth for disclosed data flows. `struct PrivacySection` id/title/body (:5-9); `enum PrivacyGuideContent.sections(in:)` returns exactly **4** sections (:32-63):
  - `reminders` — EventKit read/write, stays on device or own iCloud, "never sent to the author or any third party" (:49).
  - `preferences` — display/sync prefs in shared app storage, synced to own Watch over "a direct local connection, never over the internet" (:42-47).
  - `skipped` — skipped reminders/excluded lists on device, Watch-synced over same direct local connection (:52-57).
  - `background` — proxy claim: "downloaded from a proxy at vardy.cc", "This is the app's only network request", "never includes any reminder, preference, or list data"; proxy holds Unsplash API key (:59-64).
- `closingLine(in:)` — **"SingleThread has no analytics, no tracking, and no advertising."** (:67-69). Doc comment (:12-19) says this copy is "the single source of truth" and hardcodes the three data flows (EventKit, WCSession, vardy.cc).
- Localization: full English sentences as `LocalizedStringResource` keys resolved against the in-app interface language (:80-93); translations in SingleThread/Resources/Localizable.xcstrings:4495-4531 (EN, zh-Hans, es, ja, de, fr).
- Tests asserting disclosures (`SingleThreadTests/PrivacySettingsContentTests.swift`, @MainActor, Swift Testing): `privacyGuideContentCoversAllDisclosures` (4 sections, vardy.cc literal, :13-29), `privacyGuideContentHasNoAnalyticsClaim` (closing line has "no analytics"/"no tracking"/"no advertising", :32-46), `privacyGuideContentResolvesInEveryInterfaceLanguage` (:48-61), `privacyGuideContentNonEnglishValuesDifferFromEnglish` (:63-83). Related `vardy.cc` assertions: SettingsViewTests.swift:287, AboutViewTests.swift:22.
- Actual network/data behavior: `SingleThread/BackgroundImageStore.swift` endpoints `https://vardy.cc/unsplash` and `/unsplash/random` (:180,:183); `@MainActor @Observable` phone-local cosmetic only, "never touches the App Group or sync payloads" (:52-55); transport `URLSession.shared` injected for tests (:63); `refreshIfNeeded` fetch/persist (:96-112+). No other outbound URLSession usage surfaced; WCSession/EventKit are non-internet (Q2 residual: didn't exhaustively prove "only network request").
- Entitlements & App Group: SingleThread/SingleThread.entitlements (app sandbox, `group.app.alanvardy.SingleThread`, audio-input, calendars, IAP); SingleThread/AppGroup.entitlements (group only). SingleThreadCore/Sources/SingleThreadCore/AppGroup.swift:12-39 — `suiteName = "group.app.alanvardy.SingleThread"`, single cached `nonisolated(unsafe) static let defaults`; carries UI prefs + store payload keys (:3-11).

## Q3: How is dependency and build configuration expressed in the Xcode project and SPM?

### Findings
- `SingleThreadCore/Package.swift:1-13` — `swift-tools-version: 6.0`; platforms iOS 17.0, watchOS 11.0, macOS 26.5; one `.library(name: "SingleThreadCore")`; one `.target(name: "SingleThreadCore", resources: [.process("Resources")])`.
- `project.pbxproj` package wiring — **single project-level reference** for the whole project:
  - Project object `packageReferences = (… XCLocalSwiftPackageReference "SingleThreadCore")` (project.pbxproj:458-460).
  - `XCLocalSwiftPackageReference` object — `isa = XCLocalSwiftPackageReference; relativePath = SingleThreadCore` (project.pbxproj:1228-1233): a **local filesystem** reference, not git/registry, no version string.
  - `XCSwiftPackageProductDependency "SingleThreadCore"` object (project.pbxproj:1235-1240).
- Target-restriction mechanism: each target lists the product under `packageProductDependencies`; adding/removing it from that list is the per-target scope toggle. Six `PBXBuildFile` entries `productRef = SingleThreadCore` (project.pbxproj:10-15). Target lists: SingleThread app (:261-262), SingleThreadTests (:285-286), SingleThreadUITests (:309-310), SingleThreadWatch (:332-333), SingleThreadWidget (:355-356), SingleThreadWatchTests (:402-403).
- No per-target package versions/conditionals; the reference list is shared. Adding a git remote package (Sentry) means a second entry in `packageReferences` + a new `XCSwiftPackageProductDependency`, linked only from the SingleThread target's `packageProductDependencies` (and any test target that needs it), not SingleThreadCore.
- dSYM build settings (shared project configurations): Debug `DEBUG_INFORMATION_FORMAT = dwarf` (project.pbxproj:651); Release `"dwarf-with-dsym"` (:714, also `ENABLE_NS_ASSERTIONS = NO`, `COPY_PHASE_STRIP = NO`). Only Release emits dSYMs — the material for Sentry symbolication. The SPM package declares no debug-info setting.

## Q4: What are the repo's test-suite and CI conventions?

### Findings
- `SingleThreadTests/` — flat ~80 files, `<Subject>Tests.swift`, Swift Testing (`import Testing`, `@Test`, `#expect`). Imports: `import Foundation`, `import SingleThreadCore`, `import Testing` (AppGroupTests.swift:1-3); app-target code via `@testable import SingleThread` (e.g. PrivacySettingsContentTests.swift:2). Single top-level `struct <Name>Tests`. Shared fixtures: TestFixtures.swift, BackgroundTestFixtures.swift, StubBundle.swift, LocalizationTestHelpers.swift.
- The SingleThreadTests target does **not** enable `SWIFT_DEFAULT_ACTOR_ISOLATION` (AGENTS.md), so `@MainActor` is applied per test struct where needed (e.g. MacOSActionButtonChromeTests.swift:7-8).
- Android-style platform split happens by destination, not `#if`: iOS unit tests run on simulator, macOS-native unit tests under `-destination "platform=macOS"`.
- GitHub Actions `.github/workflows/ci.yml`: jobs gated to main push + dependabot PRs (ci.yml:12-14); `concurrency: group` + `cancel-in-progress` (:7-9); runner `macos-26`, `setup-xcode` 26.6, `DEVELOPMENT_TEAM=` override (:28-34). Jobs: unit-tests (matrix iPhone 17 / iPad A16, `-parallel-testing-enabled NO -maximum-concurrent-test-simulator-destinations 1` clone-contention, ci.yml:84-98), ui-tests-smoke (single testLaunchAndRenderSmoke, :169-181), mac-tests (`CODE_SIGNING_ALLOWED=NO`, :197-244), lint (swiftformat, swiftlint --strict, warning self-test, watch build, periphery, :256-300), watch-ui-tests (:301+). Cache keyed on DerivedData + source hashes (:39-46). Every xcodebuild log piped through scripts/check-warnings.sh.
- Gate `scripts/test.sh`: `set -euo pipefail`, sources check-warnings.sh (:3-4). Sim resolution SIM= > `.simulator_id` > default (:44-95). Modes `full|--unit-only|--ui-only` (:99-113). Pre-guards `verify_deployment_target()` (:158-258, fails on floor drift) and `verify_xcodebuild_wrapped()` (:136-153, no bare xcodebuild). Full pipeline: swiftformat+fix → --lint → swiftlint --strict → warning self-test → iOS build-for-testing → watch build → periphery --strict → UI → watch UI → macOS unit tests (:278-390). Warnings-as-errors via `run_xcodebuild` tee→`check_warnings` against an allowlist (check-warnings.sh:27-33, scripts/xcodebuild-warnings.allow).

## Q5: What is the current state of the `sentry-cocoa` SDK? (external)

### Findings
- Current release line **v9.x**; 9.26.0 is the last fully-documented stable release, newer tags 9.27.0/9.28.0/9.29.0 exist, 9.26.1 dated Aug 27 2026 (actively maintained). v9 minimums iOS 15.0/macOS 10.14/tvOS 15.0/watchOS 8.0; CocoaPods dropped (last Pod 9.19.1); **SPM is the recommended integration**.
- SPM: `dependencies: [.package(url: "https://github.com/getsentry/sentry-cocoa", from: "9.26.0")]`, depend on the **`Sentry` product** (`SentryObjC` interface for pure ObjC). Min iOS 15.0+, Xcode 15.0+, Swift 5.0+. [iOS manual setup](https://docs.sentry.io/platforms/apple/guides/ios/manual-setup/) · [macOS guide](https://docs.sentry.io/platforms/apple/guides/macos/)
- `SentrySDK.start { options in … }`, called as early as possible on the main thread (SwiftUI `@main` App `init()` or UIKit `AppDelegate.application(_:didFinishLaunchingWithOptions:)`); configures a mutable `SentryOptions`. [sample AppDelegate.swift](https://github.com/getsentry/sentry-cocoa/blob/main/Samples/iOS-Swift/iOS-Swift/AppDelegate.swift)
- Key `SentryOptions` for crash/error reporting: `dsn` (String?, SDK disabled if nil), `enableCrashHandler` (Bool, default `true` — master crash switch), `enableWatchdogTerminationTracking` (default true), `enableAppHangTracking` (default true) + `appHangTimeoutInterval` (default 2.0), `sampleRate` (default 1.0), `tracesSampleRate` (default nil), `sendDefaultPii` (default false), `debug` (default false), `beforeSend`/`beforeSendLog`, `enableUncaughtNSExceptionReporting` (macOS-only, off by default), `attachScreenshot`/`attachViewHierarchy` (default false), `releaseName` (bundle-derived `<id>@<version>+<build>`), `environment` (default "production"). Top-level `enableLogs`/`enableMetrics` deprecated in 9.27.0; `enableStandaloneAppStartTracing` top-level in 9.26.0; `maxFeatureFlags` new in 9.27.0 (default 100). [9.26.0 notes](https://newreleases.io/project/github/getsentry/sentry-cocoa/release/9.26.0)
- Last-run/crash-detection API (relevant to crash→alert): legacy `options.onCrashedLastRun = { event … }` (fires after start if previous run crashed, use `event.eventId`) + `SentrySDK.crashedLastRun` (Boolean); newer tri-state `SentrySDK.lastRunStatus` (`.unknown|.didNotCrash|.didCrash`) + `options.onLastRunStatus` (fires once previous status known, PR #7469). Legacy has documented ambiguity (issue #4958); callbacks **not guaranteed main thread**. [PR #7469](https://github.com/getsentry/sentry-cocoa/pull/7469) · [issue #4958](https://github.com/getsentry/sentry-cocoa/issues/4958)
- Swift 6 / strict-concurrency: 8.41.0 fixed a runtime concurrency crash under Swift 6 by annotating ObjC callbacks (PR #4512); `SentryId` made `Sendable` in 8.42.0 (issue #4545); 9.0.0 set package swift-tools-version 6.0. Current 9.x is usable under strict concurrency; treat event/`eventId` crossing callback boundaries as non-`@MainActor`. [PR #4512](https://github.com/getsentry/sentry-cocoa/pull/4512)
- Caveats: async variants of callback-based ObjC methods may not be covered by `NS_SWIFT_UI_ACTOR` annotations; 9.26.0 added `enableUIViewControllerInitSwizzling` (experimental) to avoid instantiating `@available`-gated `UIViewController` subclasses at start (a startup-crash fix). [issue #6129](https://github.com/getsentry/sentry-cocoa/issues/6129)
- Per-crash email is a **Sentry server** alerting feature, not in the SDK — app-side only triggers capture; the alert rule delivers email (Q5 gap; confirm against Sentry alert docs).

## Q6: What are Apple's privacy-manifest and Xcode Cloud symbolication requirements? (external)

### Findings
- `PrivacyInfo.xcprivacy` is a plist at bundle root declaring `NSPrivacyCollectedDataTypes`, `NSPrivacyAccessedAPITypes`, `NSPrivacyTracking`/`NSPrivacyTrackingDomains`; at archive Xcode merges the app's manifest with each SDK's into a Privacy Report feeding the App Store label. [Apple privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy_manifest_files)
- Enforcement **May 1 2024** onward for iOS-family (not macOS): required-reason codes mandatory; list is open-ended. [Apple — describing required reason API](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api)
- Five required-reason categories: FileTimestamp, SystemBootTime, DiskSpace, ActiveKeyboards, UserDefaults — exact codes, case-sensitive. Examples: `CA92.1` (UserDefaults app-only), `1C8F.1` (App Group shared defaults), `35F9.1` (SystemBootTime), `C617.1` (FileTimestamp app container). [TN3183](https://developer.apple.com/documentation/technotes/tn3183)
- Collected-data-type entries = 4 keys, enum values only (`NSPrivacyCollectedDataType`, `Linked`, `Tracking`, `Purposes`). [Apple — describing data use](https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests)
- Third-party SDK: an SDK bundled as a binary dependency needs its own signed manifest; an SDK may not rely on the host app's manifest; static-linking is a known edge (app may need to aggregate the SDK's reason codes itself). [Apple — third-party SDK requirements](https://developer.apple.com/support/third-party-SDK-requirements/)
- Sentry's own manifest (Cocoa ≥ 8.25.0, dynamically linked): Crash/Performance/Other-Diagnostic data, `Linked=false`, `Tracking=false`; reasons UserDefaults `CA92.1`, SystemBootTime `35F9.1`, FileTimestamp `C617.1`. [Sentry Apple Privacy Manifest](https://docs.sentry.io/platforms/apple/guides/visionos/data-management/apple-privacy-manifest/)
- Static/SPM caveat: manifest is **absent from SPM distributions** of sentry-cocoa (issue #3853); with SPM/static linking the app supplies the entries itself. [sentry-cocoa #3853](https://github.com/getsentry/sentry-cocoa/issues/3853) · [issue #3775](https://github.com/getsentry/sentry-cocoa/issues/3775). Whether Sentry is on Apple's published "commonly used SDKs" list is unconfirmed (verify live page).
- Rejection codes: ITMS-91053..91056/91061 (missing/invalid reason codes, missing manifest) — fixes need a `CFBundleVersion` bump.
- Xcode Cloud custom scripts live in `ci_scripts/` (next to project/workspace): `ci_post_clone.sh` (install tools), `ci_post_xcodebuild.sh` (runs after build, even on failure). Need shebang + executable bit; non-zero exit aborts. [Apple — writing custom build scripts](https://developer.apple.com/documentation/Xcode/Writing-Custom-Build-Scripts)
- Archive env vars for symbolication: `CI_ARCHIVE_PATH` = exported app archive (dSYMs under `$CI_ARCHIVE_PATH/dSYMs`); also `CI_APP_STORE_SIGNED_APP_PATH`, `CI_DEVELOPMENT_SIGNED_APP_PATH`, `CI_XCODEBUILD_ACTION`, `CI_PULL_REQUEST_NUMBER`, `CI_WORKSPACE`. [Apple env var reference](https://developer.apple.com/documentation/xcode/environment-variable-reference)
- Standard upload: `ci_post_clone.sh` → `brew install getsentry/tools/sentry-cli`; `ci_post_xcodebuild.sh` → guard `$CI_ARCHIVE_PATH`, then `sentry-cli debug-files upload --org "$SENTRY_ORG" --project "$SENTRY_PROJECT" "$CI_ARCHIVE_PATH"`. Command is `debug-files upload` (old names `upload-dif`/`upload-dsym`). [Apple forums thread 713326](https://developer.apple.com/forums/thread/713326) · [Sentry Apple debug artifacts](https://github.com/getsentry/plugin-codex/blob/main/plugins/sentry/skills/sentry-instrument/references/debug-artifacts/apple.md)
- sentry-cli auth env vars → `.sentryclirc` keys, take precedence: `SENTRY_AUTH_TOKEN` (auth.token, required), `SENTRY_ORG` (defaults.org), `SENTRY_PROJECT` (defaults.project), `SENTRY_URL` (defaults.url, self-hosted only). Set in Xcode Cloud workflow Environment panel, token secret, never reaching the app. [sentry-cli config](https://docs.sentry.io/cli/configuration/) · [Uploading Debug Symbols](https://docs.sentry.io/platforms/apple/guides/macos/dsym/)
- Prerequisites: dSYMs only with `DEBUG_INFORMATION_FORMAT = DWARF with dSYM File` (Release default; q3 confirms the repo's Release setting); `ENABLE_USER_SCRIPT_SANDBOXING = NO` or the post-build script can't read the dSYM dir; upload from the exact shipped archive (UUID match); already-ingested events need reprocessing after a late upload.

## Cross-Cutting Observations
- **First third-party dependency**: the project currently has exactly one SPM package, a **local** filesystem reference (SingleThreadCore); Sentry would be the first remote/git package (project.pbxproj:458, 1228-1233).
- **Init placement constraint**: app is a single `@main` SwiftUI struct under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`; the pure options-factory pattern the ticket wants must be callable from `AppViewModel.init`/app launch, and `SentrySDK.start` wants the main thread.
- **Privacy copy is test-pinned**: adding Sentry contradicts "no analytics/tracking" and "never sent to a third party", and `privacyGuideContentHasNoAnalyticsClaim` (PrivacySettingsContentTests.swift:32-46) will **fail** unless the copy is updated in-step — a high-signal conflict to resolve.
- **No `.xcprivacy` exists anywhere** (locator); the app relies on no privacy manifest today, including its own UserDefaults/App Group usage (required-reason codes apply).
- **No Xcode Cloud `ci_scripts/` and no dSYM upload exists**; symbolication is net-new infrastructure on the Release (Xcode Cloud) path.
- **macOS privacy-manifest exemption** vs iOS enforcement is relevant since scope spans iOS + macOS.
