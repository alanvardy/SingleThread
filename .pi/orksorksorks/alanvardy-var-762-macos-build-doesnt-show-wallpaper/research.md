# Research Findings

Research for branch `alanvardy-var-762-macos-build-doesnt-show-wallpaper`. All paths relative to repo root. One Xcode target compiled for iOS + macOS (`SUPPORTED_PLATFORMS = "iphoneos iphonesimulator macosx"`, `project.pbxproj:772/:822`); platform differences are compile-time `#if os(...)` directives in shared files.

## Q1: Image rendering and conditional compilation

### Findings
- **The only UIKit/AppKit↔Color bridge** is `SingleThread/Color+CrossPlatform.swift`: import gate `#if os(macOS) import AppKit #else import UIKit #endif` (:3-7); `static var systemBackground` resolved per-expression — `#if os(macOS) Color(nsColor: .windowBackgroundColor) #else Color(uiColor: .systemBackground) #endif` (:16-20). Doc (:9-12): exists so shared views reference one symbol instead of inline per-platform guards. Consumed at exactly one site: `ContentView.swift:149` `Color.systemBackground.ignoresSafeArea()`.
- **The image bridge is per-method, not a shared type.** `BackgroundImageStore.swift:2-7` imports `#if os(iOS) import SwiftUI; import UIKit #elseif os(macOS) import AppKit #endif` (iOS also needs SwiftUI for the gated view; macOS imports only AppKit). `isDecodableImage` (:241-247) is the sole UIImage/NSImage call in the model layer: `#if os(iOS) UIImage(data:) != nil #elseif os(macOS) NSImage(data:) != nil #endif`. `persist(imageData:metadata:)` (:250-256) is platform-agnostic (`Data.write(options: .atomic)`). **NSImage is used only for validation, never rendering.**
- **`BackgroundPhotoLayer` is iOS-only, whole-block gated**: `BackgroundImageStore.swift:260-289` `#if os(iOS)` … `struct BackgroundPhotoLayer: View` (UIImage-based `Image(uiImage:)`, `.overlay { Color.clear }`, `.ignoresSafeArea().opacity().allowsHitTesting(false).accessibilityHidden(true)`, :268-288). No macOS counterpart exists. Its only instantiation is `ContentView.swift:150-155`, itself inside `#if os(iOS)`.
- **The fetch→persist→observe pipeline is fully shared**: `AppViewModel.swift:81` creates `backgroundImage = BackgroundImageStore()`, `:196` `let backgroundImage: BackgroundImageStore`, `:207` injects into `ContentViewModel` (lets `:34`/`:40`); `ContentViewModel.swift:92` `await backgroundImage.refreshIfNeeded()` from `task(showUndatedReminders:)`, called from `ContentView.swift:216`. Preferences: `@AppStorage` `backgroundEnabled`/`backgroundFadePercent`/`backgroundPinned` (`ContentView.swift:86-93`, ungated, `store: .standard`). `BackgroundFade.swift:13-24` converts percent → SwiftUI opacity (no image APIs).
- **Conditional-compilation catalog** — five flavors, all in the app target:
  1. *Import-level*: `BackgroundImageStore.swift:2-7`, `Color+CrossPlatform.swift:3-7`, `SingleThreadApp.swift:2-7`, `AppearanceMode.swift:2-7`, `AppViewModel.swift:4-11` (`#if os(iOS)` x3 imports + `#if os(iOS) || os(macOS) import WidgetKit`), `SettingsViewModel.swift:2-4`.
  2. *File/whole-block*: `ContentView+iOS.swift:8-44` (entire extension, reached from `ContentView.swift:203-207`); `AppDelegate.swift:1-60` `AppDelegate` (iOS) vs `:62-92` `MacAppDelegate` (macOS) in one file; `BackgroundImageStore.swift:260-289` view; `SkippedReminderSyncService.swift:4-380` whole file `#if os(iOS) || os(watchOS)` (Core); `AboutView.swift:50-54` iOS-only `#Preview`; `#if !os(watchOS)` negation in Core (`EventKitStoring.swift:26/42/50/66`, `ReminderStore.swift:112/231/359`).
  3. *Per-expression*: `ContentView.swift:22-24` (init writes iOS-only `appViewModel`), `:287-291` (`swipePromptBinding` → `$showSwipePrompt` vs `.constant(false)`), `:150-155` (photo layer), `:625-637` (bottomBar iOS cluster vs `#else` mic-only); `ContentView+Settings.swift:21-31` (`onChange` chains) and `:50-86` (`makeSettingsBag` 19-param iOS branch vs 13-param `#else`); `ContentViewModel.swift:40-49` (`showsActionButtons`) and `:105-109` (`handleAppearanceMode` dispatch `AppDelegate` vs `MacAppDelegate`); `ReminderDictation.swift:126-130,154-156` (`AVAudioSession` iOS-only).
  4. *@AppStorage key gates*: iOS-only keys `allowsLandscape` (`ContentView.swift:78-81`), `enableActionButtons` (:95-98), `showSwipePrompt`/`showUndoButton`/notification keys (:100-114) vs the ungated background cluster (:86-93).
  5. *Delegate adaptors*: `SingleThreadApp.swift:27-30` `@UIApplicationDelegateAdaptor` vs `:31-34` `@NSApplicationDelegateAdaptor`. `canImport` appears only in Core's `CodeSpanFormatter.swift:3-5,122,137,143-151` (color bridging per-platform); no `#available` guards anywhere.
- **Shared-view references to the photo** (all cross-platform compounds except the render site): `ContentView.swift:149` (fallback color), `:216/:219` (pin sync), `:562-565` (`setBackgroundPinned`), `ContentView+Settings.swift:11` (bag → `SettingsView(backgroundImage:)`), `SettingsView.swift:94` (row), `BackgroundSettingsView.swift:16,38,43,48,50,56,60` (store-driven controls), `ContentViewModel.swift:34,92`, `AppViewModel.swift:81,196,207`.

## Q2: macOS window and content surface

### Findings
- **`SingleThreadApp.swift` body is a bare `WindowGroup`** (:15-22): `WindowGroup { ContentView(viewModel: viewModel.contentViewModel, appViewModel: viewModel) }` — **no `.commands`, no `MenuBarExtra`, no window/safe-area modifiers**. `init()` eagerly constructs `AppViewModel()` (:10-12). No `NSWindow`/`NSWindowChrome`/`NSFocusWindow` reference exists anywhere in the app target (grepped).
- **`MacAppDelegate`** (`AppDelegate.swift:62-92`) touches only window *appearance*: `applyAppearance(_:)` loops `NSApp.windows` setting `.appearance` (:72-76); called from `applicationDidFinishLaunching` (:78-79) and `applicationDidBecomeActive` (:81-82) via `applyLaunchAppearance()` (:84-87). It never references ContentView or any background layer.
- **What paints the macOS window background**: `Color.systemBackground.ignoresSafeArea()` (= `NSColor.windowBackgroundColor`, `Color+CrossPlatform.swift:16-17`) as the first child of the root ZStack (`ContentView.swift:146-160`).
- **Scroll content transparency is unconditional (both platforms)**: `reminderList` (`ContentView.swift:388-470`) — `GeometryReader` → `ZStack(alignment: .bottom)` → `List` with `.listStyle(.plain)`; per-row `.listRowBackground(viewModel.rowChromeBackground)` where `rowChromeBackground == .clear` (`ContentViewModel.swift:54-56`); `.scrollContentBackground(.hidden)` at `ContentView.swift:450` (comment :448-449: exists so the iPadOS opaque scroll content shows the photo through); `.background(Color.clear)` at :453 (must follow the hide, :451-452); `.listRowSeparator(.hidden)`. Cards are opaque (`ReminderCardView.swift:41,48-52` plateFill).
- **`ignoresSafeArea()` call sites**: `ContentView.swift:149` (root color, ungated), `:535` (`completionGlowOverlay`, ungated), `BackgroundImageStore.swift:281` (inside the iOS-only layer). No macOS-specific branch. Manual safe-area math in the List: `geometry.safeAreaInsets.top/.bottom` subtracted from `viewHeight` (`ContentView.swift:354-357`) — no `safeAreaInset`.
- **The macOS stack has no photo slot**: the same root `ZStack` compiles with children (1) system background, (2) content — the middle `BackgroundPhotoLayer` child (`ContentView.swift:150-153`) is removed at compile time. `BackgroundImageStore` fetch/persist (`BackgroundImageStore.swift:62-257`) is platform-agnostic, so `imageData`/`backgroundEnabled` exist on macOS, but the only SwiftUI consumer of `imageData` (the iOS-only layer) is absent — fetched bytes are never rendered. There is no macOS-gated replacement view, `.background`, or window surface where a photo could attach (no NSWindow decoration, no layer primitives, no titlebar chrome).

## Q3: Settings surface on macOS

### Findings
- **Rows are hand-written, not data-driven**: `SettingsView.swift:32-131` `NavigationStack { List { Section… } }` with explicit `NavigationLink { SubSettingsView } label: { Label }` rows, each with `.accessibilityIdentifier`. First section order: Interface (:35-56), Notifications (:57-66), Reminder (:67-78), Filtering & Sorting (:79-88), **Background (:89-98)**, Purchase (:99-109); second section Privacy/About (:112-126).
- **Three per-platform row patterns in SettingsView**:
  1. *Row omitted on macOS*: Notifications row wrapped `#if os(iOS)` (:57-66); `NotificationsSettingsView.swift:4` documents it "compiles everywhere but its NavigationLink is iOS-gated".
  2. *Row adapted per platform*: Interface row's destination takes 8 bindings under `#if os(iOS)` vs 5 under `#else` (:36-54), mirrored by `InterfaceSettingsView.swift:13-29,56-98`.
  3. *Background row — unconditional* (:89-98): passes `$bindings.backgroundEnabled`, `$bindings.backgroundFadePercent`, `$bindings.backgroundPinned` + the live `backgroundImage` store on both platforms.
- **`SettingsBindings.swift`**: `@Observable final class` (:21-23); background defaults `true`/`50`/`false` (:30-32); stored fields (:72-74) declared unconditionally. Doc comment (:8-16): `#if` is illegal inside a parameter list, so iOS-only fields (`allowsLandscape`, `enableActionButtons`, `showUndoButton`) are always declared — on macOS they are "never wired or read" (runtime no-op, not compile-time omission). The three background fields ARE wired and read on macOS (in contrast).
- **`BackgroundSettingsView.swift` has no `#if` anywhere** — byte-identical on both platforms. Inputs (:10-16): three `@Binding`s + `var backgroundImage: BackgroundImageStore`. Controls: enabled `Toggle` `"backgroundToggle"` (:20-23); fade `Picker` over `BackgroundFade.allValues` `"backgroundFadePicker"` (:24-29); pin `Toggle` `"pinWallpaperToggle"` in own section (:30-34, stays visible regardless of enabled per doc :7-8) ; refresh `Button` → `Task { await backgroundImage.forceRefresh() }` with `isRefreshing` ProgressView/disabled `"refreshWallpaperButton"` (:36-53) — drives the **store**, not ContentView prefs; Unsplash attribution footer (:55-67). `navigationTitle("Background")` (:69). No `viewModel` passed.
- **Wiring**: `SettingsViewModel.swift` has **no background methods** — only `allowsLandscapeChanged` (`#if os(iOS)` :12-14) and `showPreferenceChanged` (`#if os(iOS) || os(macOS)` :18-21, widget reload). `ContentViewModel` holds the store (:34/:40), refreshes unconditionally (:62), and owns `rowChromeBackground = .clear` (:54-56). Source of truth are the ungated `.standard` `@AppStorage` keys (`ContentView.swift:85-93`); render gate at :150-155; pin sync runs on both platforms — `.task` :214-218 (`await viewModel.backgroundImage.setPinned(backgroundPinned)`), `.onChange(of: backgroundPinned)` :219-221 → `setBackgroundPinned` :562-565. `ContentView+Settings.swift`: background write-backs sit outside any `#if` (:34-36); `makeSettingsBag()` includes the three background fields in **both** the iOS branch (:60-63) and the `#else` macOS branch (:74-78) — the preference plumbing round-trips fully on macOS.
- **Pattern summary**: (1) compile-time row omission (Notifications, `SettingsView.swift:57-66`); (2) compile-time row adaptation (Interface, `SettingsView.swift:36-54`); (3) `os(macOS)`-only UI — `actionButtons` (`ContentView.swift:294-337,601-604`), `MacAppDelegate` branch (`ContentViewModel.swift:105-109`); (4) `.standard` booleans existing on both platforms but consumed only by the iOS render (background cluster); (5) always-declared-but-inert iOS-only fields (`SettingsBindings.swift:8-16`); (6) the **Background row is the anomaly** — full surfaces cross-platform, only the render site is iOS-gated, so its toggles are inert-but-functional on macOS.

## Cross-Cutting Observations
- **The divergence is exactly one gate deep**: fetch → persist → observable store → preferences → settings are 100% shared; macOS diverges precisely at the render instantiation inside `ContentView.body` (`ContentView.swift:150-155`) and the view's own definition (`BackgroundImageStore.swift:260-289`). Every other platform split in the codebase follows the same shape (e.g. notifications: shared store/UX only exists iOS-side end-to-end).
- **Conditional-compilation vocabulary is consistent**: app target uses `#if os(iOS)` / `#if os(macOS)` / `#if os(iOS) || os(macOS)`; Core uses `#if os(watchOS)` / `#if !os(watchOS)` and the only `canImport` anywhere is `CodeSpanFormatter.swift`. No `#available` guards exist.
- **Two patterns for "what to do with iOS-only state on macOS"** already exist: (a) *omit/wire-nothing* — iOS-only fields in `SettingsBindings` are always declared but never wired/read on macOS (`SettingsBindings.swift:8-16`); (b) *adapt* — Interface row passes different binding arities per platform (`SettingsView.swift:36-54`) and `makeSettingsBag` branches per platform (`ContentView+Settings.swift:50-86`). The Background prefs follow neither: they are wired and read identically on both platforms.
- **Persistence split**: background prefs are `.standard`-backed (phone-local cosmetic state, `ContentView.swift:85-93`), unlike display prefs synced via the App Group (`AppGroup.defaults`); `UITestingSeed.resetPersistedState` wipes them.
- **Test asymmetry**: background *logic* (store/fade/fixtures/seed) is tested on macOS in CI; background *visual seams* (`BackgroundCardTests`) are iOS-only; no macOS UI test exists; rendering is asserted headlessly nowhere (explicitly documented in `BackgroundCardTests.swift` and `SingleThreadUITestsFlows.swift:338-340`).
- **The macOS UI-test target exists but is dead weight**: SingleThreadUITests declares macOS support (`project.pbxproj:904,928`) yet no harness ever schedules it on `platform=macOS`, and the `--ui-testing` smoke seam it would rely on is iOS-only compiled (`AppViewModel.swift:238-274`).

## Open Areas
- **No macOS visual verification has ever been recorded**: prior research (VAR-743 Open Areas) admits no macOS build was executed during research; macOS confidence rests on build + ungated unit tests.
- **Window surface unknowns**: whether `NSWindow` appearance/titlebar behavior interacts with any future behind-content layer is unexercised — `WindowGroup` has no modifiers and `MacAppDelegate` touches only `NSApp.windows[].appearance`.
- **macOS-specific `ignoresSafeArea` semantics** (does the root color actually extend behind the titlebar on macOS?) are not verified anywhere in code or artifacts.
- **The `--ui-testing` single-reminder flow is unreachable on macOS** — any future macOS UI-test verification would need a seam that currently doesn't compile there.
