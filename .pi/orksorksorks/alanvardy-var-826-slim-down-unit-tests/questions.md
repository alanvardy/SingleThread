# Research Questions

## Context

This repo has four test targets: `SingleThreadTests` (Swift Testing `@Suite`/`@Test`) and `SingleThreadWatchTests` (Swift Testing), plus two XCTest UI smoke suites (`SingleThreadUITests`, `SingleThreadWatchUITests`). The unit suites exercise `SingleThreadCore` domain code (ReminderStore, sync services, view models, formatters) through shared seams (`InMemoryEventStore`, `--seed`/`--ui-testing*` launch args, App Group `UserDefaults`). iOS and watch suites test the same persisted behaviors through different seams, and several behaviors are asserted at multiple layers. Prior slimming work exists under `.pi/orksorksorks/alanvardy-var-755-slim-down-test-suite/` and `.pi/orksorksorks/alanvardy-var-796-slim-down-test-suite/`. Focus on the structure, duplication, and maintenance-cost signals of the unit test suites and their fixtures, plus the measurement tooling available to quantify test value.

## Questions

1. **iOS↔watch mirrored coverage.** For the pairs `ReminderStoreTests`/`ReminderStoreWatchTests`, `SkippedReminderSyncServiceTests`/`WatchSyncPipelineTests`, `CompletionGlowTests`/`ShowCompletionGlowStateTests`, and the `EnableActionButtons*`/`ShowEnableActionButtonsStateTests` families: how much of the coverage is structurally identical — same test scenarios, same fixture idioms (`makeReminder`, `inListReminder`, per-file fake session), same persisted keys asserted, same assertion shapes? Which test functions are near-duplicates apart from the seam used, and are there any full-file or full-suite duplicates?

2. **Multi-layer coverage of the same behaviors.** For behaviors asserted at two or more layers (showDate/showAlarms/showRecurrence/showList, enableActionButtons, completion glow, skip counts, sort, excluded lists, priority marker, recipients): trace each behavior through its layers (store/model, sync service, view-model, view-render, UI smoke) and say what each layer's assertion adds or restates. Which persisted App Group keys are asserted in how many test files, and which scenarios are re-proven nearly verbatim at each layer?

3. **Brittleness and maintenance-burden signals.** Inventory the concrete markers of costly tests: real-time waits (sleeps/polling loops with durations and `file:line`), suites forced `@Suite(.serialized)` and the shared state they serialize, test files with `file_length` lint disabled, single test functions that brute-force multiple scenarios by constructing several stores in one body, and dead or unused test helpers (e.g. the unused helpers in `SingleThreadUITestCase.swift`). Also: what test-count documentation exists (`scripts/count_tests.sh`) and is it accurate?

4. **Fixture and fake duplication in test land.** Map the per-file test support code: fake transcriber classes in `MicrophoneToggleTests` and `CompletionGlowTests`, fake session classes in `SkippedReminderSyncServiceTests` and `WatchSyncPipelineTests`, `FetchGate`/`TogglingBackgroundFetcher` in `BackgroundImageStoreTests`, the recording `EventKitStoring` double, and re-declared fixtures (`makeReminder` per file, `sharedWatchEventStore`/`watchReminder`/`makeViewModel` in multiple watch test files). How similar are the duplicated fakes, how large are the duplicated blocks, and what real system interaction does each fake replace?

5. **Test-harness machinery living in production code.** `InMemoryEventStore` (133 lines) and `UITestingSeed` (185 lines, plus its 16 dedicated tests in `UITestingSeedTests`) ship inside the `SingleThreadCore` package, alongside the `--seed`/`--ui-testing*` launch-arg seams in app view models and the App Group `UserDefaults` suite keys. Which of these run in production builds versus only in test/UI-testing builds, how much test-only machinery is itself directly covered by tests, and what does the `UITestingSeedTests`/`resetPersistedState` surface test that nothing else tests?

6. **Prior slimming trail and value conventions.** What did the earlier slimming tickets actually change: read the design/plan/evidence artifacts of `alanvardy-var-755-slim-down-test-suite` and `alanvardy-var-796-slim-down-test-suite`, the "Stage 2" deletions referenced in watch UI tests, and the git history of the test directories. What did those tickets identify as removable or low-value but leave in place, and is there any decision record in this repo defining what counts as a low-value or duplicate test?

7. **Coverage measurement and distribution.** What does the repo's coverage tooling (`make coverage*`, xccov result bundles, `.periphery.yml` exclusions) currently report for the unit targets? Where does coverage clump (the same production lines exercised by many test files — over-coverage) versus thin coverage, and which production files in `SingleThreadCore` are exercised by multiple overlapping test files versus barely tested at all?
