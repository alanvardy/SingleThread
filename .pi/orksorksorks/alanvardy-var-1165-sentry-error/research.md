# Research Findings

## Q1: What synchronous work runs on the main thread during app launch and `AppViewModel` initialization, and what dependencies does that construction chain touch?

### Findings
- App target sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`; `AppViewModel` is `@MainActor @Observable` (`SingleThread/AppViewModel.swift:14-17`).
- `SingleThreadApp.init()` (`SingleThread/SingleThreadApp.swift:14-18`) runs synchronously on the main thread before any view: `SentryBootstrap.startIfEnabled()` then `State(initialValue: AppViewModel())`.
- `SentryBootstrap.startIfEnabled()` is fully synchronous: reads `CrashReportingPreference().isEnabled`, `SentryConfiguration.make(...)`, then `SentrySDK.start { options in … }` with DSN, breadcrumbs, sampling, crash/hang/watchdog flags, scrubbers (`SingleThread/SentryBootstrap.swift:10-41`).
- `AppViewModel.init` (`SingleThread/AppViewModel.swift:21-64`) does, in order: `makeStore` (line 26), reads `SortOptionStore().load()` (line 28), constructs `AISortCoordinator` (line 29), `registerDefaults()` incl. one-time App-Group migration (line 30, body `:161-179`), `BackgroundImageStore()` (line 32, no I/O in init), iOS `setupSyncService` (line 35), sets `store.onRemindersChanged` (lines 37-45), `onAIRerankRequested` + `setupAIRankingObservation()` (lines 47-51), iOS `setupSyncObservation()`/`setupEntitlementObservation()` (lines 55-57).
- `makeStore` (`SingleThread/AppViewModel.swift:~283-360`) returns `ReminderStore(...)`; `ReminderStore.init` (`SingleThreadCore/.../ReminderStore.swift:23-57`) synchronously constructs `EKEventStore()` plus `SkippedReminderStore`, `SkipCountStore`, `PendingCompletionStore`, `ExcludedListStore`, `DailyCompletionStore`, `CompletionCounterStore` (all App-Group/UserDefaults-backed, several performing a synchronous read) and `EntitlementStore` (whose init spawns an async StoreKit task, `EntitlementStore.swift:17-21`). Init only assigns fields; `store.start()` is NOT called here.
- `ContentView.task` (`SingleThread/ContentView.swift:280-294`) → `ContentViewModel.task` (`SingleThread/ContentViewModel.swift:~143-160`) is the deferred path: `await store.start()`, then build/start `StaleReminderRechecker`, `await backgroundImage.refreshIfNeeded()`.

## Q2: How does the WatchConnectivity sync service operate — queues/actors, activation, payload handling, main-actor intersection?

### Findings
- `SkippedReminderSyncService` is a nonisolated `public final class ... NSObject, WCSessionDelegate`, entirely inside `#if os(iOS) || os(watchOS)` (`SingleThreadCore/.../SkippedReminderSyncService.swift:16,48`). It is in `SingleThreadCore`, which does NOT enable default MainActor isolation.
- Seam: protocol `SkipSyncSession` (`:18-35`) abstracts `isReachable`, `activate()`, `updateApplicationContext`, `sendMessage`, `queueUserInfo`; `extension WCSession: SkipSyncSession` (`:36-42`); `FakeSession` test double (`SingleThreadTests/TestFixtures.swift:71-104`).
- `activate()` (`:266-271`) assigns `session.delegate = self` only when `session as? WCSession` succeeds, then calls `activate()`. Real delegate callbacks run on WCSession's own serial delegate queue — the service never hops actors itself.
- Delegate entry points: `didReceiveApplicationContext → apply(context:)` (`:334-337`), `didReceiveMessage → apply(request:)` (`:339-341`), `didReceiveUserInfo → apply(request:)` (`:344-350`), `activationDidCompleteWith` logs errors (`:352-359`), iOS `sessionDidDeactivate` re-activates (`:361-366`).
- ~18 `nonisolated(unsafe) var on…Received` hooks (`:175-262`) are written once from the main actor before `activate()` and read afterward on the delegate queue (documented happens-before, `:161-172`). Main-actor hop happens at the AppViewModel/WatchAppViewModel call sites via `Task { await store?.… }` / `Task { @MainActor in … }`, not in the service.
- Send side `pushAll()` (`:276-333`) builds one latest-wins `updateApplicationContext`; `entitled` read via `MainActor.assumeIsolated` (`:325-330`). `deliver(_:)` (`:430-440`) is the single outgoing chokepoint: `sendMessage` when reachable, else `queueUserInfo`. Receive side `apply(context:)` (`:447-517`) + `applyRemaining(context:)` (`:522-548`) decode key-by-key, persist via injected stores, then invoke handlers. `apply(request:)` (`:412-428`) decodes complete/delete/reschedule.
- No `WCContentIndex`, `transferFile`, or file-transfer usage exists anywhere in the repo (also Q1 locator).
- iOS wiring `AppViewModel.setupSyncService` (`SingleThread/AppViewModel.swift:486-540`): guard `session != nil || (WCSession.isSupported() && !usesInMemoryStore)` (`:489`), handlers assigned before `activate()` (`:504-521`), store hooks wired after (`:523-539`). Watch wiring `WatchAppViewModel.setupSyncService` (`SingleThreadWatch/WatchAppViewModel.swift:190-228`); `WCSession.default` at `:248`; delayed application-context replay for UI tests at `:312-327`.

## Q3: How does the EventKit `ReminderStore` persistence path execute reads, writes, settle delays, and change observers, and what guards them?

### Findings
- `ReminderStore` is `@MainActor @Observable public final class` (`SingleThreadCore/.../ReminderStore.swift:14-16`); `EventKitStoring` is `@MainActor` and `EKEventStore` conforms (`EventKitStoring.swift:9-10,63`) — every EventKit call routed through the store is MainActor-isolated.
- `ResumptionGate` (`@unchecked Sendable`, `ResumptionGate.swift:19`) is the one-shot continuation guard; its invariant is that check-and-set happens on MainActor with no `await` between (`:30-33`), and `resumeOnMainActor(_:_:)` is `nonisolated` so EventKit's off-main completion can hop back (`:46-51`).
- `fetchReminders(matching:)` (`ReminderStore.swift:711-721`) bridges the completion-handler API with a `ResumptionGate`; the comment states fetch works off the main thread and the gate keeps setup from blocking UI.
- Reads: `reload(clearSkipped:)` (`:522`) → `refreshSourcesIfNecessary` (iOS, `:526`) → predicate (`:542`) → `await fetchReminders` (`:549`); computes `hasHidden`, filters pending completions, assigns `reminders`/`availableLists`, reconciles skip state, prunes, fires `onRemindersChanged?()` (`:567-587`). Derived state is computed MainActor properties (`:182-243`).
- Writes (iOS branch) all follow save → `await settle()` → `await reload()`: `completeReminder` (`:294`), `undoLastCompletion` (`:353`), `deleteReminder` (`:378`), `addReminder` (`:407`), `rescheduleReminder` (`:438`). `skipCurrentReminder` (`:463`) spawns `Task { await settle(); if applySkipSet(...) { await reload() } }` (`:471-483`) guarded by `skipGeneration`; `skipCurrentReminderImmediately` (`:504`) writes synchronously with no settle.
- Settle seam: `public typealias ReminderStoreSettle = @Sendable () async -> Void` (`:12`), production default `Task.sleep(200 ms)` (`:48-50`), tests inject a no-op.
- Change observer: `EventStoreChangedObserving.onChange(_:)` (`EventStoreChangedObserver.swift:9-11`); `EventStoreChangedObserver.onChange` registers `.EKEventStoreChanged` on `queue: .main` (`:25-28`) and returns a removal closure. `StaleReminderRechecker` (`@MainActor`, `:18`) consumes it; reentrancy guarded by `isReloading`/`reloadPending` with no `await` between the final `reload()` and clearing the flag (`:107-118`). `live(store:)` factory at `:127-141`; lifecycle in `ContentViewModel.task` (`SingleThread/ContentViewModel.swift:144-161`).
- Watch-relayed writes do not touch EventKit: they mutate `reminders`/`pendingCompletions` and fire relay hooks (`ReminderStore.swift:296-312, 379-385, 443-447`).
- No `NSFileCoordinator`/coordinated file I/O exists in the repo (per Q1/Q3 locator).

## Q4: How is the AI sorting coordinator triggered and executed?

### Findings
- `AISortCoordinator` is explicit `@MainActor` (`SingleThreadCore/.../AIReminderRanking.swift:63-64`); constructed in `AppViewModel.init` (`SingleThread/AppViewModel.swift:29`) with a 500 ms default debounce (`:23-25`).
- Triggers: rules-text App-Group notification (`AppViewModel.swift:450-457`), `store.onRemindersChanged` (`:39-45`), `store.onAIRerankRequested` → forced refresh (`:47-51`, request at `ReminderStore.swift:264-267`).
- `refreshAIRanking(force:)` (`AppViewModel.swift:418-425`): cancels when sort option ≠ `.ai`, else `aiCoordinator.update(rules: AISortRulesStore().load(), candidates: store.aiCandidates, force: force)`.
- `update(rules:candidates:force:)` (`AIReminderRanking.swift:104`): blank rules or `!ranker.isAvailable` → cancel/reset/`emit([:])` (`:105-113`); digest hash of rules+candidates (`:179-187`); dedupe unless forced (`:121-128`); increments `generation`, cancels `pending`, creates `Task { Task.sleep(for: wait); await ranker.rank(...) }` (`:133-142`). Success guards generation, clears pending, sets `lastCompletedDigest`, `emit(reconcile(...))` (`:138-143`); failure retains prior ranking, leaves digest unset for retry, logs, fires `onRankingFailed` unless unavailable (`:144-151`). `reconcile` drops invented ids/dedupes/appends omitted (`:79-99`).
- The `pending` Task inherits MainActor isolation; only `await ranker.rank` and `Task.sleep` suspend. `emit`/callbacks run on the main actor. No separate queue/actor.
- Production ranker `FoundationModelsReminderRanker` is `nonisolated struct`, `isAvailable` from `SystemLanguageModel.default.availability` (`SingleThread/FoundationModelsReminderRanker.swift:12,22-48`); `rank` builds a `LanguageModelSession` and awaits `session.respond(...)` (`:78-91`), so it runs off the MainActor when awaited. Protocol `AIReminderRanking: Sendable` (`AIReminderRanking.swift:37`).
- Flow: reminder change / rules edit / refresh button → `refreshAIRanking` → `update` (MainActor debounce+dedupe) → `await ranker.rank` (nonisolated) → `reconcile` → `onRankingUpdated` → `store.setAIRanking` → `visibleReminders` applies AI order (`ReminderStore.swift:172-196`). `setAIRanking` deliberately fires no `onRemindersChanged` (`:252-259`).

## Q5: How are App Group `UserDefaults` values and change notifications read and observed, and what constraints exist?

### Findings
- `AppGroup.defaults` is a deliberately cached `nonisolated(unsafe) static let` (`SingleThreadCore/.../AppGroup.swift:28-29`); suite `group.app.alanvardy.SingleThread` (`:8`), falling back to `.standard` when the suite is unavailable (`:11-13,19-21`). The doc comment (`:15-26`) states the invariant: `didChangeNotification` posts with the changing instance as `object`, so a computed property would break every `object:`-filtered observer.
- Store wrappers (`BoolPreferenceStore.swift:16`, `SortOption.swift:59`, `AISortRulesStore.swift:9`, `SkipCountStore.swift:26`, `DailyCompletionStore.swift:18`, `PendingCompletionStore.swift:20`, `ExcludedListStore.swift:7`, `CompletionCounterStore.swift:20`) all default `defaults: UserDefaults = AppGroup.defaults`. `BoolPreferenceStore` deliberately avoids `bool(forKey:)` so nil ≠ explicitly-off (`:7-9,26-28`).
- App-side observers, all `object: AppGroup.defaults`, `queue: .main`, then a MainActor hop: `PreferenceHolder` (`PreferenceHolder.swift:13-22`, refresh `:53-67`, token removal `:45-51`), `AppViewModel.setupSyncObservation` → `handlePreferencesChanged()` (value-diff against cached `last*` fields before `pushAll`, `AppViewModel.swift:565-638`), `AppViewModel.setupAIRankingObservation` (`:435-461`). One-time `enableActionButtons` migration from `.standard` (`:129-148`).
- Watch side does NOT observe `didChangeNotification`; state holders read once and rely on explicit sync callbacks (`ShowDateState.swift:14-34`, `ShowListState.swift:31-34`, `ShowRecurrenceState.swift:29`, `ShowAlarmsState.swift:29`, `ShowCompletionGlowState.swift:28`). `ShowEnableActionButtonsState` is the outlier using `AppGroup.defaults` (`:21-26`).
- Divergence noted: the sync service receive side writes show-* prefs through `BoolPreferenceStore` over `AppGroup.defaults` (`SkippedReminderSyncService.swift:495-534`), while watch UI holders read/write `.standard` for the same keys except `enableActionButtons`; these coincide only because `AppGroup.defaults` falls back to `.standard` on watch.
- Tests enforcing the invariants: `SingleThreadTests/AppGroupTests.swift:28-72` (`defaultsIsAStableInstance` at `:36-42`, `objectFilteredObserverSeesAppGroupWrites` at `:44-64`). Runtime regression probe `scripts/check-appgroup-notify.sh`.

## Q6: What is the current Sentry integration, and what diagnostics/breadcrumbs exist around hangs?

### Findings
- `SingleThreadApp.swift:15` calls `SentryBootstrap.startIfEnabled()` before `AppViewModel()` (line 16). Guard requires `CrashReportingPreference().isEnabled` AND a non-nil `SentryConfiguration.make(...)` (`SentryBootstrap.swift:11`).
- Options (`SentryBootstrap.swift:17-41`): dsn, environment, `maxBreadcrumbs`, `sendDefaultPii`, `tracesSampleRate`, `enableCrashHandler = true` (`:25`), `enableAppHangTracking = true` (`:26`), `enableWatchdogTerminationTracking = true` (`:27`), `enableAutoSessionTracking = false`; iOS `attachScreenshot/attachViewHierarchy = false` (`:31-34`); macOS `enableUncaughtNSExceptionReporting = true` (`:35-37`); `beforeSend`/`beforeBreadcrumb` routed to `SentryScrubber.scrub` (`:38-39`). `setEnabled(_:)` starts/closes (`:44-48`).
- Hang/watchdog are SDK auto-instrumentation flags only — no app-configured thresholds or callbacks. No `SentrySDK.addBreadcrumb`/`captureMessage`/`captureError` calls exist anywhere (only `start`/`close`).
- `SentryConfiguration` is pure `Equatable, Sendable`, no Sentry import (`:4-19`); `make` returns nil on empty DSN, defaults `maxBreadcrumbs: 20`, `sendDefaultPii: false`, `tracesSampleRate: 0` (`:22-35`).
- `SentryScrubber` is an allow-list scrubber: nils user/extra/request/modules/message/transaction, filters tags to `["environment","release","level"]`, nils each exception `value` but keeps `type` so crashes still group, compacts breadcrumbs through `scrub` (`SentryScrubber.swift:11-33`).
- Consent: `CrashReportingPreference` persists in `UserDefaults.standard` deliberately not App Group (`:4-6,9,20`), absent key → enabled (`:24-26`); binding in `SettingsBindings.swift:219-230`; toggle `SettingsView.swift:155`.
- Only prose source is `docs/CrashReporting.md` (DSN/org setup, dSYM upload; Debug uses `dwarf` so only Release symbolicate).

## Q7: What test seams and conventions exist, and how are targeted tests run?

### Findings

Delegate callbacks driven directly on the service. Suites: `SkippedReminderSyncServiceTests.swift`, `SkipCountSyncTests`, `AISortOptionTravelTests`, `AppViewModelSyncWiringTests.swift:22-27`.

## Cross-Cutting Observations
- The ticket's cited culprit thread names (`WCContentIndex index`, file coordination) have **no app-code counterpart**: the repo contains no `WCContentIndex`, `transferFile`, `NSFileCoordinator`, or `BGTaskScheduler` usage; the only WatchConnectivity API surface is `updateApplicationContext`/`sendMessage`/`transferUserInfo` (`SkippedReminderSyncService.swift`) with no app frames on the hung main thread. Those frames are therefore system-internal to the captured stack, consistent with the "no app frames" report.
- Main-thread work is concentrated in two places: synchronous construction at `SingleThreadApp.init` / `AppViewModel.init` (Q1), and every `@MainActor` coordinator/observer callback hopping back to the main actor (Q3-Q5).
- App Group `UserDefaults` is the shared wire between phone and watch; its correctness rests on three documented invariants — single cached instance, `object:` filtering, and token lifetime — each with a guarding test.
- EventKit's completion-handler APIs are bridged with `ResumptionGate` + `resumeOnMainActor`; writes are spread out by a 200 ms injectable settle delay before reload.

## Open Areas
- The actual cause of the reported hang is NOT established by static research: no code path was found that obviously blocks the main thread indefinitely. The hang could be a system-level stall (EventKit/CloudKit/WatchConnectivity internals) not visible in app code.
- The captured Sentry stacks were not provided to the researchers; stack-frame correlation was not possible. No Sentry breadcrumb/attachment diagnostics exist to correlate (Q6).
- Exact WCSession delegate-queue identity and whether a delegate callback can contend with MainActor work were reasoned from structure/comments, not instrumented (Q2).
- Whether the production 200 ms settle or the rechecker loop can overlap/starve under specific conditions was not proven.
