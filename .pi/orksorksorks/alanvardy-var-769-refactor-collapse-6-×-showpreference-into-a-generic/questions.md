# Research Questions

## Context

The focus is the persisted user-preference layer of SingleThread: the preference-store value types in `SingleThreadCore` (the `Show*Preference` family, `SortOptionStore`, and sibling `*Store` types), their call sites across the iOS app, watchOS app, widget extension, and the phone↔watch sync service, and the App Group `UserDefaults` container (`AppGroup.defaults`). Related test suites (`SingleThreadTests`, `SingleThreadWatchTests`, `SingleThreadUITests`, `SingleThreadWatchUITests`) and the var-759 state-audit artifacts under `.pi/qrspi/alanvardy-var-759-do-a-full-audit-of-state/` are also in scope.

## Questions

1. **Key lifecycle and dataflow**: Trace the complete lifecycle of the six boolean preference keys `showDate`, `showList`, `showRecurrence`, `showAlarms`, `showCompletionGlow`, `showUndatedReminders` — where each key is declared, read, and written across the iOS app (`ContentView`, `AppViewModel`, `ContentViewModel`, settings views), `SingleThreadCore` (`SkippedReminderSyncService`), the watchOS app (`WatchAppViewModel`, the `Show*State` holders), and the widget (`NextThingWidget`). For each site, note which `UserDefaults` container (`AppGroup.defaults` vs `.standard`) is used, and how the sync service pushes and applies values between phone and watch.

2. **Preference-store API family**: Survey the preference-store types in `SingleThreadCore` (the six `Show*Preference` structs, `SortOptionStore`, and the other `*Store` types such as `ExcludedListStore`, `SkipCountStore`, `CompletionCounterStore`, `PendingCompletionStore`, `SkippedReminderStore`). For each, document the initializer shape (`defaults`/`key` parameters and their defaults), read/write API naming, absent-value fallback semantics, and serialization encoding (e.g. `object(forKey:) as? Bool` vs `bool(forKey:)`). Note any naming or semantic inconsistencies between them, and check whether any generic reuse already exists.

3. **Settings UI and change propagation**: Map how the iOS settings UI reads and writes these keys: the `@AppStorage` declarations in `ContentView.swift` (values and store), `SettingsBindings`, the toggle/picker views in `ReminderSettingsView`/`FilterSortSettingsView`, and the full change-propagation chain (`.onChange` handlers, `SettingsViewModel.showPreferenceChanged`, `WidgetCenter` reloads, `AppViewModel`'s `UserDefaults.didChangeNotification` shadow caches and `lastShow*` comparisons). Also list any raw `UserDefaults` reads that bypass the preference structs (e.g. `NextThingWidget.swift:71`) and how previews inject values without touching real defaults.

4. **Test coverage and injection seams**: Document the test conventions covering these preferences: the structure of the per-preference unit-test files (absent-value fallback, save/read round-trip, custom UUID keys on `.standard`), the `SkippedReminderSyncServiceTests`/`WatchSyncPipelineTests` patterns (including any test-side abstraction over the divergent concrete types), serialized-suite tests such as `ShowCompletionGlowStateTests`, init-parameter injection seams (`ContentViewModel`, `SkippedReminderSyncService`), and which keys lack a direct unit-test file. Note the UI tests that toggle these preferences and the `--seed`/`--ui-testing`/`--reset-glow-preference` launch seams they rely on.

5. **State-audit artifacts**: Read the var-759 audit artifacts under `.pi/qrspi/alanvardy-var-759-do-a-full-audit-of-state/` (`audit/inventory.md`, `audit/findings.md`, `plan.md`, `implement-tasks/`). Summarize what they document about the six `show*` keys: the App-Group inventory rows, the dual-read-path table, findings T2.1/T2.3/T2.4/T3.1/T4.4 (including the per-key fallback values and any documented next actions or acceptance criteria), and how the audit's plan and implement-tasks reference these keys.

6. **Shared-code constraints**: Investigate the constraints on code in `SingleThreadCore` shared across the iOS, watchOS, and widget targets: Swift 6 language mode, actor-isolation defaults (which targets set `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and which do not), `Sendable` requirements, how the watch's `@Observable Show*State` holders bridge preference values, and any `#if os(...)` conditional-compilation patterns in the preference-related code. Note the lint/format rules that apply to these files (SwiftLint `--strict`, SwiftFormat options, identifier-length rules).
