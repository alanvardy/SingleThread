## Q2: How does a boolean setting flow from toggle to storage and back to its effect?

### Findings
- **Toggle → bag**: `InterfaceSettingsView.swift:19,84` (`Toggle(isOn: $enableActionButtons)`); row wires `enableActionButtons: $bindings.enableActionButtons` at `SettingsView.swift:46` (iOS) and :55 (macOS). Bag: `SettingsBindings.swift:24` `final class SettingsBindings`, `@Observable`, `@MainActor`; plain in-memory `var enableActionButtons: Bool = false` (:31, :43, :59) — *not* one of the computed store-backed App-Group props (:64+), per header comment :22-24.
- **Durable storage**: `SingleThread/ContentView.swift:95-96` — `@AppStorage("enableActionButtons", store: AppGroup.defaults) var enableActionButtons = false`; **unconditional** across platforms (contrast iOS-gated toggles :99-110).
- **Write-back**: `ContentView+Settings.swift:31-32` (iOS) and :24-25 (macOS) `.onChange(of: bag.enableActionButtons) { _, new in enableActionButtons = new }` persists through the `@AppStorage` property (comment :19-22: standard-suite keys written back so settings survive relaunch; store-backed props need no write-back).
- **iOS relay to view model**: `ContentView.swift:258-262` `.task` initial fill and :267-271 `.onChange` live propagation, both `#if os(iOS)` → `ContentViewModel.swift:74-79` `var enableActionButtons` (comment "Mirrors ContentView's @AppStorage"), driving `showsActionButtons = enableActionButtons && store.visibleReminders.first != nil` (:81-83).
- **iOS point of effect**: `ContentView+ActionMenu.swift:6-8` `showActionMenu` → `SingleThreadCore/.../ActionMenuGate.swift:9-12` pure AND gate (`enableActionButtons && canMutate && hasVisibleReminder`); `skipButton` branch :24-45 (toggle OFF = direct skip).
- **macOS point of effect**: `ContentView+ActionMenu.swift:84-93` `macShowActionMenu` reads `AppGroup.defaults.bool(forKey: "enableActionButtons")` **straight from the store** — no `@AppStorage`/ViewModel relay (comment :86-88: phone-side toggle applies on macOS via the shared suite).
- **Sync pack/unpack of the same key**: `SingleThreadCore/.../SkippedReminderSyncService.swift:209` push; :448-451 receive.
- **Key asymmetry**: iOS = toggle → bag → write-back → `@AppStorage` property → ViewModel → gate. macOS = no authoritative UI path locally; value enters the App Group only via phone/watch sync, and the gate reads the store directly. `AppViewModel.swift:231,314` seed the key during UI tests.

- **Watch side**: `SingleThreadWatch/ShowEnableActionButtonsState.swift:15` init reads `AppGroup.defaults.bool(...)`; :22-29 `apply(value:)` persists to `AppGroup.defaults` and publishes; wired `SingleThreadWatch/WatchAppViewModel.swift:293-295`. Watch config (`makeSyncService()` :228-245) uses `.standard` stores and `sendsShowDate/.../sendsEntitled: false` — **the watch never pushes these prefs back**.
- **Test seeding**: `SingleThreadCore/.../UITestingSeed.swift:48-56` decodes `--seed '<json>'`; :74-85 `resetPersistedState()` removes `persistedKeys` (includes `"enableActionButtons"` :114) from both `AppGroup.defaults` and `UserDefaults.standard`; applied at `AppViewModel.swift:205`, with :222-231 `--ui-testing` setting `AppGroup.defaults.set(true, forKey: "enableActionButtons")`.

## Cross-Cutting Observations
- **One key, two read paths** is the established shape for shared settings: iOS persists via `@AppStorage(store: AppGroup.defaults)` + write-back and optionally relays into the ViewModel; macOS reads `AppGroup.defaults.bool(forKey:)` directly (`ContentView+ActionMenu.swift:84-93`). `enableActionButtons` is the closest full precedent (shared toggle, App-Group store, sync payload), but it is a **shared** (both-platform) surface — there is **no existing macOS-only toggle** anywhere in the Settings tree; macOS-only UI today means whole-file gating (`MenuBarExtraOptions.swift`) or hidden-rows (`SettingsView.swift:65-77`).
- **Phone is author, watch and macOS are consumers**: the watch never pushes preferences back (`WatchAppViewModel.swift:228-245`); receive-sides only write `AppGroup.defaults`; macOS settings UI write-backs only re-persist what was synced.
- **Settings conventions**: rows are `NavigationLink` + `SettingsLinkLabel` + `.accessibilityIdentifier("settings…Row")`; toggles are `Toggle(isOn: $binding)` inside `Form`; destinations must end `.settingsSubscreenLayout()`; bindings flow through one `SettingsBindings` bag re-built on each settings open; iOS-only vs macOS-only rows are expressed as `#if os(...)` in `SettingsView.swift`'s Section/list.
- **widget presence is not governed in-repo at all**: the widget is iOS-embedded, never registers anything dock/gallery-related, and no disable mechanism exists — the entire presence surface is outside this codebase (the unknown classify flagged).

## Open Areas
- **macOS dock-widget hosting/registration API — zero in-repo evidence** (Q4): how `SingleThreadWidget.appex` surfaces in the macOS dock, whether the macOS app carries it, and what WidgetKit API shows/hides it are all **unknown and outside the repo**. Design must research WidgetKit's macOS widget-gallery surface (or the product-level decision about how the widget reaches macOS) before any implementation approach is credible. Flagged `UNVALIDATED` for the design phase.
- **UserDefaults is an external type** (Q3): full API surface (suite fallback semantics, notification payloads, `access(keyPath:)` vs `object(forKey:)`) is only observable through call sites; deeper semantics need the WidgetKit docs or `tools:dump`-style verification later.
- **`Info.plist` manifest details** (Q4): `com.apple.widgetkit-extension` NSExtensionPointIdentifier noted by locator recon; gallery-facing fields (display names, capabilities) live there but were not read in depth.
- **macOS `enableActionButtons` edit path**: Q2 found the macOS write-back (`ContentView+Settings.swift:25`) only re-persists synced values; whether macOS can author the value locally today is unclear from source alone (no macOS-only UI drives it).
