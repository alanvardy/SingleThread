# Research Findings

## Q1: macOS app surface & lifecycle

### Findings
- **One shared app target, one scene.** `SingleThreadApp.swift:9-10` (`@main struct SingleThreadApp: App`); `body` is a single `WindowGroup` wrapping `ContentView` (`SingleThreadApp.swift:19-24`) — byte-identical for macOS and iOS, no scene modifiers. No `.commands`, `MenuBarExtra`, `CommandMenu`, `buildMenu`, `windowStyle`, or `defaultSize` anywhere in the app target (grep-verified, zero matches).
- **Delegate adaptors are the only platform divergence in the App struct**: iOS `@UIApplicationDelegateAdaptor(AppDelegate.self)` gated `#if os(iOS)` (`SingleThreadApp.swift:31-34`); macOS `@NSApplicationDelegateAdaptor(MacAppDelegate.self)` gated `#if os(macOS)` (`SingleThreadApp.swift:35-38`). `AppViewModel()` is constructed eagerly in `init()` (`:13-16`).
- **`MacAppDelegate` bridges only appearance.** `final class MacAppDelegate: NSObject, NSApplicationDelegate` (`AppDelegate.swift:67`), inside the `#if os(macOS)` block (`AppDelegate.swift:62`). `static func applyAppearance(_ mode: AppearanceMode)` iterates `NSApp.windows` setting `window.appearance = mode.appKitAppearance` (`AppDelegate.swift:72-75`). Applied at `applicationDidFinishLaunching` (`:77-79`) and `applicationDidBecomeActive` (`:81-83`) via `applyLaunchAppearance()` → `AppearanceMode.load()` (`:87-90`). No menu construction, no window management beyond appearance, no notification code.
- **Keyboard shortcuts are all SwiftUI `.keyboardShortcut` modifiers** — no `NSMenu`/`NSMenuItem`/`keyEquivalent`/`onCommand` anywhere (grep zero). Full inventory is in `ContentView+ActionMenu.swift`: Complete `"c"` `modifiers: []` (`:105`), Delete `.delete` (`:122`), Skip `Menu` wrapper and direct button `"s"` (`:129`, `:144`). `macDeleteButton` deliberately has no shortcut (`:150-167`).
- **No explicit app menus**: only SwiftUI's generated defaults (Application/File/Edit/View/Window/Help) exist for the `WindowGroup`. The only `Menu` in the codebase is the in-window card action menu (`ContentView+ActionMenu.swift:112-135`) — view content, not an app menu. macOS-only view-level affordances: top-left refresh overlay (`ContentView.swift:210-215`, `#if os(macOS>`), settings gear (`ContentView.swift:194-209`), bottom-bar `actionButtons` while a reminder is visible (`ContentView.swift:631-635`).
- **`ContentView+ActionMenu.swift` has no platform suffix**; gating is internal `#if os(iOS)` (`:14-66`) / `#if os(iOS)` block + `#if os(macOS)` (`:70-172`) split. Header comment (`:5-10`) says the split exists to keep `ContentView.swift` under SwiftLint `type_body_length`. iOS surface: `confirmation Dialog` with Skip/Reschedule/Delete (`:46-63`). macOS surface: `macCompleteButton` (`:96-109`), `macActionMenu` Menu with Skip/Reschedule/Delete + shortcuts (`:111-133`), `macSkipButton` (`:135-148`), `macDeleteButton` (`:150-167`), shared `actionMenuRescheduleSheet` (`:175-193`). macOS toggle ON reads `AppGroup.defaults.bool(forKey: "enableActionButtons")` (`:89-93`, comment `:71-74`).

## Q3: Appearance switching

### Findings
- **`AppearanceMode` enum** (`AppearanceMode.swift:15-18`): `.system`/`.light`/`.dark`. iOS mapping `var windowOverrideStyle: UIUserInterfaceStyle` (`:22-29`, `.system → .unspecified`); macOS mapping `var appKitAppearance: NSAppearance?` (`:34-42`, `.system → nil`, `.light → .aqua`, `.dark → .darkAqua`); preview-only `colorScheme` (`:48-55`). Persistence reader `static func load(from defaults: UserDefaults = .standard)` key `"appearanceMode"` (`:76-85`).
- **`@AppStorage` key**: `@AppStorage("appearanceMode") var appearanceMode = AppearanceMode.system` (`ContentView.swift:72-73`) — **standard `UserDefaults` (no `store:`)**, so *not* shared via the App Group; not read by widget/watch.
- **macOS path**: `MacAppDelegate.applyAppearance(_:)` sets `NSWindow.appearance` per window (`AppDelegate.swift:72-75`); call sites: launch `applicationDidFinishLaunching` → `applyLaunchAppearance()` (`:77-79`, `:87-90`), `applicationDidBecomeActive` (`:81-83`), and live change via `.onChange(of: appearanceMode)` (`ContentView.swift:277-281`-ish) → `ContentViewModel.handleAppearanceMode(_:)` (`ContentViewModel.swift:130-135`, `#elseif os(macOS)` branch). `NSApp.appearance` is never set; no OS-change observer (`AppleInterfaceThemeChangedNotification` etc. — zero grep matches).
- **iOS path**: `AppDelegate.applyAppearance(_ mode:to windows: [UIWindow]? = nil)` (`AppDelegate.swift:15-23`) sets `window.overrideUserInterfaceStyle == mode.windowOverrideStyle` on all windows of connected `UIWindowScene`s; `.system → .unspecified` (`:12-14`). Triggered at `applicationDidBecomeActive` (`:45-48`) and the same `.onChange` → VM dispatch. No `.preferredColorScheme` in app code (previews only, `ContentView+Previews.swift:39,:57`).
- **Settings UI**: shared `InterfaceSettingsView` with `Picker` `appearancePicker` id and `@Binding var appearanceMode` (`InterfaceSettingsView.swift:9, :35-46`), instantiated from `SettingsView.swift:40-49` (iOS, 7 bindings) and `:50-56` (macOS, 3 bindings). The `SettingsBindings` bag holds it in memory (`SettingsBindings.swift:64`, init default `.system` `:22`); write-back to `@AppStorage` via `.onChange(of: bag.appearanceMode)` (`ContentView+Settings.swift:19`).
- **Platform differences**: mechanism (UIKit `overrideUserInterfaceStyle` vs AppKit `NSWindow.appearance`), signature (writable `windows` param on iOS), launch-timing (iOS only on activate, macOS on finish-launch AND activate), scope (all scene windows vs `NSApp.windows`).
- **Widget/watch**: no appearance code in either target (grep zero); widget follows system appearance (`NextThingWidget.swift:98-99` containerBackground).

## Cross-Cutting Observations
- **One app target, one scene, dual delegates**: the app is a single multiplatform target (`SDKROOT = auto`, `SUPPORTED_PLATFORMS` incl. macosx); every platform difference flows through `#if os(...)` and the two delegate classes in `AppDelegate.swift`. Appearance, notifications, action surface, bottom bar, undo, refresh, dictation-availability, settings rows, and test categories all diverge this way — there is no `+macOS` file and no `MenuBarExtra`.
- **macOS currently gets no app-level chrome**: no commands/menus beyond SwiftUI defaults, no app menu items, no MenuBarExtra, no macOS notifications (permission/schedule/cancel code is entirely iOS-gated in `AppViewModel`). The only macOS-first affordances are the bottom-bar action buttons, refresh overlay, and settings min-frame.
- **Shared state is App-Group `UserDefaults`; appearance is deliberately not**: `AppGroup.defaults` carries prefs/action state/skip/completion data synced phone↔watch (WatchConnectivity) and read by the widget; `appearanceMode`, `textSize`, and background prefs stay in `.standard` and are app-local — consistent with there being no appearance handling in widget/watch.
- **The store is the gatekeeper**: `guard canMutate` (freemium cap 100) plus per-action guards in `ReminderStore` are authoritative across iOS/macOS/watch/widget; view-level gates (`ActionMenuGate`, `hasVisibleReminder`-style `visibleReminders.first` checks) only choose rendering surfaces.
- **Testing convention**: unit (Swift Testing, headless view assertions via `String(describing:)`) + UI (XCTest with launch-arg seams + accessibility audits); macOS is unit-tested only (`-only-testing:SingleThreadTests` in Makefile, script, CI) — macOS UI tests were explicitly removed by decision.
