# Research Questions

## Context

Focus areas: `SingleThreadCore`'s `EntitlementStore` (StoreKit 2 entitlement derivation), the `EntitlementStoreTests` suite in `SingleThreadTests`, the macOS unit-test stage of the project's test infrastructure (`scripts/test.sh`, `Makefile`, `.github/workflows/ci.yml`), and StoreKit 2's transaction persistence on a macOS development host where the app has previously completed purchases. Questions ask how these pieces work today; no changes are proposed.

## Questions

1. Trace, end to end, how a fresh `EntitlementStore()` instance derives `isEntitled` and `hasResolvedEntitlement` at init on macOS: which StoreKit APIs are consulted (`Transaction.currentEntitlements`, `Transaction.updates`, `AppStore.sync()`), in what order the init-spawned async refresh settles the flags, and whether those reads are scoped to the app's StoreKit transaction store on the host (file paths, storekitd) or to an active `SKTestSession`. Cite `SingleThreadCore/Sources/SingleThreadCore/EntitlementStore.swift` and `SingleThreadTests/EntitlementStoreTests.swift`.

2. How does `SKTestSession` (StoreKitTest framework) interact with the macOS host's persistent StoreKit transaction store? When a session with `configurationFileNamed: "Products"` and `disableDialogs = true` is created and later disposed on a host that already has entitled transactions from prior app runs, which store do `Transaction.currentEntitlements` and `Transaction.updates` read from? What exactly do `clearTransactions()`, session teardown, and session deallocation affect, and which stores survive between sessions and between test runs?

3. How does the app itself persist entitlement-relevant state on macOS? Walk the purchase/restore flow (`SingleThread/PurchaseSettingsView.swift`: `product.purchase()` → `entitlementStore.sync()` → `refreshEntitlement()`) and identify every persistent artifact written on the host — StoreKit transaction store, keychain, UserDefaults suites, sandbox container paths. What documented or scriptable procedure exists (Apple documentation, developer forums) to inspect or remove an entitled transaction, or to reset the macOS StoreKit store for a development app?

4. How is the macOS unit-test stage run locally versus in CI, and what differs between the two environments? Map `scripts/test.sh`'s macOS unit-test invocation and the CI `mac-tests` job (destinations, `CODE_SIGNING_ALLOWED`, derivedData paths, runner freshness), and enumerate every hook available to `xcodebuild test` runs for setup before or after tests — scheme `TestAction` vs `LaunchAction` configuration (including placement of the `StoreKitConfigurationFileReference` for `Products.storekit`), xctestplan pre-actions, environment variables, and how `SKTestSession(configurationFileNamed:)` discovers the config file in the test bundle.

5. What is the current isolation story for the `EntitlementStoreTests` suite? Enumerate how each of the seven tests constructs its store (real StoreKit path vs the `testingWithEntitled:` / `testingWithEntitlementUnresolved:` seams), which tests await the async refresh and how (fixed sleep vs polling loop), the role of `@Suite(.serialized)`, and the presence or absence of setUp/tearDown hooks. Also report the prior in-repo experiment records that mention `clearTransactions()` (e.g. `.pi/qrspi/alanvardy-var-789-skipped-sizing/implement.md`) — what was observed when used in-test, and what open questions remain about its side effects.

6. What state-reset conventions already exist in this codebase for test setup? Survey `SingleThreadCore/Sources/SingleThreadCore/UITestingSeed.swift` (`resetPersistedState`), the `--seed` / `--ui-testing` launch-arg seams in `AppViewModel`, and any test code that clears UserDefaults / App Group / keychain state — which stores are covered, how the reset is wired into app launch, and whether any StoreKit / storekitd state is touched anywhere. List the exact keys and stores each reset touches.
