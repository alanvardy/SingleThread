# Research Findings

## Q1: How does the watch reminder sheet UI invoke a reschedule, and what happens in the view model and the sheet when the action is confirmed?

### Findings
- Invocation chain: Skip button handler (`SingleThreadWatch/WatchReminderView.swift:143-146`) checks `canShowActionMenu` (`:81-85` — `viewModel.showEnableActionButtonsState.isEnabled && viewModel.store.canMutate && viewModel.store.visibleReminders.first != nil`). If true it opens `.confirmationDialog("Reminder", isPresented: $viewModel.isShowingActionMenu)` (`:277`); otherwise it calls `skipCurrentReminder()` directly. The menu's "Reschedule" button (`:215-217`) sets `isShowingActionMenu = false` and `isShowingRescheduleSheet = true`; the sheet is attached via `.sheet(isPresented: $viewModel.isShowingRescheduleSheet) { actionMenuRescheduleSheet() }` (`:280-281`).
- View-model state (`SingleThreadWatch/WatchReminderViewModel.swift`): `isShowingActionMenu` (`:68`), `isShowingRescheduleSheet` (`:71`), `rescheduleDate = Date().addingTimeInterval(86400)` (`:74`, defaults to tomorrow). There is **no** success/failure/feedback state field.
- Sheet body `actionMenuRescheduleSheet()` (`WatchReminderView.swift:290-318`): a `DatePicker("Reschedule to", selection: $viewModel.rescheduleDate, displayedComponents: [.date])` (date-only, `:294-297`); Confirm `Button("Reschedule")` with `.accessibilityIdentifier("rescheduleConfirmButton")` (`:311`) extracts a **date-only** `DateComponents` from `viewModel.rescheduleDate` (`:299-301`, time dropped), then `if let id = viewModel.store.visibleReminders.first?.calendarItemIdentifier` → `Task { await viewModel.store.rescheduleReminder(identifier: id, to: components); viewModel.isShowingRescheduleSheet = false }` (`:303-306`); the no-id branch just closes the sheet (`:307-309`); Cancel closes it (`:315-317`).
- The store's Bool return is ignored: the result of `rescheduleReminder` is dropped (`@discardableResult`) and the sheet closes unconditionally after the await (`:304-305`).
- Visible feedback: **none beyond the sheet closing** — no confirmation, no error toast when the call returns false, no refresh/reload. `refresh()`/`refreshFromCardTap()` (`WatchReminderViewModel.swift:142-157`) are the only list repopulators and are never called by the reschedule path.
- On watchOS the store call itself is a pure relay — see Q2 (`ReminderStore.swift:367-372`).

## Q2: What exactly does ReminderStore.rescheduleReminder do on each platform target?

### Findings
- Single method, compile-time split: `@discardableResult public func rescheduleReminder(identifier: String, to due: DateComponents) async -> Bool` (`SingleThreadCore/Sources/SingleThreadCore/ReminderStore.swift:366-367`). Shared prologue: `guard canMutate else { return false }` (`:368`); `canMutate` at `:183` = `entitlementStore.isEntitled || completionCounter.count < EntitlementStore.freemiumCap`.
- watchOS branch (`:369-372`): snapshot `onRescheduleReminder` (`:113`) and nil-safe invoke `handler?(identifier, due)`, then `return true` — unconditionally, whether or not the hook is set and regardless of relay outcome. No EventKit write, no skip mutation, no settle, no reload, no catch.
- iOS branch (`:373-388`): find in the in-memory `reminders` array by `calendarItemIdentifier` only, no completion filter, no refetch (`:374-376`; not found → `false`); mutate `reminder.dueDateComponents = due` (`:378`); `eventStore.save(reminder, commit: true)` — the only EventKit write (`:379`); `resetSkipCount(for: identifier)` (`:380`, impl `:592-597`, persists a pruned map only when the id was present); `await settle()` (`:381`, production default sleeps 200 ms at `:39-41`); `await reload()` (`:382`, impl `:450+` — refetch, reconcile skips/excluded, pending-completion filter, prune, fire `onRemindersChanged?`); `return true` (`:383`). Single catch logs `"Failed to reschedule reminder"` at error (`:385`) and returns `false` (`:386`); a committed save followed by a settle/reload throw is still reported `false`.
- Sibling contrast: `completeReminder` filters `!$0.isCompleted` on find; `rescheduleReminder`'s find has no such filter, like `deleteReminder` (`:374-376`).
- `onRescheduleReminder` is a plain optional callback slot, not an observer bag (`ReminderStore.swift:113`).

## Q3: How does the SkippedReminderSyncService relay contract work?

### Findings
- Seams: `protocol SkipSyncSession: AnyObject` (`SingleThreadCore/Sources/SingleThreadCore/SkippedReminderSyncService.swift:8-15`) with `activate()` / `updateApplicationContext(_:) throws` / `sendMessage(_:replyHandler:errorHandler:)`; `extension WCSession: SkipSyncSession {}` (`:17`). The service is `final class SkippedReminderSyncService: NSObject, WCSessionDelegate` (`:19`), compiled only under `#if os(iOS) || os(watchOS)`.
- Request side: `requestRescheduleReminder(identifier, dueDateComponents)` (`:268`) builds `var payload: [String: Any] = [PayloadKey.rescheduleReminderIdentifier: identifier]` (`:269`; `"rescheduleReminderIdentifier"` at `:348`), copies only non-nil year/month/day/hour/minute into a plist-safe `[String: Int]` dict (`:270-279`), stores it under the literal key `"dueDateComponents"` (`:280`), then `session.sendMessage(payload, replyHandler: nil) { error → log }` (`:283-285`) — fire-and-forget, no reply handler, errors only logged.
- Receive side: `session(_: WCSession, didReceiveMessage message: [String: Any])` (`:300`); reschedule branch (`:314-325`) fires **only when both** `message["rescheduleReminderIdentifier"] as? String` and `message["dueDateComponents"] as? [String: Int]` decode; builds `DateComponents()` nil-coalescing each field (`:316-321`), snapshots `onRescheduleReminderReceived` (`:108`) to a local, then `handler?(identifier, components)` (`:322-323`).
- Hooks: `public nonisolated(unsafe) var onRescheduleReminderReceived: ((String, DateComponents) -> Void)?` (`:108`); doc (`:101-107`) states the write-once-before-`activate()` happens-before invariant. Same shape for `onCompleteReminderReceived` (`:88-89`) and `onDeleteReminderReceived` (`:95-96`).
- Activation: `activate()` (`:189-196`) assigns `wcSession.delegate = self` only for a real `WCSession` (not the `FakeSession` test double), then `session.activate()`; activation errors log only (`session(_:activationDidCompleteWith:error:)`); iOS-only `sessionDidBecomeInactive`/`sessionDidDeactivate` re-activates (`:334-338`).
- Wire keys: `PayloadKey` enum `:342-365` keeps most keys symmetric; `"dueDateComponents"` is a bare string literal duplicated at `:270`/`:310` with no enum constant.
- Callers: watch side `SingleThreadWatch/WatchAppViewModel.swift:211-227` (`store.onRescheduleReminder = { identifier, components in service.requestRescheduleReminder(identifier:, dueDateComponents:) }` at `:221-224`); phone side `SingleThread/AppViewModel.swift:380-415`.

## Q4: How does the iPhone-side AppViewModel.setupSyncService wire its receive hooks, and what guards constrain the path?

### Findings
- `init` (`SingleThread/AppViewModel.swift:16-23`) builds the store and notes `usesInMemoryStore` (`:55`); `setupSyncService(with: store)` runs inside `init` under `#if os(iOS)` (`:29-30`), before the timeline-reload hook and observation setups (`:33-45`).
- Guard: `guard WCSession.isSupported(), !usesInMemoryStore else { return }` (`:380-381`) — either failure means no service, no handlers, no activation. `usesInMemoryStore` is true **only** for the `--seed '<json>'` launch path (`:142-144`); the iOS `--ui-testing` seam builds an `InMemoryEventStore`-backed store but reports `false` (`:215-231`), so the live sync service is still wired on that seam. Production returns `(ReminderStore(loadsReminders: loads), false)` (`:232-236`).
- Construction and hooks: service built with `session: WCSession.default` plus preference stores and flags (`:382-394`); receive handlers assigned **before** `service.activate()` (`:405-414`) per the write-once-before-activate invariant. Reschedule receive hook (`AppViewModel.swift:405-407`):
  `service.onRescheduleReminderReceived = { [weak store] identifier, components in Task { await store?.rescheduleReminder(identifier:, to: components) } }`
  — the `[weak store]` capture + `store?.` safe call silently drop the message if the store is gone; the body funnels onto MainActor and the EventKit write happens inside the core method.
- Post-activation store→service hooks (`:416-425`): `onSkipSetChanged` / `onShowUndatedRemindersChanged` / `onExcludedListsChanged` → `pushAll()`; `onCompleteReminder` / `onDeleteReminder` → request methods; `onSortOptionChanged` → save + pushAll.
- Constraint stack for an incoming reschedule to reach EventKit: iOS-only compile (`:29`); `WCSession.isSupported()` and non-in-memory store (`:381`); typed decode of both payload keys (Q3); non-nil handler + weak store (activation ordering guarantees the handler exists by the first post-activation message); the rest is inside `ReminderStore.rescheduleReminder` (Q2).

## Q5: What existing tests and seams cover the reschedule chain, and which hops are unexercised?

### Findings
- `SingleThreadTests/RescheduleSyncTests.swift` (iOS/watchOS-gated, `FakeSession`): `requestRescheduleReminderSendsMessage` (`:14`) asserts payload keys; `requestRescheduleOmitsNilComponents` (`:36`); `receiveRescheduleReminderFiresHook` (`:60`), `receiveMessageWithoutRescheduleKeyIsNoOp` (`:87`) drive the service decode+hook.
- `SingleThreadWatchTests/ReminderStoreWatchTests.swift`: `rescheduleFiresRelayHookAndReturnsTrue` (`:96-127`) and `rescheduleNoOpWhenGated` (`:128-150`) cover the watch store branch incl. the `canMutate` gate (uses `InMemoryEventStore(loadsReminders: false)`).
- `SingleThreadTests/ReminderStoreTests.swift` (`#if !os(watchOS)`): `rescheduleResetsSkipCount` (`:732`), `reschedulePreservesRecurrenceOnRepeatingReminder` (`:754`).
- `SingleThreadTests/EventKitStoringTests.swift` (FakeEventStore seam): `reschedulePersistsDueDateAndReloads` (`:274`, save count 1, commit true, reload fetch counts), `rescheduleUnknownIdentifierIsNoop` (`:298`), `rescheduleFailureReturnsFalse` (`:313`, `saveShouldThrow`), `reschedulePreservesRecurrenceRules` (`:331`).
- `SingleThreadWatchTests/WatchReminderViewModelTests.swift`: **zero reschedule coverage** — no test drives the view-model sheet state (`WatchReminderViewModel.swift:66-74`) or the confirm call (`WatchReminderView.swift:280-305`). `WatchSyncPipelineTests` (own `WatchFakeSession`) and the two UI test suites contain no reschedule references.
- Chain hops and coverage: 1 watch sheet→store unexercised · 2 watch store relay driven · 3 sendMessage payload driven · 4 WCSession transport/activation/reply/error **unexercised** (`FakeSession` at `SingleThreadTests/TestFixtures.swift:66-94` records `lastMessage`/`lastContext` but never invokes reply or error handlers) · 5 phone decode→hook driven · 6 AppViewModel hook→store wiring **unexercised** · 7 iOS EventKit write driven.
- Seam notes: reschedule tests use `UserDefaults.standard` with UUID-suffixed keys + `defer` cleanup (e.g. `ReminderStoreWatchTests.swift:99`, `RescheduleSyncTests.swift:17`); **no reschedule test uses `AppGroup.defaults`**. `--seed`/`--ui-testing` seams are covered only by `UITestingSeedTests` parsing (`SingleThreadTests/UITestingSeedTests.swift:12-46`), no reschedule flow.

## Cross-Cutting Observations
- The chain is fire-and-forget end to end: `sendMessage` has no replyHandler (`SkippedReminderSyncService.swift:283-285`), the watch store branch returns `true` unconditionally (`ReminderStore.swift:369-372`), hook invocations are nil-safe (`handler?`), and the phone hook uses a weak store with a safe call (`AppViewModel.swift:405-407`) — every hop can silently drop the operation with no observable consequence on the watch.
- No feedback path exists by design of the watch UI: the sheet closes unconditionally, the `Bool` return is discarded, no refresh occurs (Q1). A failure at any downstream hop is indistinguishable from success.
- The confirm path sends **date-only** components — the watch picker shows only `.date` and drops time at confirm (`WatchReminderView.swift:294-301`), and the sender omits nil hour/minute fields (`SkippedReminderSyncService.swift:270-279`).
- Both sides share the write-once-before-`activate()` invariant and handler-snapshot-before-invocation pattern (Q3/Q4), keeping hooks race-free by convention.
- The `canMutate` gate (`ReminderStore.swift:183`) plus `canShowActionMenu` gating (`WatchReminderView.swift:81-85`) mean reschedule is hidden behind enable-action-buttons state, a visible reminder, and entitlement/freemium availability.
- The `--seed` seam short-circuits phone sync (`usesInMemoryStore: true`, `AppViewModel.swift:142-144,381`) while the `--ui-testing` seam does not (`:215-231`) — an inversion that matters for any end-to-end test design.

## Open Areas
- `WCSession.isSupported` / `WCSession.default` / delegate dispatch are external WatchConnectivity SDK internals not readable in this repo (`SkippedReminderSyncService.swift:189-196`, `AppViewModel.swift:380-381`).
- No in-repo test or path verifies a message is actually delivered over a real session (hop 4) or that the phone's hook→store wiring executes (hop 6).
- Real `EKEventStore` save/commit semantics are never exercised; all write tests use `InMemoryEventStore` / `FakeEventStore` (Q5).
- Why the reported symptom ("visibly does nothing") occurs — which specific hop is broken — cannot be determined from the code alone; the chain's silent-drop design makes every hop a candidate.
