## Q4: Today and calendar-date window semantics

### Findings

- **`ReminderDateFilter`** — the only date-window logic, `nonisolated enum` (`ReminderDateFilter.swift:26`), all members defaulted to `Calendar.current`/`Date()`: `endOfToday` :27-36 (startOfDay +1 day −1 s); `overdueCutoff` :38-49 (default `days: 30`, startOfDay −30 d); `isInCurrentWindow` :51-62 (nil date → true; else `overdueCutoff <= date <= endOfToday`).

## Cross-Cutting Observations

- **Single completion path, many surfaces**: one mutation (`completeReminder` iOS branch) drives counter increment, undo retention, skip reset, reload, and — via view-model observation — the glow, empty-state transition, and watch-visible counter. Any new momentum feedback would attach to this same seam (`ReminderStore.swift:239-253`) plus its view models.
- **`completionCount` is already watch-synced but there is no post-completion push** — `pushAll` always carries it (:208), the watch persists it (`WatchAppViewModel.swift:197-200`), but the phone only pushes on skip/pref changes, not on completion (`AppViewModel.swift:404-415`).
- **No date-aware persistence anywhere**: the only persisted counters (`completionCount`, `skipCounts`) are undated; the only day-window is a single `[now−30d, endOfToday]` computed in `ReminderDateFilter` inside `reload()`. Streak or per-day-history semantics would be net-new. Day boundaries always derive from `Calendar.current`/`Date()` device-local.
- **Watch-shared values must default to `AppGroup.defaults`** (suite exists on iOS/simulator, `.standard` on watch) — the divergence is silent, per AGENTS.md; every new persisted key needs the `seededStore`/`resetPersistedState`/payload-key inventory updated in lockstep.
- **UI feedback convention**: transient surfaces are preference-gated (except creation bubble), auto-dismissing via `Task.sleep` or timer tasks, hidden from a11y unless a `--ui-testing` flag is set, and mirrored on watch via `.standard`-backed `Show*State` holders.
- **Test seams are mature**: `InMemoryEventStore` + `TestFixtures` + `--seed` + UUID-isolated suites + `noopSettle` cover store-state assertions with clear patterns; new persisted state should follow the `SkipCountStore`/`CompletionCounterStore` pattern (store class + `@Suite(.serialized)` store tests + integration tests through `ReminderStore` + seed/round-trip/sync coverage).

## Open Areas

- Whether the watch should surface any new momentum feedback at all — no existing watch surface shows completion counts or history of any kind, so there is no precedent to cite.
- Day-boundary edge semantics (e.g. how "today" behaves across timezone/`Calendar.current` changes on-device) are untested beyond the UTC seam; no persistence of "day" values exists to model against.
- `completionCount` can currently diverge between phone and watch between pushAll events; whether momentum feedback must be exactly watch-synced has no existing pattern to reference.
- Freemium gating (`canMutate`) and undo interplay with any new counter (e.g. does undoing a completion decrement a same-day or streak counter?) has no precedent — undo currently decrements `completionCount` only.
