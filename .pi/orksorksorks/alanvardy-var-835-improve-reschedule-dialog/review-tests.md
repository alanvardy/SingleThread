## Review — Test quality & fragility (RescheduleSheetTests.swift new tests)

**Verdict: BLOCK no — the tests pass and follow house style, but as written they overclaim. The a11y "combine" fix (the PR's point) is effectively not tested, one ordering intent is pinned only by an SDK type-name token, and one negative assertion (`Spacer`) is a weak proxy. Precedent inspection: the cited SwipePromptTests.swift:44-53 is itself the weakest kind of structural test and does not prove "stable token" persistence; the same precedent file contains the better pattern (range-ordering) that these tests should have used.**

### Per-assertion findings

**fix-now — RescheduleSheetTests.swift:81** — `#expect(description.contains("AccessibilityAttachmentModifier"))` is *non-discriminating*. Both `rescheduleDatePicker` (RescheduleSheet.swift:33) and `rescheduleConfirmButton` (:43) carry `.accessibilityIdentifier(...)`, which already serializes as `AccessibilityAttachmentModifier` (the same token SwipePromptTests relies on for its Dismiss button). The test passes identically with or without the new `.accessibilityElement(children: .combine)` (RescheduleSheet.swift:36) — the one behavior this PR exists for. Why it matters: it gives false confidence that the a11y improvement is verified, while the project's test bar ("a bug-fix ticket is done only when a test reproduces the *reported symptom*") isn't met. Fix: drop the assertion, or first verify what `.accessibilityElement(children: .combine)` serializes to and assert *that*; otherwise rely on the accessibility-audit UI seam if one covers the sheet (none exists today — see last finding).

**fix-now — RescheduleSheetTests.swift:64** — `#expect(description.contains("HStack<"))` pins a SwiftUI type name, and it does not test the claimed behavior. The test's name says "LabelBesidePicker" but the assertion only proves *some* HStack exists somewhere in the tree — it doesn't verify the `Text("Reschedule to")` and the `DatePicker` are siblings or that the label precedes the picker. An innocent refactor (row container renamed, layout switched to explicit `Layout`/`Row`) breaks the test for no behavior change; conversely the label could be moved outside the HStack and this still passes. Fix: use the repo's existing ordering pattern — `description.range(of: "Reschedule to")` vs `description.range(of: "DatePicker<")`, as already done in SwipePromptTests.swift:19-24 and MicrophoneToggleTests.swift:225-231 — which directly pins "label beside (before) picker" without naming the container.

**optional — RescheduleSheetTests.swift:99** — `#expect(!description.contains("Spacer"))` is a weak proxy both ways. False-pass: if the full-width intent (`RescheduleSheet.swift:42`, `.frame(maxWidth: .infinity)`) regresses to a compact left-aligned button without a Spacer, the test still passes — nothing asserts full-width at all. False-fail: a legitimate Spacer added elsewhere in the sheet (e.g., between VStack rows) trips it, and a substring match on the type name could catch unrelated tokens after SDK changes (a specificity risk, not a current bug). Fix: drop it, or pin the actual `.frame(maxWidth: .infinity)` serialization if the description reflects it; don't overload `rescheduleSheetConfirmUsesProminentStyle` with a layout claim.

**optional — RescheduleSheetTests.swift:63, 80** — `contains("DatePicker<EmptyView")` is the *load-bearing* assertion of the whole set: it guards the exact regression the diff fixes (old code embedded `"Reschedule to"` in the DatePicker label slot, RescheduleSheet.swift pre-diff; the watch twin WatchReminderView.swift:294 still does). It is the only thing preventing a duplicated label. It is, however, an SDK serialization token — `EmptyView` is the label slot rendered under `.labelsHidden()` — and it will break on an innocent SDK description change. Keep it, but annotate it as an SDK-token guard to revisit on toolchain bumps (see next).

**optional — drift risk across SDK versions.** `.mise.toml` pins only swiftlint/swiftformat/periphery — the Swift/SwiftUI SDK is unpinned and comes from CI/runner defaults, and `String(describing:)` output format is SDK-controlled. `HStack<`/`DatePicker<EmptyView`/`BorderedProminentButtonStyle`/`AccessibilityAttachmentModifier` are all tree-serialization tokens, not behavior; a single SDK bump can fail all three tests with no behavior change. This is the repo's known cost of the pervasive describe-string pattern (SingleThreadButtonModifierTests, SettingsSubscreenLayoutTests, SwipePromptTests all do it), so it's a method-level concern, but the new tests add three more surfaces for an unguarded dependency.

**keep — RescheduleSheetTests.swift:62, 79 (`contains("Reschedule to")`)** — meaningful as a literal-copy smoke check (consistent with house pattern of asserting visible copy), and free. But note it **cannot detect duplication**: `contains` passes whether the string appears once (Text only) or twice (Text + picker label re-added). The duplicate guarantee rests solely on the `DatePicker<EmptyView` token, so don't read the literal assertion as the duplicate guard.

**keep — RescheduleSheetTests.swift:95, 98** — `BorderedProminentButtonStyle` + `!SingleThreadButtonModifier` is the best-justified pair: it pins a real diff change (`.buttonStyle(.borderedProminent)`, RescheduleSheet.swift:39) and matches the established native-chrome invariant already asserted in SingleThreadTests.swift:149. The comment on :94 ("Stable token proven in SwipePromptTests.swift:52") overstates the precedent — see next — but the assertion itself should stay.

### Precedent assessment — SwipePromptTests.swift:44-53

The cited `dismissButtonHasAccessibilityLabel` does **not** justify these tests, and should itself be questioned:
- It is misnamed: it never asserts the accessibility label, and its own comment (:46-48) concedes "SwiftUI never serializes accessibility label *strings*… The label value itself is asserted by the Phase 4 UI test." So the unit test adds near-zero behavior coverage beyond what the UI test provides.
- `contains("Button<")` (:50) is vacuous — any button in the prompt matches.
- `BorderedProminentButtonStyle`/`AccessibilityAttachmentModifier` (:51-52) are the same SDK-token pins with the same drift exposure.

Critically, citing it as "proven stable" is a category error: one test using a token on today's SDK proves nothing about stability across SDK versions. The *strong* part of the cited file is lines 17-24 — the document-order/range-ordering check — which the new tests should have borrowed instead. So: precedent exists and matches a pervasive house pattern, but it is a weak precedent, and the new tests compound rather than improve on it.

### Gaps

**Fix-now (test policy)** — the diff is a styling/a11y change (label+combine, prominent button, full-width) with **zero** UI coverage and no stated reason for skipping one: `SingleThreadUITests` has no reschedule references at all. Per AGENTS.md, this is exactly the sanctioned case for a justified UI test — "a regression that only manifests at the UI layer (accessibility)" — and the repo has the `testAccessibilityAudit()` seam for it. The three new unit tests verify layout structure through serialization and cannot verify look-and-feel; the PR should either (a) tighten the unit tests as above and add a brief note on why no UI test is added, or (b) add one UI-level assertion (e.g., picker labelled once, combined a11y element) and drop the token pins.

**optional** — overlap: `dateOnlySheetStillRendersLabeledRow` (:67-82) and `rescheduleSheetPutsLabelBesidePicker` (:51-66) differ only in the due-time branch, which the static-helper tests (:15-48) already discriminate. The three structural tests could collapse to one tightened test plus the existing helper tests; as-is it's three tests asserting mostly the same description tokens.

**Good parts to preserve:** the pre-existing static-helper tests (:15-48) are the behavioral model for this file; naming follows Swift Testing conventions; the `makeReminder`/construction-only fixture style is correct; the `Range`-ordering idea is right even if misapplied here.

**Summary for the parent:** nothing blocks merge. Highest-value changes: (1) remove or make discriminating the :81 a11y assertion (the combine fix is currently untested), (2) replace the `HStack<` token with range-ordering to actually test "label beside picker", (3) state UI-test skip rationale or add one a11y-audit test, (4) keep :95/98 and the literal-copy checks, annotate `DatePicker<EmptyView` as an SDK-token duplicate-guard, and drop or re-scope `!contains("Spacer")`.
