## Q1: How a fresh `EntitlementStore()` derives `isEntitled` / `hasResolvedEntitlement` on macOS

### Findings
- Whole class is `@MainActor @Observable` (`SingleThreadCore/Sources/SingleThreadCore/EntitlementStore.swift:11-12`). Public `init()` (`.swift:18-23`) spawns one inherited-main-actor `Task` that runs, in fixed order: **`refreshEntitlement()` first** (`.swift:20` → `:102-113`), then **`observeTransactionUpdates()`** (`.swift:21` → `:93-99`).
- `refreshEntitlement()` iterates `Transaction.currentEntitlements` (`.swift:104`); a `.verified` transaction with `productID == Self.unlockProductID` (`app.alanvardy.SingleThread.unlimited`, `.swift:49-51`) sets `entitled = true; break` (`:105-109`); then `isEntitled = entitled` and `hasResolvedEntitlement = true` are written unconditionally (`:111-112`) — the resolved flag settles **true even on an empty account**.
- `observeTransactionUpdates()` is an infinite `for await` over `Transaction.updates` (`.swift:94`); each `.verified` tx is `transaction.finish()`ed (`:96`) then `refreshEntitlement()` re-runs (`:97`); `.unverified` skipped (`:95`). Loop ends only via `deinit` → `observationTask?.cancel()` (`.swift:43-45`, `nonisolated(unsafe)` property at `:60-62`).
- `sync()` (`.swift:72-80`) is the only other refresh trigger: `AppStore.sync()` awaited **before** an explicit `refreshEntitlement()` (`:74-75`); the `Transaction.updates` loop may fire first, then the post-sync refresh re-settles.
- `hasResolvedEntitlement` flips true at exactly two sites: end of `refreshEntitlement()` (`.swift:112`) and `init(testingWithEntitled:)` (`.swift:32`); `init(testingWithEntitlementUnresolved:)` (`:39-41`) leaves both false. Declared default `false` at `.swift:67`/`:58`.
- `EntitlementStore` has **no `SKTestSession`/`StoreKitTest` reference** — only `StoreKit` (`:3`) and the three APIs above. Whether reads hit a session-scoped store or the host store is decided at process level: tests **with** a live session (`EntitlementStoreTests.swift:43, :63, :77`) get session-scoped reads; tests **without** (`.swift:13-14, :19-20`) read the host StoreKit store synchronously and never await the async refresh.
- Comment at `EntitlementStoreTests.swift:47-49` is the only explicit `storekitd` mention: `SKTestSession.buyProduct` cannot complete via `xcodebuild test` on Xcode 26.6 — config "never reaches the simulator's storekitd container" (FB22237318).
- Production wiring: `SingleThreadApp.swift:49` → `AppViewModel()` (`AppViewModel.swift:17-20`) → `makeStore` → `ReminderStore(loadsReminders:)` (`AppViewModel.swift:259-261`); `ReminderStore.init` defaults `entitlementStore: EntitlementStore = EntitlementStore()` (`ReminderStore.swift:37`, stored `:58`). `SettingsView.swift:23` also defaults a fresh `EntitlementStore()`. Test/UI seams instead inject `testingWithEntitled:`/`testingWithEntitlementUnresolved:` (`AppViewModel.swift:248, :256, :296-302`).
- Consumers: `ReminderStore.canMutate` = `isEntitled || count < freemiumCap` (`ReminderStore.swift:176-179`); `hasResolvedEntitlement` mirrors the store (`:183-184`); `ContentView.swift:671-674` (`#if os(iOS)` only) renders `EmptyView()` until resolved. Watch never consults StoreKit — flag arrives via `EntitlementState.swift:1-25` / `SkippedReminderSyncService` (though `WatchAppViewModel.swift:245` and `SkippedReminderSyncService.swift:73` still construct a non-observing `EntitlementStore()`, per Q1 agent's host observation).

## Q2: `SKTestSession` vs. the macOS host's persistent StoreKit store

### Findings
- Test side: `import StoreKitTest` (`EntitlementStoreTests.swift:2`); `@MainActor @Suite(.serialized)` (`:7-8`). Three tests create sessions, each a local `let` scoped to the function (`:43, :63, :77`) with `disableDialogs = true` (`:44, :64, :78`). **Zero** `end()`/`defer`/`try-finally`/`clearTransactions()` call sites in committed code (grep hits only `.pi` docs). Sessions "die" by Swift scope exit (deallocation).
- `Transaction.currentEntitlements` / `Transaction.updates` / `AppStore.sync()` are not parameterized by session — StoreKit 2 resolves whatever is *current* for the process (`EntitlementStore.swift:74, :94, :104`). Prior audit: `isEntitled` is "never persisted or cached… always re-derived… at process start" (`.pi/qrspi/alanvardy-var-754-purchase-button-flashing/research.md:57-58`).
- In-repo host-behavior record (the load-bearing evidence):
  - `var-789/plan.md:297`: the two macOS tests fail with `!isEntitled` receiving `true` — "the host's StoreKitTest/storekitd leaks an entitled sandbox state into `Transaction.currentEntitlements`"; `[SKTestSession] Error saving configuration file: SKServiceErrorDomain Code=2`; "bouncing `storekitd` did not help"; **"An in-test `clearTransactions()` made the two tests pass in isolation, and the full suite re-creates the leak"** with no purchases/`AppStore.sync()` in the suite.
  - `var-789/implement.md:27`: same five-point evidence; suggested "reset host sandbox account".
  - `var-792/implement.md:53-57`: local StoreKit Test session "cannot isolate… entitlements read **real-store state**"; storekitd restart attempted; "a reboot / Xcode StoreKit component refresh may clear it locally".
  - `var-781/implement.md:30`: "this Mac's StoreKit **sandbox account** resolves `isEntitled=true`"; suggests resetting sandbox/purchase state.
  - `var-796/implement.md:46`: "`SKTestSession` doesn't reach storekitd in an unsigned local build" (macOS runs `CODE_SIGNING_ALLOWED=NO`).
- Store lifecycle across runs: leak re-appeared gate after gate locally (var-780 green → var-781/789/792/794/796 red) until something host-level (sandbox reset / reboot) clears it; CI `mac-tests` (fresh runners, still unsigned, `ci.yml:293-308`) is green, so session isolation succeeds there.
- `clearTransactions()` observation: clears the entitled transaction **at that moment only**; the full suite re-creates the leak — it does not survive subsequent session creation (`var-789/plan.md:297`, `implement.md:27`).
- **Unanswerable from repo**: internal mechanics of `clearTransactions()`, session teardown/deallocation semantics, whether deallocation revokes the isolated store, host store file paths, and session-scoped vs host-store behavior in a *working* isolating session.
- `.pi/skills/storekit/SKILL.md:1-20` documents only product-ID source of truth + scheme sync + real-device sandbox prerequisites; **no host store paths** anywhere in the repo.

## Q3: How the app persists entitlement-relevant state on macOS

### Findings
- Purchase/restore flow: `PurchaseSettingsView.purchase(_:)` — `await product.purchase()` (`SingleThread/PurchaseSettingsView.swift:154`); on `.success` awaits `entitlementStore.sync()` (`:157`); `Restore Purchases` button (`:40-43`) runs the same `sync()`. `EntitlementStore.sync()` = `try await AppStore.sync()` → `refreshEntitlement()` (`EntitlementStore.swift:72-82`).
- Persistent artifacts written on the host:
  1. **StoreKit transaction store (Apple-managed, via storekitd)** — the only entity that persists entitlement. All `product.purchase()`/`AppStore.sync()`/`Transaction.*` are SDK/OS-side (`EntitlementStore.swift:3`); nothing app-side writes it. Repo evidence it is host-persisted: `var-792/implement.md:48-55` ("real-store state", storekitd restart, reboot hint).
  2. **UserDefaults suites** — `AppGroup.defaults` = `UserDefaults(suiteName: "group.app.alanvardy.SingleThread") ?? .standard` (`AppGroup.swift:11-17`). **The entitlement flag is never written to either suite**: `isEntitled` is in-memory only (`EntitlementStore.swift:58`), re-derived every launch; confirmed by `var-754/research.md:56`. `"isEntitled"` appears in the seed reset list (`UITestingSeed.swift:85`) as defense-in-depth cleanup only (`var-759/research.md:49`) — production never writes it. Seeded entitlement injected via `testingWithEntitled:` (`AppViewModel.swift:296-301`), never stored.
  3. **Keychain** — zero `Keychain`/`keychain` matches in any Swift file repo-wide. No keychain artifact.
  4. **Sandbox container paths** — Apple-managed (Simulator/dev host); `EntitlementStoreTests.swift:47-49` says the config "never reaches the simulator's storekitd container" (FB22237318).
  5. **`Products.storekit` + scheme ref** — `SingleThread/Products.storekit` (product `app.alanvardy.SingleThread.unlimited`, USD 2.99) is a dev storefront *config*, wired via `SingleThread.xcodeproj/xcshareddata/xcschemes/SingleThread.xcscheme:90-92` (`StoreKitConfigurationFileReference → ../SingleThread/Products.storekit`). Not a runtime-writable artifact.
- Documented procedures in-repo: only prose hints — `SKILL.md:20` ("PaymentQueue / transaction logs"), `var-781/implement.md:30` ("`xcrun simctl` erase / StoreKit sandbox account reset per the `storekit` skill" — the referenced command is **not** in the skill), `var-792/implement.md:57` (reboot / Xcode StoreKit refresh). `var-789/plan.md:297-304` suggests "reset the host sandbox account", no concrete command. **No scripted inspect/remove procedure exists.** The in-test `clearTransactions()` experiment lives only in `.pi` docs, never in committed source.
- **Open area** (external, parent web-searched): Apple-documented host store paths and transaction-inspect/remove tooling — see Cross-Cutting.

## Q4: macOS unit-test stage — local vs CI, and available hooks

### Findings
- **Local** (`scripts/test.sh:286-292`): `MAC_SIM="platform=macOS"` (`test.sh:12`), `DERIVED_DATA="DerivedData"` repo-relative (`test.sh:10`); invocation `xcodebuild -scheme SingleThread -destination "$MAC_SIM" -configuration Debug -derivedDataPath "$DERIVED_DATA" CODE_SIGNING_ALLOWED=NO test -only-testing:SingleThreadTests`. No `-resultBundlePath`; runs **last** in the full pipeline after iOS build/unit/UI tests in the same shell. `make mac-test` (`Makefile:26-27`) is nearly identical but omits `-configuration Debug`; `make mac-build` (`Makefile:23-24`) adds `-configuration Debug` + `build`.
- **CI** (`mac-tests` job, `.github/workflows/ci.yml:270-320`): `runs-on: macos-26` (`:271`); `DERIVED_DATA: ${{ github.workspace }}/DerivedData` (`:273`); `setup-xcode@v1` → Xcode 26.6 (`:277-280`); `DEVELOPMENT_TEAM=` written to `$GITHUB_ENV` (`:282`) neutralizing the hardcoded team `6NWX2DHB9Q` (pbxproj:652,715,…). `actions/cache@v4` (`:284-292`) caches DerivedData keyed by OS+Xcode+ref+source-hash with restore-keys fallbacks — **build products survive between runs; StoreKit/storekitd state does not** (ephemeral runner home). Build step (`:293-302`, timeout 20) adds `-showBuildTimingSummary`; test step (`:304-313`) adds `-resultBundlePath TestResults-mac.xcresult`; failure → `upload-artifact@v4` (`:315-320`).
- **Environment deltas**: local host is long-lived — app sandbox container + storekitd transaction store survive across runs (the ticket's real entitled transaction from prior manual Mac testing persists → fresh real `EntitlementStore()` derives `isEntitled == true`). CI runners are ephemeral VMs with an empty StoreKit store; only DerivedData carries over.
- Scheme hooks (`SingleThread.xcscheme`): **TestAction** `:39-69` — `buildConfiguration="Debug"`, `shouldUseLaunchSchemeArgsEnv="YES"`, `shouldAutocreateTestPlan="YES"`, Testables = SingleThreadTests + SingleThreadUITests (`parallelizable="YES"`); **no PreActions/PostActions, no EnvironmentVariables, no StoreKitConfigurationFileReference**. **LaunchAction** `:70-93` holds the only StoreKit hook: `<StoreKitConfigurationFileReference identifier = "../SingleThread/Products.storekit">` (`:90-92`) — honored only on Run, never consumed by `xcodebuild test`.
- **No `*.xctestplan` files exist** in the repo (find = 0 matches) — no xctestplan pre-action mechanism; auto-created plan carries no hooks. No `EnvironmentVariables` in any scheme action.
- `Products.storekit` discovery: **zero pbxproj references** (no PBXFileReference) — the file is bundled via the app target's synchronized folder (`pbxproj:257-259`; folder root `:111-115`), so it lands in the app bundle resources. `SingleThreadTests` is a hosted test bundle: `TEST_HOST = $(BUILT_PRODUCTS_DIR)/SingleThread.app/...` (`pbxproj:860` Debug, `:889` Release), `BUNDLE_LOADER` (`pbxproj:838, :867`). `SKTestSession(configurationFileNamed:"Products")` resolves the bare name against the **host app bundle's resources** — that is the entire discovery mechanism.
- StoreKitTest compile wiring only relaxes warnings on the test target (`pbxproj:853-856` Debug, `:882-885` Release; iOS-18-deprecated-symbol comment). **No `com.apple.developer.in-app-purchases` entitlement exists repo-wide**; `SingleThread.entitlements` / `AppGroup.entitlements` carry only app-group/sandbox keys.

## Q5: Isolation story of `EntitlementStoreTests`

### Findings
- File `SingleThreadTests/EntitlementStoreTests.swift` (89 lines): `@testable import SingleThreadCore` (`:1`), `import StoreKitTest` (`:2`), `import Testing` (`:3`); suite `@MainActor` (`:7`) + `@Suite(.serialized)` (`:8`). The comment `:10` ("SKTestSession for driving StoreKit in test") describes intent, but no shared session exists — sessions are per-test locals.
- Per-test construction & await mechanics:
  1. `isEntitledIsFalseByDefault` (`:12-16`) — real `EntitlementStore()`, no session, no await, synchronous assert.
  2. `hasResolvedEntitlementIsFalseByDefault` (`:18-22`) — real `EntitlementStore()`, no session, no await.
  3. `seamSetsEntitlement` (`:24-32`) — seam only (`testingWithEntitled: true`/`false`), no session, no await.
  4. `unresolvedSeamLeavesFlagsFalse` (`:34-39`) — seam `testingWithEntitlementUnresolved: ()`, no session, no await.
  5. `isEntitledSurvivesStoreRecreation` (`:41-59`, async) — session (`:43`) + `disableDialogs` (`:44`); seam `first` (`:51`), fresh real `second` (`:54`); awaits via **fixed `Task.sleep(200ms)`** (`:57`); asserts `!second.isEntitled` (`:58`).
  6. `nonMatchingProductIDDoesNotSetEntitlement` (`:61-70`) — session (`:63`), real store (`:68`), no await.
  7. `initialRefreshSettlesResolvedFlag` (`:72-88`, async) — session (`:77`), real store (`:80`); awaits via **polling loop** `while !store.hasResolvedEntitlement, waited < 2_000_000_000` with 50 ms sleeps (`:82-85`).
- So: 4 tests never touch StoreKit; 3 drive real SKTestSession; only 2 await the async refresh (one fixed sleep, one poll).
- `@Suite(.serialized)` role: project convention is annotation-enforced isolation for suites touching real StoreKit/UserDefaults/shared EventKit/timers (`.pi/qrspi/alanvardy-var-755-slim-down-test-suite/research.md:105`; `var-796/conventions.md:37` — "one SKTestSession per process"). Here it also prevents suite-internal session/storekitd contention (3 sessions per process against the same host storekitd).
- **No setUp/tearDown hooks exist** in the Swift-Testing unit targets (`func setUp`/`tearDown` hits are only in XCTest UI targets `SingleThreadUITests/`, `SingleThreadWatchUITests/`). Sessions rely on scope-exit deallocation.
- `clearTransactions()` experiment records:
  - `var-789/plan.md:297`: in-test `clearTransactions()` made the two failing tests **pass in isolation**; "the full suite re-creates the leak"; no purchase/`AppStore.sync()` calls in the suite → host StoreKit sandbox state; `SKServiceErrorDomain Code=2` saving config; serial-mode run aborted outright; bouncing `storekitd` did not help.
  - `var-789/implement.md:27`: same five-point evidence; follow-ups "reset host sandbox account; keep macOS tests serial in CI".
  - Related side-effect record: `var-642/implement.md:35` — `syncDoesNotCrashOnEmptySession` was dropped because `AppStore.sync()` hangs in-process after earlier sessions wedge storekitd (passes in isolation, hangs 2/2 in-suite) — session side effects persist across tests within a suite.
  - Sibling isolation conventions: `EntitlementSyncTests.swift:1-12`, `UITestingSeedTests.swift:7-9` also use `@Suite(.serialized)`.
- Open questions (also `questions.md` q2): whether `clearTransactions()`/teardown/deallocation wipe the host persistent store or only the active session store; which store the reads consult with a session present on an entitled host; whether session disposal restores prior-purchase state. Only documented observed fact: in-isolation pass / full-suite re-leak.
- **Host StoreKit store paths** (observed on this machine, not in repo — Q1 agent's host check): per-user daemon `storekitd` at `/System/Library/Frameworks/StoreKit.framework/Support/storekitd`, DB at `~/Library/Application Support/App Store/StoreKit.db`.

## Q6: State-reset conventions for test setup

### Findings
- `UITestingSeed.resetPersistedState()` (`SingleThreadCore/Sources/SingleThreadCore/UITestingSeed.swift:62-69`) removes all 24 `persistedKeys` (`:73-98`) from **both** `AppGroup.defaults` (`:63-64`) and `UserDefaults.standard` (`:66-67`). Keys: `skippedReminderIdentifiers`, `skipCounts`, `excludedListTitles`, `showDate`, `showList`, `showRecurrence`, `showAlarms`, `showCompletionGlow`, `showUndatedReminders`, `sortOption`, `completionCount`, `isEntitled`, `enableActionButtons`, `showMicrophoneButton`, `showSwipePrompt`, `showUndoButton`, `backgroundEnabled`, `backgroundFadePercent`, `backgroundPinned`, `allowsLandscape`, `textSize`, `appearanceMode`, `notificationsEnabled`, `notificationIntervalHours`.
- Launch wiring: `AppViewModel.makeStore` `--seed` branch (`AppViewModel.swift:205-206`) → `seededStore` (`:274-330`) calls `UITestingSeed.resetPersistedState()` **first** (`:275`), then re-writes seeded state into `AppGroup.defaults` only: `completionCount` (`:287`), `skipCounts` (`:291`), `enableActionButtons` (`:295`); entitlement injected via the three seams (`:296-301`). Wipe runs in-process at every `--seed` launch; seeded writes never touch `.standard`.
- `--ui-testing` seam (iOS `#if os(iOS)` block, `:208-258`): `--reset-glow-preference` → `UserDefaults.standard.removeObject("showCompletionGlow")` (`:216-217`); `--reset-swipe-preference` → `UserDefaults.standard.removeObject("showSwipePrompt")` (`:219-220`) — `.standard` only, `resetPersistedState()` deliberately NOT called (`:223` sets `enableActionButtons`). UI tests that assert persistence relaunch with `--ui-testing` explicitly to avoid the seed wipe (`SingleThreadUITests/SingleThreadUITestsFlows.swift:161, :257, :315`).
- Watch seam: no `removeObject` at all; seeds AppGroup keys only (`WatchAppViewModel.swift:26, :67`).
- Unit-test convention: per-key `defer { …removeObject(forKey:) }` cleanup on `.standard` (or both stores where a key migrated) — `MicrophoneToggleTests.swift:77,94,…`, `ReminderStoreTests.swift:905,…`, `SortOptionTests.swift:49,58`, `AppGroupTests.swift:16`, `EnableActionButtonsMigrationTests.swift:18-19,…`, `SettingsViewTests.swift:356-364` (App Group set+remove); watch tests similar (`ShowCompletionGlowStateTests.swift:35,…`, `WatchSyncPipelineTests.swift:537,552`).
- **Keychain: none** (grep zero across app/tests). **StoreKit/storekitd: no reset mechanism exists anywhere** — `clearTransactions` matches nowhere in source; `EntitlementStoreTests` has no setUp/tearDown and its only isolation is per-test `SKTestSession` creation (`:43-44, :63-64, :77-78`) against whatever host sandbox state exists. `isEntitled` is transient (`EntitlementStore.swift:94, 101-106`), never persisted; the `isEntitled` key in `persistedKeys` is never populated by the app.
- **Bottom line**: every existing reset touches only the two defaults containers. No code touches StoreKit transaction state, storekitd, or keychain — those stores have no reset convention.

## Cross-Cutting Observations
- **Entitlement is a StoreKit-truth system**: `isEntitled` is always re-derived from `Transaction.currentEntitlements` at launch; there is deliberately no cached copy anywhere (UserDefaults, keychain, files) — the only persistent artifact is the OS-managed transaction store, which is why host state controls test outcomes.
- **The macOS-local failure is environmental and recurring**: documented identically in var-781, var-789, var-792, var-794, var-796 as "host StoreKit sandbox leaks entitled state into `Transaction.currentEntitlements`; CI green; clearTransactions() helps only in isolation". The suite has no mechanism to defend against it (no setUp/tearDown, sessions never cleared, no serial-order guarantee beyond `@Suite(.serialized)`).
- **Test-run isolation is annotation-based**, not hook-based: `@Suite(.serialized)` + per-test `SKTestSession` locals + per-key `defer` cleanup; no `setUp`/`tearDown` (Swift Testing), no xctestplan (none exist), no scheme TestAction hooks.
- **Scheme StoreKit config lives in LaunchAction only** (`xcscheme:90-92`); `xcodebuild test` never consumes it — tests depend on `SKTestSession(configurationFileNamed:)` resolving `Products` from the test-host app bundle (synchronized-folder resource, zero pbxproj refs).
- **macOS unsigned builds** (`CODE_SIGNING_ALLOWED=NO`, `test.sh:287`, `ci.yml:296,307`) correlate with the local session-isolation failure (`var-796/implement.md:46`).
