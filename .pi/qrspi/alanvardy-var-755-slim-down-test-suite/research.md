## Cross-Cutting Observations
- **Single-suite orientation**: all unit tests use Swift Testing with `#expect`/`try #require`; XCTest exists only in the two UI-test targets (and WatchUI).
- **Two state universes collide in tests**: App-Group-suite-backed persistence (`group.app.alanvardy.SingleThread` with `.standard` fallback) vs `.standard`-backed keys. The `--seed` reset clears both (`UITestingSeed.swift:48-55`) — which is precisely why 5 persistence UI tests must relaunch with `--ui-testing` instead.
- **Isolation is enforced by annotation, not by fixture design**: every suite touching a real UserDefaults key, real StoreKit session, real file I/O, shared `EKEventStore`, or a real timer is `@Suite(.serialized)`; pure-logic suites stay parallel.
- **Real-time waits are the unit wall-time driver even though tests are mostly pure logic**: the 200 ms `eventKitSettleDelay` plus `.serialized` sequencing of the two biggest store suites concentrate cost in ~90 tests.
- **Duplication is layered with narrow uniqueness**: preference tests prove key semantics; view tests prove body rendering; gate tests prove freemium interaction; sync tests prove watch transport — the same flag/flow is asserted 4-5 ways across `SingleThreadCore`, iOS unit, watch unit, and both UI targets, with setting toggles UI-tested only for a subset (glow, show-list, background, pin, swipe prompt, undo).
- **The local runner is a deliberately sequential monolith** (9 xcodebuild phases, shared DerivedData, no clean) while CI parallelizes the same work into 7 jobs with explicit anti-parallelism flags on the UI steps.
