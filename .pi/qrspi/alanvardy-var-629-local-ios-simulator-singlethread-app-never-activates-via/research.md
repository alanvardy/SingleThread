# Research Findings

## Q1: iOS app launch & activation lifecycle

### Findings
- Process entry point is `@main struct SingleThreadApp: App` — `SingleThread/SingleThreadApp.swift:11-12`. `init()` runs first: it reads the launch args, builds a `ReminderStore`, loads the sort option, and (iOS) activates `WCSession` + wires WatchConnectivity hooks — `SingleThreadApp.swift:15-56`.
- The iOS delegate is installed via the property wrapper `@UIApplicationDelegateAdaptor(AppDelegate.self) private var appDelegate` — `SingleThreadApp.swift:73-74`. The delegate type is `final class AppDelegate: NSObject, UIApplicationDelegate` — `AppDelegate.swift:10`. (macOS uses `@NSApplicationDelegateAdaptor(MacAppDelegate.self)` — `SingleThreadApp.swift:79-80`.)
- Scene presentation: `App.body` declares a single `WindowGroup { ContentView(store: store) }` — `SingleThreadApp.swift:59-62`. Scene-based lifecycle is enabled by generated build settings `GENERATE_INFOPLIST_FILE = YES` + `INFOPLIST_KEY_UIApplicationSceneManifest_Generation[sdk=iphonesimulator*] = YES` — `SingleThread.xcodeproj/project.pbxproj:603, 607-608` (Debug; Release :653, 657-658). There is no hand-written scene delegate in the iOS sources; the only physical Info.plist is `SingleThreadWidget/Info.plist`.
- Content presentation drives startup: `ContentView.body`'s `.task { store.showsUndatedReminders = …; await store.start() }` runs on view appearance — `SingleThread/ContentView.swift:64-67`. `store.start()` then kicks off EventKit authorization / reminder loading — `SingleThreadCore/Sources/SingleThreadCore/ReminderStore.swift:105-118`.
- **Which callbacks are actually implemented (iOS):** only `applicationDidBecomeActive(_:)` — `AppDelegate.swift:45-47`, and `application(_:supportedInterfaceOrientationsFor:)` — `AppDelegate.swift:49-57`. **Absent from the iOS sources** (grep-verified): `applicationDidFinishLaunchingWithOptions`, `applicationWillEnterForeground`, `applicationDidEnterBackground`, `applicationWillResignActive`, and all `UISceneDelegate` methods. The only `applicationDidFinishLaunching` in the repo is on the **macOS** `MacAppDelegate` — `AppDelegate.swift:77-79`.
  - Consequence: a UIKit-side callback *ordering* (e.g. `didFinishLaunchingWithOptions → applicationWillEnterForeground → applicationDidBecomeActive`) cannot be reconstructed from source — the code hooks only the become-active transition.
- Active/foreground vs merely running: the app never sets its own foreground/active state; it only reacts. Running is established by `@main` + `App.init`; the active transition is the one point the delegate observes (`applicationDidBecomeActive`). The only foreground-driven *work* is view-driven (`ContentView`'s `.task`).
- **Where `applyAppearance` is invoked:**
  - iOS activation: `applicationDidBecomeActive` → `Self.applyAppearance(AppearanceMode.load())` — `AppDelegate.swift:45-47`.
  - SwiftUI settings: `.onChange(of: appearanceMode)` → `AppDelegate.applyAppearance(newValue)` (iOS) / `MacAppDelegate.applyAppearance(newValue)` (macOS) — `ContentView.swift:75-79`.
  - macOS launch+activation: `applicationDidFinishLaunching` and `applicationDidBecomeActive` both call `applyLaunchAppearance()` — `AppDelegate.swift:82-89`.
- `applyAppearance` defaults its windows to `UIApplication.shared.connectedScenes` → `as? UIWindowScene` → `.windows`, then sets `window.overrideUserInterfaceStyle` — `AppDelegate.swift:15-22`. `AppearanceMode.windowOverrideStyle` maps `.system/.light/.dark → .unspecified/.light/.dark`, `AppearanceMode.swift:24-29`; `AppearanceMode.load()` reads `UserDefaults` key `"appearanceMode"` (fallback `.system`) — `AppearanceMode.swift:66-72`.

## Q2: EventKit / Reminders access at startup

### Findings
- Launch→access chain: `SingleThreadApp.init()` sets `loads = !ProcessInfo.processInfo.arguments.contains("--ui-testing")` and builds `ReminderStore(loadsReminders: loads)` — `SingleThreadApp.swift:16-17`. The view's `.task` calls `store.start()` — `ContentView.swift:64-67`.
- `ReminderStore.start()` (`ReminderStore.swift:105-118`): `guard loadsReminders else { return }` (:106); reads `authorizationStatus = eventStore.authorizationStatus(for: .reminder)` (:107-108); if `.fullAccess` → `await reload()` (:109-110), else `await requestAccess()` (:112).
- `requestAccess()` (`ReminderStore.swift:261-271`): a `do { try await eventStore.requestFullAccessToReminders() … } catch { … }` loop over the `EventKitStoring` protocol seam (declared `EventKitStoring.swift:14`, real impl `EKEventStore` — `EventKitStoring.swift:41`). `authorizationStatus` defaults to `.notDetermined` (`ReminderStore.swift:50, 108`).
- **Which prompt / when:** on a fresh install `authorizationStatus == .notDetermined`, so `requestFullAccessToReminders()` fires — the iOS 17+ EventKit "Reminders full access" API (`ReminderStore.swift:263`). First call triggers the **OS-owned Reminders privacy (TCC) prompt** ("Allow SingleThread to access your reminders?"), a SpringBoard/TCC dialog, not a SwiftUI view. Timing = first launch, from `.task` → `start()` → `requestAccess()`. Because the store is `@MainActor` (`ReminderStore.swift:8`) and the target sets `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, the awaited call suspends (doesn't block), so the SwiftUI `ProgressView` can still render/animate while the prompt is up.
- **If unresolved:** the code has no timeout/retry/fallback. `requestFullAccessToReminders()` is awaited (`:263`); until the OS resolves it, `start()`/`requestAccess()` stay suspended (`:112, :263`), `authorizationStatus` stays `.notDetermined`, and `ContentView`'s `authGatedContent` keeps rendering the `.notDetermined` branch — `ProgressView("Requesting access…")` — `ContentView.swift:221-224`. `reload()` is never reached, so `reminders` stays `[]` (`ReminderStore.swift:41`). The app stays interactive (await suspends, not blocks).
- **If the prompt cannot render:** calling `requestFullAccessToReminders()` requires the Info.plist key `NSRemindersFullAccessUsageDescription`; if absent when the OS presents the prompt, the documented behavior is that the OS terminates the app. In this repo, the **iOS app target** declares only the legacy `INFOPLIST_KEY_NSRemindersUsageDescription` (`project.pbxproj:605` Debug / `:655` Release) and **not** `NSRemindersFullAccessUsageDescription` (grep shows `NSReminders` at 605/655 (app), 794/822 (watch), 852/883 (widget) — only watch+widget declare the full-access key). So the app target is the one that both calls `requestFullAccessToReminders()` and lacks its required key.
- **`loadsReminders`:** a stored `public let` (`ReminderStore.swift:51`), set in production init (:21) and preview/test init (:31). It gates both `start()` (:106) and `reload()` (:206). In the view it switches `authGatedContent` vs `reminderList` (`ContentView.swift:44-46`).
- **`--ui-testing`:** the only real-app source of `loadsReminders`. `SingleThreadApp.swift:16` inverts its presence; set by UI tests at `SingleThreadUITests/SingleThreadUITests.swift:18`. Even the watch app mirrors this gate (`SingleThreadWatch/SingleThreadWatchApp.swift:11`). Effect: `loadsReminders == false`, `start()` no-ops, and **no Reminders TCC prompt fires**; the view shows the empty reminder list.
- **App Group identifier:** `AppGroup.suiteName = "group.app.alanvardy.SingleThread"` (`AppGroup.swift:8`), used only for `UserDefaults` via `AppGroup.defaults` with `.standard` fallback (`AppGroup.swift:13-14`). It is **orthogonal to the prompt** — it neither gates nor triggers it. It is registered in both `SingleThread/AppGroup.entitlements:7` (iOS device+simulator builds — `project.pbxproj:592-593/642-643`) and `SingleThread/SingleThread.entitlements:9` (macOS — `594/644`). The macOS entitlements file additionally carries `com.apple.security.personal-information.calendars` (`SingleThread.entitlements:13`), which the iOS AppGroup file does not — consistent with iOS Reminders access being TCC-gated, not sandbox-entitlement-gated.
- **`INFOPLIST_KEY_NSRemindersUsageDescription`:** declared for the iOS app target (`project.pbxproj:605/655`), supplying the legacy usage string. Since the code path uses the full-access API (`ReminderStore.swift:263`) whose key is absent on the app target, this is the crux of the "cannot render" case.

## Q3: iOS Simulator install/launch surface

### Findings
- **Direct `simctl` usage exists only in CI pre-boot steps.** `.github/workflows/ci.yml:41-43` (unit-tests) and :102-104 (ui-tests) do:
  `SIM_UDID=$(xcrun simctl list devices available | grep -F "<device> (" | head -1 | sed …)` → `xcrun simctl boot "$SIM_UDID" || true` → `xcrun simctl bootstatus "$SIM_UDID" -b`. This is the only live `simctl` use.
- `Makefile` (`:13,27,40,53,72,83`) and `scripts/test.sh` (`:91,111,119,127,136,151,160,173,182`) contain **zero** simctl calls — they pass `-destination "$SIM"` to `xcodebuild`; install+launch then run inside xcodebuild/XCTest.
- Configured devices/runtimes: local default `platform=iOS Simulator,name=iPhone 17` (`Makefile:1`, `scripts/test.sh:5`); CI matrix `["iPhone 17", "iPad (A16)"]` with `SIM=platform=iOS Simulator,name=${{ matrix.device }}` (`ci.yml:16-18, 77-79`); watch `generic/platform=watchOS Simulator` (`Makefile:2`, test.sh:6); macOS `platform=macOS` (`Makefile:3`, test.sh:7). Deployment target `IPHONEOS_DEPLOYMENT_TARGET = 26.5` on all iOS targets (`project.pbxproj:617,667,695,720,744,768,853,884`). Environment has iOS 26.2/26.4/26.5 runtimes; the task's `iPhone 17` UDID sits under iOS 26.5.
- **simctl subcommand surface:** `boot` (boot a device; CI `|| true` tolerates already-booted), `bootstatus` (`-b` boots if needed and blocks until boot finishes — the CI gate ci.yml:43/104), `launch <device> <bundle-id> [args…]` (launch by bundle id; env via `SIMCTL_CHILD_*`), `erase` (wipe device), `io <device> screenshot` (capture framebuffer; not a top-level subcommand). Not used by repo automation.
- **Foreground vs background:** `simctl launch` carries **no foreground/background flag** (verified from help). The launch request goes to the booted SpringBoard/FrontBoard (`FBSystemService`), which normally creates **and activates** the app's scene — that activation is what moves the app foreground and fires `applicationWillEnterForeground`/`applicationDidBecomeActive`. Two prerequisites gate it: (1) the device is fully booted with SpringBoard's render server ready — CI enforces via `bootstatus -b` (ci.yml:43/104); (2) the app exposes a UI scene SpringBoard can activate (SwiftUI `App`/`WindowGroup` backing a `UIApplicationSceneManifest`). A scene-less app would launch a process but never become frontmost.
- The observed symptom (process launched, `applicationDidFinishLaunching` fires, `applicationDidBecomeActive` never fires, screenshots still show SpringBoard) is the signature of a launch whose process started but whose **scene activation/foreground handoff never completed**.

## Q5. UI-test launch mechanics

### Findings
- Two launch paths, same core primitive (`XCUIApplication`), differing in launch config:
  - `SingleThreadUITestsLaunchTests.swift` — `override class var runsForEachTargetApplicationUIConfign = true` (:14-16); `app.launch()` with **no** `launchArguments` (:22-25); then logs an `XCTAttachment(screenshot: app.screenshot())` "Launch Screen" (:32-35). Runs the normal production launch.
  - `SingleThreadUITests.swift` — `app.launchArguments = ["--ui-testing"]` then `app.launch()` (:18-20), waits `app.staticTexts.firstMatch.waitForExistence(timeout: 2)` (:25-27), then `app.performAccessibilityAudit(for: […])` (:31-38). The flag is consumed at `SingleThreadApp.swift:16`.
- Target config: UI test target product type `com.apple.product-type.bundle.ui-testing` (`project.pbxproj:265`), producing `SingleThreadUITests.xctest` (:77). It depends on the app target (`PBXTargetDependency` :451-452). **`TEST_TARGET_NAME = SingleThread`** (Debug :757, Release :781) tells XCTest which app to launch/control, and it has **no** `TEST_HOST`/`BUNDLE_LOADER` (those belong to the unit-test target :690/708, 715/733) — UI tests are not injected; they drive the app remotely.
- **Entitlements:** the UI test target build config carries **no `CODE_SIGN_ENTITLEMENTS`** (Debug block :740-757, Release :764-781). The app-group entitlement lives only on the app target (see Q5).
- scheme wiring: `SingleThread.xcscheme` `TestAction` (Debug) lists `SingleThreadUITests.xctest` as a testable `parallelizable = "YES"` (:57-67); the app is in `BuildAction` with `buildForTesting = "YES"` (:10-19).
- **XCUIApplication / XCTest mechanics:** `XCUIApplication` is the client handle to the launched app. `app.launchArguments`/`app.launchEnvironment` are mutable and only take effect when set **before** `launch()` (that's why UITests.swift sets :19 then calls :20, while LaunchTests calls :25 with no args). `launch()` terminates any running instance and starts a fresh one, then blocks until the app reaches the running/idle state (making `staticTexts`/`screenshot()`/`performAccessibilityAudit()` valid).
- **What actually foregrounds:** the UI-test bundle runs in the xctest runner on the simulator; `XCUIApplication.launch()` does **not** run the app in-process. It sends a launch request through XCTest's automation bridge to **`testmanagerd`**, which instructs **SpringBoard** on the simulator to open/activate the app identified by `TEST_TARGET_NAME` (`SingleThread`). So **SpringBoard under `testmanagerd`/XCTest control performs the foregrounding**, not the test bundle and not the app. The app's `applicationDidBecomeActive` (`AppDelegate.swift:45-47`) runs *after* that foregrounding and only applies appearance.
- Test script/Makefile: `scripts/test.sh` default `SIM` = iPhone 17 (scripts/test.sh:5); `--ui-only` path builds `-only-testing:SingleThreadUITests` then runs `test-without-building -only-testing:SingleThreadUITests` (`test.sh:172-186`). CI `ui-tests` job pre-boots the simulator (`simctl boot`/`bootstatus`, ci.yml:102-104) then runs the same on both matrix devices.

Injected `INFOPLIST_KEY_*`: `NSMicrophoneUsageDescription` (:604), `NSRemindersUsageDescription` (:605), `NSSpeechRecognitionUsageDescription` (:606), and sdk-scoped `[sdk=iphoneos*/iphonesimulator*]` `UIApplicationSceneManifest_Generation` (:607/608), `UIApplicationSupportsIndirectInputEvents` (:609/610), `UILaunchScreen_Generation` (:611/612), `UIStatusBarStyle` (:613/614), plus iPad/iPhone orientation keys (:615/616).   - Widget: `GENERATE_INFOPLIST_FILE = YES` **and** `INFOPLIST_FILE = SingleThreadWidget/Info.plist` (:684/879) — merges physical plist + generated keys (incl. `NSRemindersFullAccessUsageDescription` :852/883).
  - Watch: `INFOPLIST_KEY_CFBundleDisplayName`, `NSRemindersFullAccessUsageDescription`, `WKCompanionAppBundleIdentifier`, `WKWatchOnly` (:793-796/821-824).
  - Test targets: `GENERATE_INFOPLIST_FILE = YES`, no `INFOPLIST_KEY` (:694/719/743/767).
- **ProductBundleIdentifier:** app `app.alanvardy.SingleThread` (:622/672); tests `app.alanvardy.SingleThreadTests` (:698/723); UI tests `app.alanvardy.SingleThreadUITests` (:747/771); watch `app.alanvardy.SingleThread.watchkitapp` (:798/826); widget `app.alanvardy.SingleThread.widget` (:859/890).
- **Scheme (SingleThread.xcscheme):** BuildAction builds app `buildForTesting = YES`/`buildForRunning = YES` (:10-11), watch `buildForTesting = YES`/`buildForRunning = NO` (:24-25). TestAction: `Debug` config, LLDB debugger+launcher (:40-42), testables = SingleThreadTests + SingleThreadUITests, both `skipped=NO`,`parallelizable=YES` (:46-67). LaunchAction: Debug, LLDB (:71-73), runnable = `SingleThread.app`, with **no** `CommandLineArguments`/`EnvironmentVariables` (:80-88). Analyze=Debug (:109), Profile/Archive=Release (:92,112).
- **Launch arguments / preprocessor:** the real app reads `ProcessInfo.processInfo.arguments.contains("--ui-testing")` (`SingleThreadApp.swift:16`; watch `SingleThreadWatchApp.swift:11`). The argument is supplied only by the UI test (`SingleThreadUITests.swift:18-20`), not by the scheme. `DEBUG=1` is defined **only** in the project-level Debug config via `GCC_PREPROCESSOR_DEFINITIONS = ("DEBUG=1","$(inherited)")` (:512-514) and `SWIFT_ACTIVE_COMPILATION_CONDITIONS = "DEBUG $(inherited)"` (:526). **No source currently uses `#if DEBUG`** — the app instead uses `#if os(iOS)` / `#if os(macOS)` / `#if os(iOS)||os(macOS)` conditionals. Debug-vs-Release project-level differences influencing the built binary: `DEBUG_INFORMATION_FORMAT` dwarf vs dwarf-with-dsym (:503/566), `ENABLE_IS = YES` vs absent (:506), `GCC_OPTIMIZATION_LEVEL 0`, `SWIFT_OPTIMIZATION_LEVEL -Onone` (:527), `SWIFT_COMPILATION_MODE` wholemodule in Release (:582).
- **iOS Simulator vs macOS target differences:** same app target builds `SUPPORTED_PLATFORMS = "iphoneos iphonesimulator macosx"` (:627/677). Differences: entitlements file (AppGroup vs SingleThread), `CODE_SIGN_IDENTITY[sdk=macosx*] = "Apple Development"` (:595/645), `LD_RUNPATH_SEARCH_PATHS` override for macOS (:619/669), sdk-scoped Info.plist keys (scene/launch-screen/status-bar only for iphoneos*/iphonesimulator*), `ENABLE_APP_SANDBOX`/`ENABLE_HARDENED_RUNTIME` Mac-only, watch embedding `platformFilter = ios` (:14,456; so macOS builds embed the widget, CI disables signing with `CODE_SIGNING_ALLOWED=NO`), and compile-time lifecycle adaptor (`@UIApplicationDelegateAdaptor` iOS vs `@NSApplicationDelegateAdaptor` macOS — `SingleThreadApp.swift:77-81`).

## Cross-Cutting Observations
- **Foregrounding is OS-driven, not app-driven.** Every path that lands the app in the foreground (simctl launch, XCTest `XCUIApplication.launch()`) does so by having SpringBoard activate the app's UI scene. The app's only active-lifecycle hook (`applicationDidBecomeActive`, `AppDelegate.swift:45-47`) runs *after* foregrounding and only applies appearance. So "app runs" (process up, `applicationDidFinishLaunching` may or may not fire) and "app is active/foreground" are decoupled — the app becomes active only when SpringBoard activates its scene.
- **Scene presence is a hard requirement.** Scene-based lifecycle comes from generated build settings (`INFOPLIST_KEY_UIApplicationSceneManifest_Generation[sdk=iphonesimulator*] = YES`), not a checked-in scene manifest. A scene-less/headless app would start a process but never become frontmost.
- **`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`** is set on the iOS app (and watch) targets, so the `@MainActor` `ReminderStore` awaits suspend rather than block — relevant to both the TCC prompt (UI stays animating) and the missing-foreground symptom (the process is up but the scene activation never happens).
- **No prompt, tests any place.** `--ui-testing` is a single runtime arg used by the UI-accessibility test to suppress EventKit — a direct link between the test launch config, the app's `loadsReminders`, and the TCC prompt firing.

## Open Areas
- **Exact UIKit→SwiftUI callback ordering** cannot be reconstructed from source because `applicationDidFinishLaunchingWithOptions`, `applicationWillEnterForeground`, and all `UISceneDelegate` callbacks are not implemented in the iOS sources (`AppDelegate.swift` implements only `applicationDidBecomeActive` + orientation). No runtime logging/instrumentation was present to observe actual ordering.
- **The `simctl launch` foreground semantics** (whether launch requests activation vs merely starting a process) are not pinned down by any repo automation — the repo never calls `simctl launch`; it does this only in test/simulator tests via manual steps / planning notes, and `launch` has no documented foreground/background flag. The "started but not frontmost" mechanism is inferred from SpringBoard/FrontBoard-tierring rather than a repo-documented flag.
- **`NSRemindersFullAccessUsageDescription` vs `NSRemindersUsageDescription` mismatch** is observed in config: the app target calls the full-access API but only injects the legacy key. The claim that a missing full-access usage key causes app termination is documented EventKit behavior, not something observed in a run.
