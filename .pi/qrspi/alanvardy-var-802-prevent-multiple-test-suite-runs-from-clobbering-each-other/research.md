# Research Findings

Scope note: branch `alanvardy-var-802-prevent-multiple-test-suite-runs-from-clobbering-each-other` at 7aa3d67 (question commit; no implementation commits yet). Repo root = git root. All references relative to repo root unless quoted.

## Q1: How is filesystem state shared between build and test invocations?

### Findings
- **`-derivedDataPath` is a fixed project-relative path everywhere locally**: `Makefile:9` (`DERIVED_DATA := DerivedData`), `scripts/test.sh:15`, `scripts/simverify.sh:9`, `scripts/run-devices.sh:27` (env-overridable). Scripts `cd` to git root first (`test.sh:38`, `simverify.sh:11`, `run-devices.sh:35`), so the relative path always resolves to `<git-root>/DerivedData`; Makefile targets resolve from the caller's CWD. `.gitignore:4` ignores it (plus `DerivedDataPhase3/` :5, `DerivedDataPhase4/` :46).
- **All 8 phases of the full local gate share the one `DerivedData` sequentially inside one bash process** (`set -euo pipefail`, `test.sh:3`): iOS build-for-testing `test.sh:211-215`, watch build `:219-223`, iOS unit `:231-237`, iOS UI `:241-245`, watch build-for-testing `:249-256`, watch UI `:272-275`, watch unit `:280-283`, macOS `:288-292`. Reduced modes: unit `:304-308`/`:311-315`, UI `:325-329`/`:333-337`.
- **Two invocations running concurrently on the same machine write the same `DerivedData`** — nothing makes it per-invocation. A second `make`/`test.sh` run simultaneously shares it. The only coordination is convention (see Q6).
- **Fixed product paths inside DerivedData are read across invocations**: watch runner Frameworks patch `test.sh:262-263`; `make mac-run` opens `$(DERIVED_DATA)/Build/Products/Debug/SingleThread.app` (`Makefile:31`); `run-devices.sh:32-33` defines `APP_PATH`/`MAC_APP_PATH` from it (install/launch `run-devices.sh:93-112, 131-137`).
- **Periphery index store**: written by xcodebuild into `DerivedData/Index.noindex/DataStore` (gitignored via `.gitignore:4`); read explicitly with `--index-store-path DerivedData/Index.noindex/DataStore` at `test.sh:227` (fixed, non-unique); elsewhere read via periphery's tool default — `Makefile:114-115` (`periphery scan --strict -- -destination "$(SIM)"`) and the CI lint job `ci.yml:366-368`, whose preceding watch build (`ci.yml:356-364`) omits `-derivedDataPath` altogether (tool default location).
- **`-resultBundlePath` values are fixed, distinct names** (local Makefile only + 2 CI spots; `test.sh`/`simverify.sh` never pass it):
  - `build/Coverage.xcresult` (`Makefile:10`, written `:40-46`, read `xcrun xccov view --report` `:46`), `build/Coverage.UI.xcresult` (`:11`, `:50-58`), `build/Coverage.All.xcresult` (`:12`, `:62-70`). Each target `rm -rf`s its own bundle before running (`Makefile:38, 51, 64`), so re-runs clobber their own bundle but the three names never collide with each other — though all share the same `DerivedData`.
  - CI `TestResults.xcresult` (`ci.yml:80`, workspace root) and `TestResults-mac.xcresult` (`ci.yml:313`), uploaded **only `if: failure()`** (`ci.yml:83`, `:317`), on fresh per-job runners.
- **Coverage is Makefile-only; CI has no coverage job** (no `-enableCodeCoverage` in ci.yml). All three targets use the `test` action (build+test combined) with `-enableCodeCoverage YES` (`Makefile:39-45, 52-58, 65-70`); raw `.profraw` files land under DerivedData (gitignored `.gitignore:15`) and are consumed only inside the xcresult bundle by `xccov view` — no `.profdata` merge/export anywhere.
- **User-global shared state**: XCTest simulator runtimes at `$HOME/Library/Developer/XCTestDevices` (`test.sh:20`) — read/written by every UI-test run, shared across all invocations/machines; pruned age-gated (see Q6). CI never prunes (workflow calls xcodebuild directly, not `test.sh`).
- **`build/` directory** (gitignored `.gitignore:11`): coverage bundles, `build/simverify-cold-launch.png` (`simverify.sh:38-39`), `build/SingleThread.xcarchive`/`.pkg` (`distribute-macos.sh:6, 9`).
- **CI DerivedData is per-runner**: `DERIVED_DATA: ${{ github.workspace }}/DerivedData` (`ci.yml:28, 96, 157, 216, 273, 372`). Jobs/matrix legs never share a filesystem; cross-run reuse only via `actions/cache` (see Q5).
- **Invocations with no `-derivedDataPath`** (tool default applies): `make clean` (`Makefile:104`), CI lint watch build (`ci.yml:356-364`), `distribute-macos.sh:5-9` (archive only).

## Q2: Which simulator devices and `simctl` state do test runs depend on, and what persists across runs?

### Findings
- **Local destination defaults**: `SIM="${SIM:-platform=iOS Simulator,name=iPhone 17}"` (`test.sh:5`, `Makefile:1`), `WATCH_SIM="generic/platform=watchOS Simulator"` (build-only, `test.sh:6`), `WATCH_TEST_SIM` default `platform=watchOS Simulator,name=Apple Watch Series 11 (46mm)` (`test.sh:11`, `Makefile:7`; comment: xcodebuild needs a concrete device for XCTests, name-only works only with one standalone watch, override `,id=…`), `MAC_SIM="platform=macOS"` (`test.sh:12`). `SIM` is env-overridable (`Makefile:13` exports it); `simverify.sh:8` mirrors.
- **Name-only destinations are ambiguous with multiple runtimes** (AGENTS.md:15-17: "a bare `name=` hangs"); pin `,OS=<ver>` or `,id=<UDID>`. Archive evidence: `.pi/qrspi/alanvardy-var-769-…/implement.md:16` replaced a nonexistent `OS=26.1` pin with a UDID.
- **UDID resolution → pre-boot**, local: `resolve_sim_udid()` greps `simctl list devices available` (`test.sh:22-30`, format `name (UDID)`); `SIM` is rewritten to `platform=iOS Simulator,id=$SIM_UDID` (`test.sh:44-48`, left unchanged if unresolvable `:47`); `preboot_sim()` runs `simctl boot` + `simctl bootstatus -b` (`test.sh:32-36`) when `SIM` contains `,id=` (`test.sh:49-51`). CI uses the identical pair per iOS matrix leg: `ci.yml:47-52, 115-120, 176-181, 235-240`. `simverify.sh:13-18` same gate ("CI-identical; do not skip `bootstatus -b`").
- **Watch sims are not pre-booted locally** — `test.sh` passes `WATCH_TEST_SIM` straight to xcodebuild (`test.sh:272, 280`); boot cost is paid inside XCTest. CI explicitly boots the watch (`ci.yml:403-406`).
- **CI creates a fresh *unpaired* watch with a deterministic name**: `xcrun simctl create "CI Watch S11" "…Apple-Watch-Series-11-46mm" "$RUNTIME"` (`ci.yml:391-401`; comment `:393-396`: GitHub's image ships a standalone watch AND paired watches, so a name-only destination is ambiguous). **No `simctl pair` call exists anywhere in ci.yml** (grep-verified) — CI's watch is deliberately unpaired.
- **Local watch UI tests depend on a manually paired, pre-existing watch**: `.pi/skills/simulator-pairing/SKILL.md:12-15` (`simctl shutdown all` → list devices → `simctl pair <watchUDID> <phoneUDID>` → re-run watch UI tests only) and AGENTS.md:19-22. Local and CI deliberately diverge on pairing.
- **No shutdown/erase/terminate in any automation** (grep over ci.yml, test.sh, simverify.sh, Makefile): only `simctl shutdown all` as manual remediation (SKILL.md:12, AGENTS.md:21) and `devicectl … --terminate-existing` for real hardware (`run-devices.sh:112`). `make clean` (`Makefile:104`) is never called inside a run. App relaunches are XCTest terminate-and-relaunch over an existing install, never erase-and-install.
- **XCTestDevices runtime pruning is local-only and age-gated**: `RUNTIMES_DIR="$HOME/Library/Developer/XCTestDevices"` (`test.sh:20`), `cleanup_xctest_runtimes()` (`test.sh:53-84`: skips non-dirs/symlinks, `stat -f '%m'` mtime gate, `rm -rf` older than `RUNTIME_AGE_HOURS`, default 1 h `test.sh:17-18`), invoked once before modes (`test.sh:104`). Comment `test.sh:50-53`: each UI run leaves a fresh ~3 GB runtime Xcode never prunes. Corroborated: var-645 research.md:152-153, var-755 research.md:97 (4 leftover runtimes).
- **No XCTestManager/XCTestDeviceManager references exist** anywhere in Swift sources or tests (grep: zero); the app/test code has no simulator-state pruning of its own.
- **Persists across local runs**: sim devices + UDIDs (nothing shuts down/erases), on-device App Group UserDefaults (see Q3), installed app + relaunched state, the manual watch pair association, and XCTestDevices runtimes until aged out. **CI**: a fresh `macos-26` VM per job discards all of it (created watch included; workflow has no delete step).

## Q3: How do the `--seed` and `--ui-testing` seams and unit-test code interact with persisted UserDefaults state?

### Findings
- **AppGroup.defaults vs UserDefaults.standard**: `AppGroup.swift:11` suiteName `"group.app.alanvardy.SingleThread"`; `AppGroup.swift:16-17` returns `UserDefaults(suiteName:) ?? .standard` — falls back to `.standard` on watchOS, unregistered simulators, and previews (doc comment `AppGroup.swift:12-15`). All Core stores default to `AppGroup.defaults` with a `defaults:` escape hatch: `ReminderSkip.swift:124`, `SkipCountStore.swift:26`, `ExcludedListStore.swift:7`, `PendingCompletionStore.swift:21`, `CompletionCounterStore.swift:20`, `SortOption.swift:25`, `BoolPreferenceStore.swift:15`.
- **`--seed '<json>'` (iOS only)**: parsed by `UITestingSeed.fromLaunchArguments` (`UITestingSeed.swift:48-56`); dispatched in `AppViewModel.makeStore` (`AppViewModel.swift:205-206`); `seededStore` (`AppViewModel.swift:274-338`) calls `UITestingSeed.resetPersistedState()` (`:284`), builds `InMemoryEventStore(reminders:, calendars:, defaultCalendar:)` (`:285-286`), then re-seeds App-Group keys.
- **The only blanket persisted-state reset in the tree**: `resetPersistedState` (`UITestingSeed.swift:62-68`) removes all 24 `persistedKeys` (`UITestingSeed.swift:73-96`) from **both** `AppGroup.defaults` and `UserDefaults.standard`. Called only from `AppViewModel.swift:284` (per `--seed` launch) and directly by `UITestingSeedTests` (e.g. `UITestingSeedTests.swift:141-186`). Neither iOS nor watch `--ui-testing` calls it.
- **After the wipe a seeded launch writes back**: `completionCount` unclamped (`AppViewModel.swift:287`), `skipCounts` (`:291`), `enableActionButtons = true` (`:295`); `excludedListTitles` via `store.setExcludedListTitles` → `excludeStore.save` (`ReminderStore.swift:499`). `loadsReminders: true` (unless empty+hasHidden) makes `reload()`/`reconcileSkipState` re-save `skippedReminderIdentifiers` + prune `skipCounts` into the App Group (`ReminderStore.swift:668-683, 595`).
- **`--ui-testing` (iOS) does no reset** (`AppViewModel.swift:214-258`): conditional `--reset-glow-preference` → `UserDefaults.standard.removeObject("showCompletionGlow")` (`:216-217`), `--reset-swipe-preference` → `.standard` `showSwipePrompt` (`:219-220`), and force-`AppGroup.defaults.set(true, "enableActionButtons")` (`:222`). `loadsReminders: false` (`:244-257`) means `start()`/`reload()` never run, so no skip/count writes occur on that launch. The seam's own comment (`AppViewModel.swift:213-215`) acknowledges the persistent App Group suite value on the test simulator.
- **`--ui-testing` (watch)** (`WatchAppViewModel.swift:106-164` scratch EKEventStore + one "Buy groceries" reminder): writes per launch — `--ui-testing-gated` → `completionCount` (`:27`), `--ui-testing-skip-count` → `skipCounts` (`:133`), glow flags → `.standard:showCompletionGlow` via `ShowCompletionGlowState.swift:23-25` (`:50-53`), `--ui-testing-action-menu` → `AppGroup.defaults:enableActionButtons` (`:67`) **re-forced to `false` on every other launch** because the value "persists in the App Group across relaunches" (`WatchAppViewModel.swift:61-66`).
- **InMemoryEventStore**: `:23-44` init, `:49-51` fullAccess, `:57-59` requestFullAccess, predicate NSPredicate(true) `:63-65`, fetch filters `!isCompleted` `:69-70`; `save`/`remove`/`makeReminder` exist only under `#if !os(watchOS)` (`:97-126`); `makeReminder` backs reminders with a process-wide scratch `EKEventStore` (`sharedStore`, `:126-133`) — the watch side builds its reminder from its own scratch store (`WatchAppViewModel.swift:108-113`).
- **Key → tier map** (per Q3 agent trace, keyed to store sites):
  - App Group (`AppGroup.defaults`): `skippedReminderIdentifiers` (`ReminderSkip.swift:132-135`; writes `ReminderStore.swift:604, 619, 680`), `skipCounts` (`SkipCountStore.swift:34`; `ReminderStore.swift:576, 585, 595`), `excludedListTitles` (`ExcludedListStore.swift:15`; `ReminderStore.swift:499`), `completionCount` (`CompletionCounterStore.swift:29`; `ReminderStore.swift:246, 278`), `enableActionButtons` (`ShowEnableActionButtonsState.swift:15,24`), `showDate/showList/showRecurrence/showAlarms/showCompletionGlow/showUndatedReminders` (`BoolPreferenceStore.swift:15`), `sortOption` (`SortOption.swift:18,25`), `pendingCompletionIdentifiers` (`PendingCompletionStore.swift:34`; lands in `.standard` on a real watch, `PendingCompletionStore.swift:8-14`).
  - `UserDefaults.standard`: `showMicrophoneButton` (`AppViewModel.swift:110`), notifications pair (`NotificationPreference.swift:19-22`; denial flip `NotificationScheduler.swift:67`), `appearanceMode`/`textSize`/`allowsLandscape`/background trio/`showSwipePrompt`/`showUndoButton` (`ContentView.swift:72-105`), and all watch `Show*State.apply()` → `.standard` (`ShowDateState.swift:22-31`, `ShowListState.swift:22-31`, `ShowRecurrenceState.swift:22-31`, `ShowAlarmsState.swift:22-31`, `ShowCompletionGlowState.swift:20-30`) plus the watch sync service's injected `.standard` stores (`WatchAppViewModel.swift` makeSyncService).
  - `isEntitled` is listed in `persistedKeys` (`UITestingSeed.swift:85`) but no code writes it to UserDefaults — it is transient in `EntitlementStore` / wire payload only.
- **Unit-test hygiene**: iOS tests inject `defaults: .standard` + UUID keys and `defer { UserDefaults.standard.removeObject(...) }` (`ReminderStoreTests.swift:905, 924, 943, 963, 984`; `ReminderStoreGateTests.swift:88, 109, 158, 165-166`; `BoolPreferenceStoreTests.swift:14-44`; `SortOptionTests.swift:49-58`). App-Group-touching tests clean both tiers (`AppGroupTests.swift:16-17`; `SettingsViewTests.swift:356-364`; `EnableActionButtonsSyncTests.swift:23-47`); `AppearanceModeTests.swift:83-87` uses throwaway `UserDefaults(suiteName: "AppearanceModeTests-\(UUID)")`. Watch tests likewise: `.standard` UUID + defer (`ReminderStoreWatchTests.swift:33-146`), dual-tier cleanup (`ShowEnableActionButtonsStateTests.swift:17-68`).
- **Intentional cross-launch retention (built on, not a bug)**: `testBackgroundAndPinTogglesPersistAcrossRelaunch` launches 1×`--seed` then 2-3×`--ui-testing` to assert `.standard` toggles survived (`SingleThreadUITestsFlows.swift:132-198`); `assertTogglePersists` relaunches with `["--ui-testing"]` (`SingleThreadUITestCase.swift:47-61`); watch glow comment `WatchAppViewModel.swift:45-49` ("both tests relaunch the same app install, so UserDefaults carries across"). **Implicit retention**: iOS `enableActionButtons=true` accumulates across `--ui-testing`-only sessions; any `.standard` toggle flipped during `--ui-testing` survives until a `--seed` launch; watch `completionCount`/`skipCounts`/`enableActionButtons`/`showCompletionGlow` persist across relaunches (`WatchAppViewModel.swift:27, 51-53, 67, 133`).

## Q4: How is parallelism structured within a single test run?

### Findings
- **Scheme-level**: `SingleThread.xcscheme:6` `<BuildAction parallelizeBuildables="YES">`; `<TestableReference parallelizable="YES">` for SingleThreadTests (`:48`) and SingleThreadUITests (`:59`). `SingleThreadWatch.xcscheme:6, :34, :45` (watch UI + watch unit). `project.pbxproj:415` `BuildIndependentTargetsInParallel = 1`. No test-setting `flag/value` blocks in either scheme.
- **Local full gate = 8 strictly sequential xcodebuild invocations** (`set -euo pipefail`, `test.sh:3`). Parallelism flags by phase:
  - iOS unit `test-without-building` (`test.sh:231-237`): **`-parallel-testing-enabled YES`** + `-maximum-test-execution-time-allowance 900` — the only parallel-enabled phase locally.
  - iOS UI `test-without-building` (`:241-245`): no flags.
  - Watch build-for-testing (`:249-256`): **two `-only-testing:` filters in one invocation** and no flags.
  - Watch UI (`:271-275`) / watch unit (`:279-283`): no flags.
  - macOS (`:287-292`): `test` action (build+test in one invocation) `-only-testing:SingleThreadTests`, no flags.
  - `--unit-only` (`:304-315`) and `--ui-only` (`:325-337`) modes: `test-without-building`, no parallel flags.
- **CI is the opposite policy**: `-parallel-testing-enabled NO` + `-maximum-concurrent-test-simulator-destinations 1` on every iOS test step (`ci.yml:76-77, 145-146, 204-205, 265-266`). Comments cite GitHub virtualized-macOS clone timeouts: unit job `ci.yml:68-71` ("EventKit/EKReminder test teardowns crash with SIGTRAP under clone contention"), UI jobs `:134-138` and `:254-258` (`com.apple.instruments.deviceservice.lockdown` 120 s connection timeout). Watch UI tests (`ci.yml:426-429`) and watch unit (`:433-438`) carry no parallel flags. `-retry-tests-on-failure` is CI-only (`ci.yml:144, 203, 264, 427`).
- **`-maximum-concurrent-test-simulator-destinations` never appears locally**; only CI. Repo-wide grep confirms no `-parallelize-testing`, `-jobcount`, `-serialize`, or `-parallel-testing-workers` anywhere in current scripts.
- **`build-for-testing` → `test-without-building` pattern** everywhere except macOS: iOS `test.sh:236/244`, watch `:274/:282`, reduced modes `:314/:336`; CI `ci.yml:78, 147, 206, 267, 428, 437`. macOS uses combined `test` (`test.sh:288-292`, `Makefile:27`, `ci.yml:305-313`).
- **Process-scoped shared objects**: the seam's `InMemoryEventStore.sharedStore = EKEventStore()` is file-scope/process-wide (`InMemoryEventStore.swift:126`, aliased `:101`; comment `:122-127`: one store so the host never exceeds EventKit's per-process connection cap `EKCADErrorDomain Code=1021`). Per-suite-file `@MainActor private let sharedTestEventStore = EKEventStore()` fixtures ("Construction only — never saved") at `ReminderStoreTests.swift:1094`, `EventKitStoringTests.swift:536`, `ReminderStoreGateTests.swift:177`, `ListContentTests.swift:5`, `ReminderDisplayTests.swift:6`, `PendingCompletionLogicTests.swift:5`; watch: `ReminderStoreWatchTests.swift:10`, `WatchReminderViewRegressionTests.swift:15`, `ShowCompletionGlowStateTests.swift:11`. **No ReminderStore singleton** — one per view (`ContentView.swift:34, 53`; `WatchAppViewModel.swift:18, 151, 160`).
- **`@Suite(.serialized)`** decorates nearly every suite (iOS: `ReminderStoreTests.swift:15, 511, 720, 898`; `EventKitStoringTests.swift:148, 355, 502`; `ReminderStoreGateTests.swift:11`; `UITestingSeedTests.swift:9`; watch: `ShowCompletionGlowStateTests.swift:27`, `ShowEnableActionButtonsStateTests.swift:12`, `ReminderStoreWatchTests.swift:26`, `WatchSyncPipelineTests.swift:526`) — serialized against the shared file-scope stores/real UserDefaults keys.
- **Suite relationship in a run**: 7 targets in one project (`project.pbxproj:435-448`) across **two schemes** — `SingleThread` (iOS app, iOS unit, iOS UI, macOS-capable) and `SingleThreadWatch`. Each platform's suite runs in its **own xcodebuild process** with a single `-destination` + `-only-testing:` filters (`test.sh:212, 220, 232, 242, 250, 272, 280, 288`). iOS and macOS run the *same* `SingleThreadTests` bundle / `SingleThread` scheme, differing only by destination (`platform=macOS`) and combined `test` action. The two watch bundles are the only pair sharing a build invocation (one build-for-testing, two `-only-testing:` flags) before being executed in two separate test invocations.

## Q5: How does the GitHub Actions pipeline isolate or share state across jobs and runs?

### Findings
- **Concurrency group is workflow-level, per-ref**: `concurrency: group: ci-${{ github.ref }}, cancel-in-progress: true` (`ci.yml:8-10`) — serializes runs on the same ref (newer run cancels the older); different refs run independently. Not scoped per job/matrix leg/device.
- **Matrix**: four iOS jobs (`unit-tests` `ci.yml:21-87`, `ui-tests-flows` `:89-149`, `ui-tests-launch-appearance` `:150-208`, `ui-tests-audits` `:209-269`) each with `device: ["iPhone 17", "iPad (A16)"]` (`:24-25, 92-93, 153-154, 212-213`) → 8 iOS legs. iOS UI classes are split disjointly via `UI_GROUP_A/B/C_ONLY_TESTING` env (`ci.yml:16-18`; group A has two flags, group C has two). `mac-tests` (`:270-321`) and `watch-ui-tests` (`:369-438`) have no matrix. All jobs on `runs-on: macos-26`.
- **DerivedData cache key is identical across all four iOS jobs and both device legs** (`ci.yml:43, 111, 172, 231` byte-identical): `derived-data-${{ runner.os }}-${{ steps.xcode.outputs.version }}-${{ github.ref_name }}-${{ hashFiles('SingleThread/**', '...', 'SingleThread.xcodeproj/project.pbxproj') }}` (hash over 7 source dirs + pbxproj). **Not device-scoped** — `matrix.device`/SIM never appears in key or restore-keys (`:44-45` prefix fallbacks). mac prefix `derived-data-mac-` with its own hashFiles (`:288-290`); watch prefix `watch-ui-derived-data-` (`:387-388`, single restore-key, no ref-less fallback). mise tool cache `:335-340`. Cache `path` is `${{ github.workspace }}/DerivedData` for all (`:42, 110, 171, 230, 287, 386`).
- **Fixed artifact/xcresult names, not device-qualified**: both `unit-tests` legs use `-resultBundlePath TestResults.xcresult` (`ci.yml:80`) and upload `name: unit-test-results` (`:86-87`) `if: failure()` (`:83`); mac-tests uses `TestResults-mac.xcresult` / `mac-unit-test-results` (`:313, 319-320`), also failure-only. `if-no-files-found` never set; **no `download-artifact` anywhere** — artifacts are never consumed by later jobs. The three iOS UI jobs and watch job pass no `-resultBundlePath` and upload nothing.
- **Per-job VM freshness assumption**: every job runs on a fresh GitHub-hosted `macos-26` VM; job-local FS (DerivedData, xcresults, created simulators) evaporates at job end. Cross-job/cross-run state flows **only** through (a) the shared actions/cache DerivedData entries, (b) failure-only artifacts, (c) the git-ref concurrency group. Because the iOS key is shared, whichever leg first writes the cache determines the entry the others restore; actions/cache skips a save when the exact key exists.
- **Simulator state is re-created per job**: iOS legs resolve+boot by name (`ci.yml:48-52` etc.); watch job creates a brand-new unpaired watch every run (`ci.yml:391-401`).

## Q6: What coordination mechanisms exist around test runs today, and what documented incidents show runs interfering with each other?

### Findings
- **No lock files, flock, semaphore, or serialization machinery exists** (repo-wide grep: zero matches in scripts/Makefile/ci.yml). `.pi/qrspi/implement.lock` is a tracked 0-byte placeholder added by commit `6215941`; nothing acquires or references it.
- **Coordination is by convention**: AGENTS.md:19-22 "**One xcodebuild test process at a time** (simulator contention). On `Busy`/`RequestDenied` runner-launch failures: shutdown sims (`xcrun simctl shutdown all`) and kill orphaned `xcodebuild`/`xctest` processes. Watch UI tests need a paired sim (`xcrun simctl pair …`)." AGENTS.md:153-156 gate staging: full `./scripts/test.sh` runs ONCE by the parent after phases commit. The convention recurs in every branch `conventions.md` (var-769/771/773/780/783/788/790/792/794/796).
- **Age-gated cleanup (local only)**: `RUNTIME_AGE_HOURS=1` default (`test.sh:17-18`), `cleanup_xctest_runtimes` (`test.sh:53-84`), invoked before modes (`test.sh:104`). In-script comments (`test.sh:15-18, 50-53, 100-103`) state the age gate exists precisely so an in-flight parallel test run is never disturbed ("APFS keeps open handles alive anyway"). Weekly build-artifact pruning (`make prune`) exists only on chore branch `chore/disk-hygiene-build-artifact-prune` (commit `ae67407`), **not on this branch**.
- **Retry/logic controls**: CI `-retry-tests-on-failure` (commits `ab0d5bc`/`4b6cc95` "retry failed UI tests once"); `-maximum-test-execution-time-allowance 900` (`test.sh:235`, `ci.yml:75, 143, 202, 263, 426`; genesis `04b63cb`); CI parallel-clone disable (`da236fa`, `3743384`). No buffering (no tee/fifo/spooling) anywhere.
- **Documented interference incidents** (all in `.pi/qrspi/<ticket>/` archives or commit history):
  - **OOM kill from concurrent xcodebuild (local)**: var-783 `implement.md:33-37` and `:76-82` — full gate "twice OOM-killed at its UI stage by a concurrent `xcodebuild` from another agent session on this 24 GB machine" (`Killed: 9`); legs passed uncontended; ~11 GB reclaimed from leftover simulator runtimes. plan.md:334-336 repeats.
  - **CI `Busy`/`NSMachErrorDomain` on parallel clones**: commit `da236fa` — removing `-parallel-testing-enabled YES`; runner launch failed with `Busy (Application failed preflight checks)` → `NSMachErrorDomain Code=-308 "(ipc/mig) server died"` (corroborated var-645 research.md:86-90).
  - **CI lockdown connection timeout**: commit `3743384` — "iOSSimulator unable to connect to com.apple.instruments.deviceservice.lockdown — timed out after 120 seconds" on virtualized runners with destination clones (var-645 research.md:82-85).
  - **Local full-gate `Busy`/`RequestDenied` runner-launch flake**: var-755 `phase6-evidence.md:28-39` — three consecutive full-mode `test.sh` runs each failed only at UI runner launch (`SBMainWorkspace … Busy ("Application failed preflight checks")` / `RequestDenied`), unit phase passed (427 tests) each time; `--ui-only` passed 42/42. ## Cross-Cutting Observations
- **The interference surface is the single fixed local `DerivedData` + SHARED base simulators + on-device persisted UserDefaults** — three classes of state: build products (only one convention protects them), simulator devices/runtimes (age-gated prune + manual shutdown only), and app-visible persisted keys (only `--seed` resets them; `--ui-testing` retains intentionally).
- **Local and CI deliberately diverge** on almost every axis: parallelism (local iOS unit YES vs CI NO/1 everywhere), watch pairing (paired manual local vs fresh unpaired CI), runtime pruning (local test.sh only; CI fresh VM), DerivedData (shared fixed local vs per-runner + cache), reset semantics (identical in code, but CI discards the sim so on-device leaks don't cross jobs).
- **CI's isolation is crude but effective**: fresh VM per job + git-ref concurrency group mean CI interference is limited to cache races and the shared `TestResults.xcresult` artifact *name*, while local machines carry the whole surface with no enforcement.
- **iOS, watchOS, and macOS suites are always separate xcodebuild processes**; the only intra-process parallelism ever enabled is the local iOS-unit phase. The shared `EKEventStore` (process-wide, file-scope) and `@Suite(.serialized)` are the intra-process coordination mechanisms.
- **Every documented incident is environmental (contention/flakes), never a logic bug**: OOM (var-783), Busy/RequestDenied/NotFound (var-755, 792, 780), SIGTRAP + lockdown timeouts (da236fa, 3743384), degraded watch (var-755). The fixes all landed in CI config, not test code.
