# Research Findings

Scope: how the background photograph changes over time, how that behavior is driven/surfaced from Settings, and how background state is persisted and tested. All `file:line` references verified against the working tree.

## Q1: Paths that replace the displayed photo

### Findings
- Core type: `@MainActor @Observable final class BackgroundImageStore` (`SingleThread/BackgroundImageStore.swift:53-55`); observable state all `private(set)`: `imageData` (:69), `photographer` (:71), `photographerURL` (:73), `isRefreshing` (:76). Only two mutators: `fetchAndPersist(from:)` and `loadStoredImage()`.
- **Two production entry points**:
  - `refreshIfNeeded(maxAge:)` (:91-99) — default `maxAge = defaultMaxAge` = 86400s/24h (:122). Always calls `loadStoredImage()` first (:92), then `guard !isFresh(maxAge:) else { return }` (:93), then `fetchAndPersist(from: Self.endpoint)` (:95). Never touches `isRefreshing`.
  - `forceRefresh()` (:107-116) — re-entrancy guard `guard !isRefreshing` (:108); `isRefreshing = true` (:109) with `defer { isRefreshing = false }` (:110); always fetches `Self.randomEndpoint` (:112). Never consults `isFresh`/`loadStoredImage`; always hits network (proven by `forceRefreshBypassesFreshSidecar`, `SingleThreadTests/BackgroundImageStoreTests.swift:179-194`).
- `init(client:directory:)` (:61-64) is inert — no disk read, no fetch.
- **Decision state**:
  - `isFresh(maxAge:)` (:178-183) reads sidecar `background.json`, decodes `BackgroundMetadata` with ISO8601 (`fetchedAt` :33, decode :185-189), returns `Date().timeIntervalSince(metadata.fetchedAt) < maxAge`. Missing/unreadable sidecar ⇒ `false` ⇒ fetch runs.
  - `loadStoredImage()` (:162-176) requires both a decodable sidecar and image bytes; missing/corrupt either ⇒ state cleared to `nil` (:168-170). The on-disk `.jpg` is **never deleted**.
- **Production call sites (exactly two)**:
  - `ContentViewModel.swift:83` — `await backgroundImage.refreshIfNeeded()` inside `task(showUndatedReminders:)`, triggered once by `ContentView.swift:88-90` `.task` (lifecycle task, auto-cancelled; doc `BackgroundImageStore.swift:87-90`: rendering never gated on the result).
  - `BackgroundSettingsView.swift:26` — refresh Button (`Task { await backgroundImage.forceRefresh() }`).
  - No timers, no `scenePhase`/`onAppear`/`.refreshable` wiring to the store (the list's `.refreshable` at `ContentView.swift:314/328/398` only calls `viewModel.reload()` of the ReminderStore).
  - Single production instance created at `AppViewModel.swift:79` (stored :92, injected into `ContentViewModel` :103), threaded `ContentView → SettingsView(:76-80) → BackgroundSettingsView`. Other constructions are previews/tests (`ContentView.swift:18/34`, `BackgroundSettingsView.swift:62`, `SettingsView.swift:142/164`).
- **Failure semantics — prior photo survives**:
  - `refreshIfNeeded` catch logs (:96-98). Photo survives in memory **iff the sidecar was valid at entry** (:92 reloaded it); missing/corrupt sidecar ⇒ memory stays `nil`, orphaned `.jpg` remains on disk. Tests: `failedFetchRetainsPriorImage` (:47), `corruptOrMissingSidecarTreatedAsNoImage` (:103-135), `photographerClearedWithoutValidSidecar` (:160).
  - `forceRefresh` catch logs (:113-115); photo/attribution **always survive**, `isRefreshing` reset by `defer`. Test: `forceRefreshRetainsPriorImageOnFailure` (:197-214).
  - Disk written before state flips (`fetchAndPersist` :155), so failures never leave disk half-written.
- **Concurrency**: `@MainActor` class; `isDecodableImage` `nonisolated` (:191). `isRefreshing` guards concurrent `forceRefresh`; **no mutual exclusion between `refreshIfNeeded` and `forceRefresh`**. `.task` cancellation lands as `CancellationError` in the catch, leaving state as-is.

## Q2: Network/disk abstraction and fetch/persist mechanics

### Findings
- **Protocol**: `protocol BackgroundImageFetching: AnyObject` — single `func fetchData(from url: URL) async throws -> Data` (`SingleThread/BackgroundImageStore.swift:14-16`). Doc (:10-13): named `fetchData` (not `data`) so the URLSession conformance can wrap the built-in async `data(from:)`, which does NOT throw on non-2xx.
- **URLSession conformance** (:18-27): `try await data(from: url)`, validates `HTTPURLResponse` status in `200..<300`, else throws `URLError(.badServerResponse)` (:24). Default client `URLSession.shared` via default `init` parameter (:61).
- **Two endpoints** (private static, hardcoded, no width/height params):
  - `endpoint = https://vardy.cc/unsplash` (:125) — "6h-cached wallpaper used on cold launch" (:124); only `refreshIfNeeded` (:95). "6h" is server-side; the *client* freshness window is 24h (:122).
  - `randomEndpoint = https://vardy.cc/unsplash/random` (:128) — served by the explicit "Refresh wallpaper" action (:126-127); only `forceRefresh` (:112).
  - Response shape `UnsplashPayload` (:39-48): keys `url`, `photographer`, `photographer_url` (CodingKeys :41-44); `created_at` ignored (:38). Tests stub image URL `https://images.unsplash.com/photo-1.jpg` (`BackgroundImageStoreTests.swift:326`, `SettingsViewTests.swift:179`).
- **`fetchAndPersist(from:)` order** (:145-158):
  1. Fetch endpoint JSON — `client.fetchData(from: endpoint)` (:146).
  2. Decode `UnsplashPayload` (:147-148).
  3. Fetch photo bytes — `client.fetchData(from: payload.url)` (:149).
  4. Validate as image — `guard isDecodableImage(data) else { throw URLError(.cannotDecodeContentData) }` (:150); `isDecodableImage` `private nonisolated` (:191), `UIImage(data:)` iOS / `NSImage(data:)` macOS (:192-197).
  5. Build `BackgroundMetadata(photographer:photographerURL:fetchedAt: Date())` (:151-154; struct :32-35).
  6. **Atomic persist before state flip** — `try persist(imageData:metadata:)` (:155); `persist` (:200-206) creates directory with intermediates (:201), writes `background.jpg` `.atomic` (:203), encodes metadata `JSONEncoder` `.iso8601` (:204-205), writes `background.json` `.atomic` (:206).
  7. Flip observable state — `imageData`/`photographer`/`photographerURL` (:156-158).
  - Doc (:87-90): "persist to disk FIRST, then flip observable state; on any error, log and keep prior state."
- **Sidecar storage**: separate file from the photo bytes, both written by one `persist` — photo `background.jpg` (`imageURL` :78-80), sidecar `background.json` (`metadataURL` :82-84). Comment (:30-31): "One write covers both the displayed photo and the attribution credit, so they can never disagree." Default dir `<Application Support>/SingleThread` (:132-136); tests inject a UUID temp dir (`BackgroundImageStoreTests.swift:333-335`). Class doc (:50-52): "Phone-local cosmetic concern: never touches the App Group or sync payloads." `fetchedAt` is a sidecar struct field, **not** a UserDefaults key.
- **View observation**: `@Observable` class; `ContentView.swift:54-57` reads `viewModel.backgroundImage.imageData` in `body` (Observation-tracked), passing `isEnabled`/`opacity` from `@AppStorage` (:165-169). `BackgroundPhotoLayer` (`BackgroundImageStore.swift:214-236`, iOS-only) renders `scaledToFill` in a pinned `Color.clear.overlay`, `.ignoresSafeArea()`, `.allowsHitTesting(false)`, `.accessibilityHidden(true)`; `isEnabled == false` renders nothing "without touching disk" (:216, :222).
- **No custom error type**: `URLError(.badServerResponse)` (:24), `URLError(.cannotDecodeContentData)` (:150), plus JSON decode/encode and file-write throws. (App's only custom error enum: `DictationError` in `SingleThread/ReminderDictation.swift:202`.)

## Q6: Cross-target consumption of background photo/preferences

### Findings
- **The keys are only** `"backgroundEnabled"` (= true, `ContentView.swift:165-166`) and `"backgroundFadePercent"` (= 50, :168-169), both `store: .standard`. No `backgroundImage`/`refreshedAt`/`fetchedAt` UserDefaults key anywhere; photo state is files-on-disk (`background.jpg`/`background.json`).
- **iOS app target (SingleThread)** — sole real consumer: renders the photo (`BackgroundPhotoLayer`, `BackgroundImageStore.swift:214-236`, used at `ContentView.swift:54-57`, both `#if os(iOS)`), reads/writes both keys (:165-169, :545-546, :559-560), refreshes (`ContentViewModel.swift:83`), exposes Settings UI (`SettingsView.swift:74-82`).
- **macOS (same target, not separate)**: "SingleThread" builds `iphoneos iphonesimulator macosx` (`project.pbxproj:767`); mac entry `MacAppDelegate` (`SingleThread/AppDelegate.swift:67`, `SingleThreadApp.swift:32`). macOS **references the preferences** (keys compile without `#if`; `makeSettingsBag` `#else` branch :559-560; Settings rows reachable; store compiles with `NSImage` decode at `BackgroundImageStore.swift:192-197`; `refreshIfNeeded` runs, no platform guard at `ContentViewModel.swift:83`) but **never renders the photo** — `BackgroundPhotoLayer` is iOS-only.
- **SingleThreadWidget — no references**: zero matches for `BackgroundImageStore`/`BackgroundPhotoLayer`/background keys. Its timeline entry reads only the App-Group reminder display prefs (`ShowDatePreference()` etc., `AppGroup.defaults.bool(forKey: "showUndatedReminders")`, `SortOptionStore().load()`; `SingleThreadWidget/NextThingWidget.swift:23-27, 58-63`). Widget carries the App Group entitlement (`project.pbxproj:992,1023` → `SingleThread/AppGroup.entitlements`). (Only substring hit: SwiftUI's `containerBackground(.fill.tertiary, ...)`, `NextThingWidget.swift:119`.)
- **SingleThreadWatch — no references**: zero background matches under `SingleThreadWatch/`. Watch state arrives exclusively via WatchConnectivity receive hooks (`WatchAppViewModel.swift:186-245`) into watch-local `.standard`-backed holders (e.g. `ShowDateState.swift:21`); initial restore from `.standard` (`WatchAppViewModel.swift:35-38`). No App Group on the watch target (no `CODE_SIGN_ENTITLEMENTS`, `project.pbxproj:937-990`), matching `AppGroup.swift:13-14`'s watchOS fallback.
- **App Group / sync split is deliberate**:
  - AppGroup-backed (shared app↔widget via entitlement; pushed to watch over WCSession): the seven show\*/sort prefs (`ContentView.swift:181-199`) plus `completionCount`/`isEntitled`.
  - `.standard`-backed (phone-local): `appearanceMode`, `textSize`, `allowsLandscape`, `showMicrophoneButton`, `enableActionButtons`, `showSwipePrompt`, **`backgroundEnabled`, `backgroundFadePercent`**.
  - WatchConnectivity payload keys (`SkippedReminderSyncService.swift`, `pushAll()` :167-201; message-only keys :212-222): `skippedReminderIdentifiers`, `excludedListTitles`, `showUndatedReminders`, `sortOption`, `completionCount`, `showDate`, `showRecurrence`, `showAlarms`, `showList`, `showCompletionGlow`, `isEntitled`. **No background key is in the payload.**
  - Corroboration: `BackgroundImageStore.swift:50-52` "never touches the App Group or sync payloads"; the only cross-suite touching of `"backgroundEnabled"` is test cleanup (`UITestingSeed.swift:71`, cleared from both suites by `resetPersistedState()` :45-54).
- **Bottom line**: a new background preference currently reaches neither the widget nor the watch — background photo + preferences are intentionally phone-local `.standard`.

## Cross-Cutting Observations

- **Single-store wiring pattern**: one `BackgroundImageStore` instance created in `AppViewModel.swift:79`, threaded through `ContentViewModel`, `ContentView`, `SettingsView`, `BackgroundSettingsView`; views observe via `@Observable`; the Settings button mutates it directly (bypassing `@AppStorage`) while cosmetic flags round-trip through the bindings bag.
- **Two writing surfaces for background state**: photo bytes + sidecar on disk (store-owned, atomic, "disk before state" `BackgroundImageStore.swift:155`) vs. the two `@AppStorage` keys in `.standard` (bag → `.onChange` write-back, `ContentView.swift:129-130`). They never touch.
- **The five-step setting pipe** (Q3 last ¶) is the project's universal pattern for any new cosmetic preference; the bag init defaults (`SettingsBindings.swift:3-13`) and `makeSettingsBag()` snapshots must stay in sync in three places (bag init default, ContentView `@AppStorage` default, `makeSettingsBag` wiring).
- **Lifecycle-triggered background refresh**: only `.task` at `ContentView.swift:88-90`; no timers or scenePhase paths. Failure keeps prior state; only a missing/corrupt sidecar can blank the photo, and even then disk bytes survive.
- **UI-test isolation philosophy**: `--seed` wipes persisted keys (`resetPersistedState()`), so cross-relaunch persistence tests relaunch with `--ui-testing` instead (documented at `SingleThreadUITestsFlows.swift:216-219, 287-288`).
- **Platform split**: photo *rendering* is iOS-only (`BackgroundPhotoLayer`); photo *store/settings* compile and run on macOS in the same target — the Settings row shows on macOS though nothing renders.
- **`BackgroundFade` is app-target** (not Core), kept in sync with `backgroundFadePercent`'s default (literal `50` in `SettingsBindings.swift:27` vs `BackgroundFade.defaultValue` in `ContentView.swift:169`).
