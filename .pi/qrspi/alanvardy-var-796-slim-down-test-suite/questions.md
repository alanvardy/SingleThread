# Research Questions

## Context

This repo's test suite spans four targets: `SingleThreadTests` (~470 `@Test`) and `SingleThreadWatchTests` (~38 `@Test`, both Swift Testing), plus `SingleThreadUITests` (~52 XCTest) and `SingleThreadWatchUITests` (~17 XCTest), runnable on iOS simulator, macOS, and watchOS simulator via `scripts/test.sh` and the `Makefile`. App logic reaches real system services (EventKit, UNUserNotificationCenter, StoreKit, WatchConnectivity, URLSession) through a mix of protocol abstractions, injectable seams, and launch-argument flags. Focus on the test inventory, runtime costs, the seam/abstraction landscape, permission-dialog triggers, and shared-state/serialization constraints. Map and measure what exists; do not propose changes.

## Questions

1. **Empirical timing profile and measurement tooling.** What wall-clock evidence exists (or can be produced) for each local test phase — iOS unit, iOS UI, watch unit, watch UI, macOS unit, and the build-for-testing phases — across cold vs. warm DerivedData? Where do the splits between compile time and test-execution time land? What timing artifacts and mechanisms are already available in the repo or machine-level (xcresults, `xcrun xcresulttool`, `-showBuildTimingSummary`, Makefile `coverage*` result bundles, CI logs), and which per-test duration data can they yield?

2. **Structure of runtime cost in the suites.** Where does wall time concentrate: counts and locations of real-time waits (explicit `sleep`/`usleep`, `waitForExistence`/`waitForNonExistence`, poll loops, background/foreground delays), suites forced sequential via `@Suite(.serialized)` and the shared state they serialize on, and app-launch counts per UI suite with the per-launch work (build/install/startup, `resetPersistedState`, seam parsing)? Which individual tests or suites dominate execution time and why?

3. **Unit-vs-UI coverage matrix.** For each behavior asserted in the UI test targets (skip, complete, delete, undo, swipe prompt, glow, freemium gate, excluded lists, background/pin prefs, show-list/glow persistence, deep link, reschedule, action-menu gate, nudge threshold, empty/all-done copy, priority marker, notifications, launch/appearance), at which lower layers does the same logic also get asserted (store, view-model, view-render, sync-service unit tests), and what does each layer uniquely prove? Which UI tests exercise integration-level behavior that no unit test covers (real process launch, XCUITest a11y audits, SpringBoard permission dialogs, real notification scheduling E2E, real WCSession receive path, layout/geometry assertions, rendered-text assertions)?

4. **Seam and abstraction inventory.** Enumerate every testability seam and where it's used: protocol abstractions (`EventKitStoring`, `SkipSyncSession`, `SpeechTranscribing`, `BackgroundImageFetching`, `AuthorizationRequiring`, URL-opening), in-memory/fake stores, launch-argument flags (`--seed`, `--ui-testing*` family, `--no-reminders`, reset flags, notification overlay seam), injectable timing (`ReminderStoreSettle`, glow duration seams), and StoreKit test sessions. For each, what real system interaction does it replace? Conversely, which app logic paths have no seam at all and only ever run against a real system service (real `UNUserNotificationCenter` scheduling/permission, real `WCSession` activation, StoreKit purchase flow, widget EventKit access, real `URLSession` wallpaper fetch)?

5. **Reminders access dialog trigger map.** Where and when is the Reminders (EventKit TCC) access dialog triggered: `requestAccess` call sites, the authorization-state decision flow, and which app launch paths reach it? Which test seams bypass it (InMemoryEventStore `.fullAccess`, `--no-reminders`/`loadsReminders:false`, `authorizationStatus` short-circuits) and which tests rely on each? Separately, map the notification-permission (SpringBoard "Allow") dialogs: which UI tests drive the real `requestAuthorization` with no bypass, and how many dialog interactions does a full local run currently perform?

6. **Shared state, isolation, and suite serialization.** What state is shared across tests (App Group suite keys with `.standard` fallback, real `UserDefaults`/AppGroup keys, file-scope `EKEventStore` fixtures, StoreKit `SKTestSession`, timers/glow, one-shot gates), which suites are `@Suite(.serialized)` because of it, and what reset/isolation mechanisms exist (`resetPersistedState` key lists, per-suite setups)? How does the local runner order suites and targets, and what is inherently sequential vs. parallelizable?
