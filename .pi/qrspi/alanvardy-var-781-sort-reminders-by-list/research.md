## Q1: Sort comparator architecture

### Findings
- `ReminderSort` is a `public nonisolated enum` (`SingleThreadCore/Sources/SingleThreadCore/ReminderSort.swift:4`) with two entry points:
  - Legacy 2-arg `areInIncreasingOrder(_:_:)` at `ReminderSort.swift:9-11` — pure delegate to the 3-arg form with `using: .priority` (`:10`); doc comment calls it "backward-compatible" (`:7-8`).
  - Option-aware `areInIncreasingOrder(_:_:using:)` at `ReminderSort.swift:14-42`, switching per `option` (`:18-41`).
- Only production call site: `ReminderStore.visibleReminders` (`ReminderStore.swift:147-152`), `.sorted { ReminderSort.areInIncreasingOrder($0, $1, using: sortOption) }` (`:151`), after two filters: skipped IDs (`:149`) and excluded list titles (`:150`). `sortOption` default `.priority` (`ReminderStore.swift:77`); hook-firing path `setSortOption` at `ReminderStore.swift:406-411` (guard `:407`, assign `:408`, `onSortOptionChanged?` `:409`, `onRemindersChanged?` `:410`).
- Three private comparison tiers, each returning `ComparisonResult?` where `nil` = tie:
  - `comparePriorities` (`ReminderSort.swift:46-59`): ranks via `ReminderPriority.rank(for:)` (`:47-48`; defined `ReminderSkip.swift:82-89` — high→0, medium→1, low→2, nil; `level(for:)` at `ReminderSkip.swift:60-67` maps 1–4→high, 5→medium, 6–9→low). Ranked-vs-ranked (`:50-51`), ranked-vs-nil (`:52-53`), nil-vs-ranked (`:54-55`), equal/nil→nil (`:56-57`).
  - `compareDueDates` (`ReminderSort.swift:61-74`): `dueDateComponents?.date` (`:62-63`); earlier ascends (`:65-66`), dated before undated (`:67-68`), undated after dated (`:69-70`), both-nil/equal→nil (`:71-72`).
  - `titleComparison` (`ReminderSort.swift:76-78`): `localizedCaseInsensitiveCompare` — non-optional, always decisive.
- Per-option composition (`ReminderSort.swift:19-40`):
  - `.priority` (`:19-26`): rank → due date → title.
  - `.dueDate` (`:27-31`): due date → title; priority never consulted.
  - `.title` (`:32-40`): title; if `.orderedSame`, due date; if still tied, `return false` (`:40`) — **no identity tie-break** (no `calendarItemIdentifier` key anywhere in the comparator).
- `SortOption` is `String`-raw, `CaseIterable`, `Sendable`, exactly `.priority/.dueDate/.title` (`SortOption.swift:6-19`), `defaultsKey = "sortOption"` (`:18`). `SortOptionStore.load()` falls back to `.priority` on missing/invalid (`SortOption.swift:34-39`).
- Test invariants (`SingleThreadTests/ReminderSkipTests.swift:134-225`, `struct ReminderSortTests`): priority→date→title chain (`:137-149`), same-priority date/title tiers (`:152-162`), **option equivalence**: `.priority` option == legacy 2-arg comparator (`:165-173`), `.dueDate` ignores priority (`:176-185`), `.title` case-insensitive + date tie-break (`:188-197`).
- What tests do **not** pin: strict-total-order laws (no property tests); determinism of fully-equal reminders (comparator returns `false` both directions, `:40` — order then comes from stdlib stable `sorted(by:)` input order); nil-title behavior (fixture always sets title, `:202-212`).
- Adjacent: `ReminderStoreTests.visibleRemindersSortsByPriorityThenDate` (`ReminderStoreTests.swift:51-75`), `setSortOptionReordersAndNotifies` (`:168-217`), `SortOptionTests` raw values / allCases / defaultsKey / presentation (`SortOptionTests.swift:8-36`).
- UI tests acknowledge the title tie-break at `SingleThreadUITestsFlows.swift:113-117` (seeds must use distinct rank buckets 1/5/9).

## Q2: List identity and metadata

### Findings
- **No app-level list model.** Lists are raw `EKCalendar`; the seam is `EventKitStoring.calendars(for:)` (`EventKitStoring.swift:13-16`), with `EKEventStore` conformance (`:25-`) and injected `[EKCalendar]` in tests (`InMemoryEventStore.swift:52-54`).
- **The title string is the list identity.** `EKCalendar.calendarIdentifier` appears zero times in Swift sources; only `calendar?.title` is consumed, at exactly three sites: `ReminderStore.swift:480-483` (`availableLists`), `ReminderStore.swift:150` (exclusion filter), `ReminderDisplay.swift:16` (`listName`). No calendar color/default-flag reads anywhere.
- Store properties: `excludedListTitles: Set<String>` (`ReminderStore.swift:57`), `availableLists: [String]` (`:71`, doc "All reminder-list titles (sorted, deduplicated) the settings UI presents" `:70`), persisted by `ExcludedListStore` under key `"excludedListTitles"` (`ExcludedListStore.swift:7,15,19`).
- Surface of list metadata on a reminder: `ReminderDisplay.listName: String?` (`ReminderDisplay.swift:48`, init `:16`); rendered iOS `ReminderCardView.swift:108-112` (a11y `"listNameText"`), watch `WatchReminderView.swift:347-348`, widget `NextThingWidget.swift:207-208` — all gated on `showList` (App Group key, default false, `ContentView.swift:124-126`).
- Exclusion flow: set path `setExcludedListTitles` (`ReminderStore.swift:409-417`, fires `onExcludedListsChanged` + `onRemindersChanged`); WatchConnectivity receive path `refreshExcludedListTitles` (`:419-429`, deliberately no `onExcludedListsChanged` echo, anti-echo comment `:420-425`); rehydration at every `reload()` (`:679`).
- `availableLists` populated only in `reload()` (`ReminderStore.swift:480-484`) → `Set(titles).sorted()` (case-sensitive; duplicate titles collapsed — pinned by `EventKitStoringTests.swift:505-519`, `["Personal","Work","work"]` from `Work, Personal, work, Work, ""`). Consumed only by Settings: `SettingsView.swift:94-96` → `FilterSortSettingsView.swift:41-45` → `ExcludedListsView.swift:21` (`ForEach(availableLists, id: \.self)`). Watch/widget never read it.
- **Shared titles / renames are not reconciled**: exclusion is by title string (`ReminderStore.swift:150`); rename leaves a stale title in the set (reminders reappear); rename *into* an excluded title hides. No `EKEventStoreChanged` observers anywhere (deliberate, per `.pi/qrspi/.../var-750/design.md:83`); refetches are explicit `reload()` calls only. Tests pinning this: `ReminderStoreTests.swift:100-106, 111-119, 127-142, 148-164`, `ExcludedListStoreTests.swift:9-24`, `ReminderDisplayTests.swift:60-71`.

## Cross-Cutting Observations
- **First-element doctrine**: the entire product surfaces a single "current reminder"; every consumer relies on `visibleReminders.first` (`ReminderStore.swift:167-168, 260-262, 315-317, 380-382, 422`; `ContentView.swift:413`; `WatchReminderView.swift:107`; widget via `listContent`). Sort order *is* product behavior — the top card, complete/skip/delete targets, reschedule targets, and the watch ghost-card are all first-element.
- **Title-as-identity for lists** is total: exclusion, display, `availableLists`, and (were it added) any list-based sort would key on `calendar?.title`; no identifier plumbing exists, and there is no EventKit change observation.
- **Everything funnels through one sort**: one comparator call site (`ReminderStore.swift:151`), one shared persisted key (`SortOption.defaultsKey`), one App Group private user-defaults suite, and WatchConnectivity `applicationContext` broadcast for phone→watch.
- **Watch/lists gap**: `availableLists` is iOS-Settings-only; the watch has no list UI and stores prefs in `.standard` (no App Group entitlement).
- The `--seed` seam resets persisted state including `sortOption` on every launch, so UI sort behavior is only ever tested in default-`.priority` mode today.

## Open Areas
- No property-based verification of comparator strict-total-order laws or equal-element determinism (Q1) — the comparator's behavior on fully-tied pairs is stdlib-stable-input-order, unasserted.
- Nil-title reminders: comparator calls `lhs.title.localizedCaseInsensitiveCompare` (`ReminderSort.swift:77`) — forced-unwrap-free via `String?` semantics? `title` is non-optional `String` on `EKReminder`; not exercised with a nil-title fixture.
- macOS app's settings/sort surface: launch restore confirmed (`AppViewModel.swift:25`), but no macOS-specific settings walk-through was performed (out of question scope; `mac-test` exists, `Makefile`).
- Actual WatchConnectivity behavior on device (vs. `updateApplicationContext` semantics described in code comments) is untested in this research.
