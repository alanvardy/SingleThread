## Q3: Compiler type-check budget in ContentView

### Findings
- The whole `body` (67–173) is **one expression**: `ZStack` + 16 chained modifiers on iOS (13 on macOS; the iOS-only ones are the undo overlay :97–114, scenePhase onChange :130–134, notificationsEnabled onChange :151–155), plus nested result-builder closures (4 overlay closures, 6 trailing `.onChange`/`.task` closures, 2 sheet closures). Type inference must solve the entire expression in one pass.
- Three extraction sites, with verbatim comments:
  - `settingsSheetContent` (574–582): "…Lives in its own functions so the long `.onChange` chain has its own type-check budget instead of blowing up `body`'s single expression." (576)
  - `settingsSheetWritebacks(_:)` (587–622): "The write-back chain is split into staged values so each expression stays within the compiler's type-check budget (a single 17-modifier chain does not)." (585–586) — staged as `withAppearance` (588–599, 2 `.onChange`), iOS `withIOSPreferences` (601–610, 6 more), final return (612–621, 10 more) = **18 `.onChange` modifiers total on iOS / 12 on macOS**; the "17" in the comment is stale. Non-compiler comment at 595–597 explains the bag→@AppStorage write-back motive.
  - `setBackgroundPinned(_:)` (633–635): "Dispatches the async pin-state change off the sync modifier closure. Extracted so the long `body` modifier chain still type-checks." (632) — call site `.onChange(of: backgroundPinned)` (139–141).
- Other chains, measured: reminder-card row = 9 modifiers on iOS (385–435: listRowBackground, 2×padding, 2×frame, listRowSeparator, contextMenu, 2×swipeActions), List = 4 (438–448), `completionGlowOverlay` = 8 (562–572), gear button = 4 (83–96).
- **Type-check vs size limits are orthogonal axes**: the extractions shrink single Swift *expressions* but add lines *inside* the struct (e.g. 587–622, 633–635); the size limits are handled purely by the disables at 5 and 13. The one place a split is justified by a length budget is the iOS extension comment (683–685): "Kept in a separate extension so `ContentView`'s own body stays within SwiftLint's `type_body_length` budget." — moving members out of the struct (which does not help `file_length`, same file).
- Shared root cause (header comment 1–4): all view modifiers for the single-screen UI deliberately stay in one struct/file — which simultaneously overflows both thresholds and creates the long body expression.
- Elsewhere in the codebase, only one non-ContentView compiler-limitation comment: `SettingsBindings.swift:9-13` — iOS-only properties are declared unconditionally because "the compiler does not support `#if` directives inside a parameter list". No type-check comments in SingleThreadCore/ or SingleThreadWatch/. Known history: `task.md` notes the body chain hit a type-check timeout in VAR-743, worked around by these helper extractions.

## Cross-Cutting Observations
- **One shared root cause** (ContentView.swift:1–4): the single-screen UI deliberately concentrates every view modifier in one struct/file. This one decision drives all three constraints: `file_length` 700/800, `type_body_length` 500/600, and the compiler's single-expression type-check budget.
- **Two distinct mechanisms already in use**: (a) *expression splitting* for the compiler (extracted funcs/computed vars 578–582, 587–622, 633–635) and (b) *body-line accounting* for SwiftLint (the iOS `private extension` 686–737 legally removes members from the struct body; the `// swiftlint:disable` directives 5 and 13 handle what splitting hasn't). The repo contains exactly one example of splitting to beat a length budget (the extension) and one of raising the budget instead (650→700).
- **Disabled-rule precedent is codified in comments**: three files carry size directives with explanatory headers (ContentView 1–4, ReminderStoreTests 5–7, SingleThreadUITestsFlows 11–12); the UI-test flows file mirrors ContentView's exact situation (a 700+ line file at the 650-era threshold).
- **Threshold history is entangled with VAR-743**: the 650→700 bump (efa156e) and the type-check helper extractions (setBackgroundPinned, 633–635) both came from the pin-wallpaper work; VAR-746 (2ff16118) added the `file_length` disable, VAR-744 added the undo overlay + the other two file-length disables.
- **Bag-writeback asymmetry is as-built**: `backgroundPinned` is the only bag member without a write-back (Q5), i.e. the persisted pin state is not updated through the settings sheet path.
- Every assertion style in the test suites is string-snapshot (`String(describing:)`) + seam-level decisions + UI-test identifiers; nothing instantiates `body` modifiers by type name.
