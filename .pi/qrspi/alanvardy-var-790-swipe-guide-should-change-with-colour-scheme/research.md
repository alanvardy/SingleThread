## Q3: Adaptive-color patterns elsewhere — helpers, purity, testability

### Findings
- **CardPlate**: `enum CardPlate` with `static let cornerRadius: CGFloat = 10` (`CardPlate.swift:16`); `static let promptBoxFill = Color(red: 0.16, green: 0.17, blue: 0.18)` fixed (`:23`); `static func plateFill(for colorScheme: ColorScheme) -> Color` — a **pure static function taking an explicit `ColorScheme` argument**, no environment inside — `CardPlate.swift:29-31`. Callers each read `@Environment(\.colorScheme)` at the view level and pass it in: `ReminderCardView.swift:49-50 -> :44`; `EmptyStateCard.swift:48-49 -> :34`. Renderer `CardPlateModifier`/`.cardPlate(fill:padding:restoresGeometry:)` is a pure shape/padding machine with no scheme logic — `CardPlateModifier.swift:8-42` (doc `:38-40` says call sites pass `plateFill(for:)` or `promptBoxFill`).
- **ControlPlateModifier**: adaptive logic **inside** the modifier via `@Environment(\.colorScheme)`, overridable `var fill: Color?`/`glyph: Color?` (nil = auto) — `ControlPlateModifier.swift:16,18,38-39`; ternaries `colorScheme == .dark ? .black : Color(white: 0.92)` (fill) and `... .white : Color(white: 0.15)` (glyph) at `:21-22`; constants `:33-36`; View helper `controlPlate(fill:glyph:)` `:51-54`. Default-adaptive call sites: `ContentView.swift:201,217,235,507,536`, `ContentView+ActionMenu.swift:41`. Fixed overrides: `.controlPlate(fill: .red, glyph: .white)` `ContentView.swift:546` (recording indicator); `feedback.backgroundColor` (`.green`/`.red`) `:588` / `CreationFeedback.swift:20-26`.
- **Other adaptive mechanisms**:
  - Dynamic system providers: `Color.systemBackground` = `Color(uiColor: .systemBackground)` / `Color(nsColor: .windowBackgroundColor)` — `Color+CrossPlatform.swift:15-19` (used `ContentView.swift:183`). `CodeSpanFormatter.platformSecondaryBackground() -> SwiftUI.Color?` — watchOS `Color.gray.opacity(0.15)` `:142`, UIKit `Color(uiColor: .secondarySystemBackground)` `:145`, AppKit `Color(nsColor: .underPageBackgroundColor)` `:148`, fallback `:151` (applied at `:131`).
  - `colorScheme == .dark` branches: exactly three in app code — `CardPlate.swift:30`, `ControlPlateModifier.swift:21-22` (no others anywhere).
  - Semantics: `.foregroundStyle(.secondary)` widespread (`ReminderCardView.swift:93,103,111,120,125`; `ContentView.swift:650...`; widget `NextThingWidget.swift:173...`; watch `WatchReminderView.swift:170...`); `.tint(.green/.orange/.red)` swipeActions `ContentView.swift:454,463,471` + ActionMenu + widget/watch.
  - Asset catalogs: only named set is `SingleThread/Assets.xcassets/AccentColor.colorset`; **zero** `Color("...")` lookups in Swift.
- **Adapts vs hardcodes**: adapts — card plate, empty-state plate, control plates (default), root background, code-span background, all `.secondary`/tints, widget `.fill.tertiary`. Hardcodes a single color regardless of scheme — swipe-prompt plate + its hint separator/buttons (Q1), recording indicator, creation feedback, upgrade CTA (`PurchaseSettingsView.swift:184,188`), completion glow `Color.green.opacity(0.1)` `ContentView.swift:552`, watch glow `:190`.
- Pure-and-testable pattern: color *decisions* live in static/pure helpers (`CardPlate.plateFill(for:)`) asserted headless in tests; the paint/rendering cannot be asserted, only the decision — see CardPlate/swipe tests in Q5.

## Q4: Runtime appearance changes — live flip vs restart, hooks, override propagation

### Findings
- **Live flip, no restart**: full chain — Picker (`InterfaceSettingsView.swift:35-46`) -> bag -> `@AppStorage` write-back (`ContentView+Settings.swift:19`) -> `ContentView.onChange(of: appearanceMode)` (`:277-279`) -> `viewModel.handleAppearanceMode` (`ContentViewModel.swift:130-136`) -> `AppDelegate.applyAppearance` applies to **every** scene window immediately (`AppDelegate.swift:15-23`; the settings-sheet window is covered via `.flatMap(\.windows)` `:17-19`; macOS loops `NSApp.windows` `:72-76`). No restart/relaunch/reopen strings anywhere in app resources (grep 0 matches); no restart instructions.
- **Existing hooks observing appearance**: **none**. Repo-wide grep confirms zero hits for `AppleInterfaceThemeChangedNotification`, `traitCollectionDidChange`/`UITraitCollection` (except the setter), `didChangeEffectiveAppearance`/`effectiveAppearance`, `onChange(of: colorScheme)`, `onReceive`. The only `NotificationCenter` observer in app code is `UserDefaults.didChangeNotification` on `AppGroup.defaults` for watch preference sync — `AppViewModel.swift:451-455`.
- **Does `UIWindow.overrideUserInterfaceStyle` reach SwiftUI `@Environment(\.colorScheme)`?** There is no bridge/forwarding code in the repo — propagation is UIKit/AppKit plus SwiftUI system behavior. Connection points: setter `window.overrideUserInterfaceStyle = mode.windowOverrideStyle` (`AppDelegate.swift:21`, iOS) / `window.appearance = mode.appKitAppearance` (`AppDelegate.swift:74`, macOS); readers are the three `@Environment(\.colorScheme)` declarations (Q2). Lifecycle reapplication taps: `AppDelegate.swift:45-48` (iOS become-active), `:78-84` (macOS launch + become-active).
- `.system` clears the override (`.unspecified` at `AppearanceMode.swift:27` / `nil` at `:40`) so windows re-follow the device — OS-managed, no app observer.
- `.preferredColorScheme` is NOT in the runtime path — previews only (`ContentView+Previews.swift:39,57`; `SettingsView.swift:216`), because the canvas has no window (doc `AppearanceMode.swift:47-49`).
- UI test drives the live toggle: `SingleThreadUITestsAppearanceLaunchTests.swift:64-89` (asserts foreground/liveness via screenshot; value mapping delegated to unit tests — comments `:64-75`).

## Cross-Cutting Observations
- **The swipe prompt is the only deliberate non-adaptive element on the adaptive card.** The card plate flips via `plateFill(for: colorScheme)` (`ReminderCardView.swift:44`); the prompt box (`promptBoxFill`) and every prompt stroke are fixed — doc comments in `CardPlate.swift:18-22` state this is by design, and `SwipePromptTests.swift:34-37` asserts the decision because the paint "can't be asserted headlessly".
- **Two distinct adaptive idioms coexist**: pure function with explicit `ColorScheme` param (`CardPlate.plateFill(for:)`) vs environment-reading modifier with overridable params (`ControlPlateModifier`). Both are unit-testable; call sites centralize the `@Environment(\.colorScheme)` read in exactly three views.
- **Appearance flows through the window layer, not SwiftUI preferences**: the entire appearance system keys off `UIWindow.overrideUserInterfaceStyle` / `NSWindow.appearance`, set from `@AppStorage("appearanceMode")`; SwiftUI just consumes the resulting `\.colorScheme`. No observer or preference bridge exists; correctness relies on UIKit/AppKit propagation plus lifecycle re-application.
- **Launch-arg seams are the de-facto test API**: `--ui-testing` (+ `--reset-swipe-preference`, `--reset-glow-preference`) in `AppViewModel.swift:257-263`; `--seed` via `UITestingSeed`. Both `UserDefaults.standard` and `AppGroup.defaults` are targets; `showSwipePrompt` is in `UITestingSeed`'s persisted-keys list so seeding resets it.
- **Every persisted switch written in this repo is iOS-to-watch-synced**, but the swipe prompt is iOS-only by design (the watch has no swipe gestures); the sync path exists at `AppViewModel.swift:451-455`.
- Platform split: swipe guide iOS-only; appearance plumbing iOS + macOS; watchOS has neither.
