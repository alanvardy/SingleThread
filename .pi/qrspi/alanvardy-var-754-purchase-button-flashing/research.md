# Research Findings

Freemium entitlement flow — `EntitlementStore.isEntitled` derivation, rendering, watch sync, and test seams. Line refs are to the working tree on branch `alanvardy-var-754-purchase-button-flashing`.

## Q1: How `isEntitled` gets its value from process start to first view evaluation

### Findings
- `EntitlementStore` is `@MainActor @Observable public final class` (`SingleThreadCore/Sources/SingleThreadCore/EntitlementStore.swift:13-16`). Single source of truth: `public private(set) var isEntitled: Bool = false` (`EntitlementStore.swift:46`); only the class writes it.
- Construction chain (production): `SingleThreadApp.init()` → `AppViewModel()` (`SingleThread/SingleThreadApp.swift:16-19`) → `AppViewModel.init` calls `makeStore(arguments:)` (`SingleThread/AppViewModel.swift:32`, production branch `:277-279`) → `ReminderStore.init` declares `entitlementStore: EntitlementStore = EntitlementStore()` as a **default parameter** (`SingleThreadCore/Sources/SingleThreadCore/ReminderStore.swift:27`, assigned `:40`, stored `:102`). The instance is created inside `SingleThreadApp.init()`, **before any SwiftUI view is evaluated**.
- The `init()` observation task (`EntitlementStore.swift:17-21`): `observationTask = Task { await self?.refreshEntitlement(); await self?.observeTransactionUpdates() }`. Created in a `@MainActor` init so the task inherits MainActor context. Not tied to `didFinishLaunching`/scenePhase — `AppDelegate` only handles appearance/orientation locking (`SingleThread/AppDelegate.swift:16-84`) and never touches `EntitlementStore`.
- **First StoreKit refresh**: `refreshEntitlement()` from the init task (`EntitlementStore.swift:20`) — this is the only refresh at boot. `ContentView .task` → `ContentViewModel.task` (`ContentViewModel.swift:154-158`) runs `store.start()` only; no entitlement call.
- `refreshEntitlement()` (`EntitlementStore.swift:80-91`): `for await verificationResult in Transaction.currentEntitlements`, keeps `.verified` transactions with `productID == Self.unlockProductID` (`"app.alanvardy.SingleThread.unlimited"`, `:39-41`), assigns `isEntitled` only after the loop ends (`:90`).
- **Value before refresh completes: `false`.** `isEntitled` starts at the default (`:46`) and is written only at the end of the async loop — so a genuinely-purchased account reads `false` until `Transaction.currentEntitlements` iteration finishes (`AsyncSequence`, `:83`). First view evaluation races this.
- `observeTransactionUpdates()` (`EntitlementStore.swift:69-77`): long-lived `for await` over `Transaction.updates`; `.finish()`es verified transactions then re-refreshes. Cancelled in `deinit` (`:34-36`).
- `sync()` (`EntitlementStore.swift:50-61`): `AppStore.sync()` then `refreshEntitlement()`. User-initiated only — Restore Purchases button (`SingleThread/PurchaseSettingsView.swift:42-43`) and post-purchase (`PurchaseSettingsView.swift:156`). **Not called at boot.**
- Seam: `init(testingWithEntitled:)` (`EntitlementStore.swift:25-32`) sets `isEntitled` synchronously and sets `observationTask = nil` — no refresh loop ever runs.
- Views never read `isEntitled` directly for gating — they read `ReminderStore.canMutate` (`ReminderStore.swift:136-138`); because `EntitlementStore` is `@Observable`, reading `.isEntitled` inside `canMutate` during a body pass registers the dependency, so views re-evaluate when the async refresh flips it.

## Q2: `isEntitled` → `canMutate` → `bottomBar` decision chain

### Findings
- `canMutate` (`ReminderStore.swift:136-138`): `entitlementStore.isEntitled || completionCounter.count < 100`. Entitled ⇒ always mutatable; else free-tier lifetime cap of 100 completions.
- `completionCounter` is an injected `public let` (`ReminderStore.swift:26, 39, 98`) of type `CompletionCounterStore` — persisted in App Group `UserDefaults` under `"completionCount"` (`SingleThreadCore/Sources/SingleThreadCore/CompletionCounterStore.swift:12-15`). `count` is a computed `UserDefaults.integer(forKey:)` read (`:18-21`) — **not observable**; no notification fires when the count crosses 100.
- Counter coupling: `canMutate` depends on the counter; the counter depends on successful EventKit saves gated by `canMutate`. All `canMutate` guards are silent no-ops: `completeReminder` (`ReminderStore.swift:174`, increment only after save `:198`), `undoLastCompletion` (`:223`, decrement `:229`), `deleteReminder` (`:248`), `skipCurrentReminder` (`:300`), widget skip intent (`:331`). `addReminder` has **no** guard (`:258-270`) — dictation-created reminders bypass the cap.
- `bottomBar` (`SingleThread/ContentView.swift:652-704`) renders in empty and populated branches (`:385, :457`), never in the allSkipped branch. Structure:
  1. macOS cluster: `#if os(macOS)` + `visibleReminders.first != nil` → `actionButtons` (`:654-657`) — no entitlement gate; mutation no-ops silently on macOS.
  2. `dictationError != nil` → error text (`:658-661`).
  3. `creationFeedback != nil` → feedback plate, `else isDictating` → partial text + recordingIndicator (`:663-676`).
  4. `else if viewModel.dictation.canDictate, showMicrophoneButton` (`:677`):
     - iOS: `if !viewModel.store.canMutate { upgradePrompt } else if viewModel.showsActionButtons { actionCluster } else { micButton }` (`:678-685`). **The freemium gate replaces the mic slot.**
     - non-iOS: plain `micButton` (`:686-687`).
  5. `else !canDictate && authorizationStatus != .notDetermined && showMicrophoneButton` → "Speech recognition is unavailable." + Open Settings (`:689-699`).
  6. else → nothing.
- `showsActionButtons` (`#if os(iOS)` only, `SingleThread/ContentViewModel.swift:44-49`): `UserDefaults.standard.bool(forKey: "enableActionButtons") && store.visibleReminders.first != nil`. The view's `@AppStorage("enableActionButtons")` (default false) is at `ContentView.swift:95-97`.
- `canDictate` (`SingleThread/DictationViewModel.swift:27-30`): speech auth `.authorized || .notDetermined`. `.denied/.restricted` ⇒ false; refreshed on scene `.active` (`ContentView.swift:644-645`).
- `showMicrophoneButton` = `@AppStorage` default true (`ContentView.swift:83-84`).
- `UpgradePromptButton` (`PurchaseSettingsView.swift:173-196`; a11y id `upgradeButton` `:193`) — **rendered at exactly one site**: `ContentView.swift:680` via `upgradePrompt` (`:499-501`), bound to `$isShowingPurchase` @State (default false, `:261`), presenting `PurchaseSheet` (`.sheet`, `ContentView.swift:248-253`) which passes `entitlementStore: viewModel.store.entitlementStore`.
- No bottom-bar control ever applies `.disabled()`; gating is render-presence + silent guards. Swipe (`:417-442`) and context-menu delete (`:406-414`) render regardless of `canMutate`. Undo button is `canMutate`-gated (`:180`). The only `.disabled` in the flow is `.disabled(isPurchasing)` on the in-sheet purchase button (`PurchaseSettingsView.swift:113`).
- Full chain: `bottomBar mounted → (macOS: visible first → actionButtons) → error → feedback/isDictating → canDictate && showMic → {iOS: !canMutate → upgradePrompt | showsActionButtons → actionCluster | else micButton; macOS: micButton} → unavailable-text → nothing`, with `canMutate = isEntitled || completionCount < 100`, `canDictate = authorized || notDetermined`.

## Q3: Patterns for deferring UI until async/unknown state settles

### Findings
- **`.notDetermined` auth → `ProgressView`**: `ReminderStore.authorizationStatus` defaults to `.notDetermined` (`ReminderStore.swift:57`), settled by `start()` (`:152-155`) and `requestAccess()` (`:418-431`), kicked from `.task` (`ContentView.swift:215-217` → `ContentViewModel.swift:84-88`). iOS renders `authGatedContent` switch (`ContentView.swift:339-347`): `.notDetermined` → `ProgressView(SharedStrings.requestingAccess)` (`:341-342`), `.fullAccess` → list, else → `ContentUnavailableView`. Watch duplicates the switch with a plain `Text` for denied (`SingleThreadWatch/WatchReminderView.swift:47-56`). Reaction is pure `@Observable` dependency tracking — **no `.onChange`, no `.task`, no timeout/fallback** on either platform. Widget maps `.notDetermined` straight to `.noAccess` (`SingleThreadWidget/NextThingWidget.swift:96-100`) — no loader possible at the timeline level.
- **nil product → "Loading…"**: `PurchaseSettingsView` keeps the load in `@State` (`@State private var product: Product?`, `:73-76`), loads in `.task` (`:56-57`, `loadProduct()` `:135-146`), and renders three branches (`purchaseContent` `:79-133`): error + "Try Again" (the only retry affordance in the codebase, `:85-86`), product UI with in-button `ProgressView` + `.disabled(isPurchasing)` (`:105-113`), else a stable-height `ProgressView` + `Text("Loading…")` row (`:124-132`; the doc comment `:7-11` explains manual loading instead of zero-height `ProductView`). **This view carries the only `.onChange(of:)` reacting to async-settled state in the codebase**: `:59-65` resets all four `@State` vars when `entitlementStore.isEntitled` flips true.
- **In-flight bool → in-button spinner + disabled**: `BackgroundImageStore.isRefreshing` (`SingleThread/BackgroundImageStore.swift:74-76`, toggled `:123-128` with a `defer`), rendered inside the Refresh button label + `.disabled` + `.accessibilityValue` (`SingleThread/BackgroundSettingsView.swift:43-51`). Watch equivalent: `WatchReminderViewModel.isRefreshing` (`:42`, `refresh` `:89-101` with a `MinimumDisplayDuration` 1s hold `:95-98, 108`) → overlay `ProgressView` above any branch + disabled Refresh button (`WatchReminderView.swift:90-92, 187-192`).
- **Ghost-card deferral**: `WatchReminderViewModel.isShowingCompletionTransition` + `transitionReminder` snapshot (`:47, 51, 65-87`) keep the stale card rendering during the completion glow instead of flashing "All Done" (`WatchReminderView.swift:79-83`), cleared by a fire-and-forget `Task.sleep` (`:70-84`). Same timer-settled pattern: `CompletionGlow` (`SingleThreadCore/Sources/SingleThreadCore/CompletionGlow.swift:35-41`), dictation `creationFeedback` 1s auto-clear (`DictationViewModel.swift:77-82`), 200ms EventKit settle delays (`ReminderStore.swift:140-141, 163, 206, 231`).
- **Not-known → static surface, not a loader**: watch freemium gate `if !store.canMutate, !entitlementState.isEnabled { upgradeOniPhonePrompt } else { actionButtons }` (`WatchReminderView.swift:219-221`; doc `:130-134`) — while the entropy flag hasn't synced, "Upgrade on your iPhone" shows with no spinner.
- **Literal placeholder for nil**: `ContentView+iOS.swift:22-31` renders `"unset"` for `pendingSummary`/`lastScheduleSummary` nils (UI-test flag only).
- `@Observable` dominant pattern: views read observable classes and re-evaluate on mutation; `@State` is used for view-local load state (product), and `Binding` only where needed for model-backed controls (`@Bindable` in `WatchReminderView.swift:203`). `AppViewModel` is `@Observable` (`:15-16`); watch `WatchAppViewModel` is a plain `@MainActor final class` (`:33`) whose state reaches views through `@Observable` holders.
- No `isLoading` symbol exists anywhere; no auth-prompts spinner timeout; no widget `ProgressView`.

## Q4: Is entitlement persisted or always re-derived?

### Findings
- **Never persisted or cached.** Sweep: no `UserDefaults`/`AppGroup` write of any entitlement key exists. `isEntitled` is always re-derived from `Transaction.currentEntitlements` at process start (`EntitlementStore.swift:17-21, 80-91`), plus `Transaction.updates` pushes (`:69-77`) and `AppStore.sync()` (`:50-61`), or set in-memory via `init(testingWithEntitled:)` (`:25-32`).
- The only durable freemium value is `"completionCount"` in App Group `UserDefaults` (`CompletionCounterStore.swift:12-15`). `AppGroup` docs restrict the suite to app/widget coordination (`SingleThreadCore/Sources/SingleThreadCore/AppGroup.swift:1-5`); no entitlement key among its uses.
- **Initial-state contract from tests** (`SingleThreadTests/EntitlementStoreTests.swift`):
  - `isEntitledIsFalseByDefault` (`:13-15`): `EntitlementStore()` then `#expect(!store.isEntitled)` — reads the default before the init task's async refresh can deliver.
  - `isEntitledSurvivesStoreRecreation` (`:27-43`): despite the name, this **does not prove persistence across recreation**. It loads `SKTestSession(configurationFileNamed: "Products")`, sets `first` via `testingWithEntitled: true` (not a purchase), then creates a fresh real `EntitlementStore()` on an empty account, sleeps 200ms, and asserts `!second.isEntitled`. The comment (`:31-35` via `:33-35`) explains `SKTestSession.buyProduct` cannot complete via `xcodebuild test` on Xcode 26.6 (FB22237318 — config never reaches the simulator's storekitd container).
- **StoreKit driving**: `import StoreKitTest` (`:2`), `@MainActor @Suite(.serialized)` (`:6`), `SKTestSession(configurationFileNamed: "Products")` loads `SingleThread/Products.storekit` (one non-consumable `app.alanvardy.SingleThread.unlimited` @ USD 2.99), `session.disableDialogs = true`. **No test calls `buyProduct`/`AppStore.purchase`** — the positive purchase path is unverified; `seamSetsEntitlement` (`:20-23`) and `nonMatchingProductIDDoesNotSetEntitlement` (`:41-47`) round out the suite.
- `SingleThreadCore/Package.swift` has no test target and no StoreKitTest dependency — tests live in the app target; StoreKitTest build-config relaxation at `project.pbxproj:850-881`.

## Q5: Entitlement shipping to the watch

### Findings
- **`EntitlementState`** (`SingleThreadCore/Sources/SingleThreadCore/EntitlementState.swift`) is an `@MainActor @Observable` in-memory holder, explicitly documented as **not double-persisted / process-only** (`:3-7`). `isEnabled: Bool = false` (`:17`), single setter `apply(_:)` (`:19-21`).
- **Only production caller of `apply`**: `service.onEntitlementReceived = { value in Task { @MainActor in entitlementState?.apply(value) } }` in `wireStateReceiveHooks` (`SingleThreadWatch/WatchAppViewModel.swift:227-229`), hooked from `setupSyncService` (`:192`) at init (`:54`). Test caller: `EntitlementSyncTests.swift:114-120`.
- **Receive path**: `session(_:didReceiveApplicationContext:)` → `apply(context:)` (`SingleThreadCore/Sources/SingleThreadCore/SkippedReminderSyncService.swift:232-234, 308`) → `applyFreemium(context:)` (`:369-374`) fires `onEntitlementReceived` only when the `"isEntitled"` Bool key is present (`PayloadKey.entitled = "isEntitled"`, `:281`). Received flag is **not persisted** — the hook is terminal.
- **Send path**: `pushAll()` (`SkippedReminderSyncService.swift:167-211`) builds one latest-wins application context; `if sendsEntitled` injects `entitlementStore.isEntitled` via `MainActor.assumeIsolated` (`:192-201`) and calls `session.updateApplicationContext` (`:206`). This is the **only transport** for the flag — `sendMessage` carries only completion/delete identifiers (`:213-229`).
- **iOS wiring**: service constructed with `entitlementStore: store.entitlementStore, sendsEntitled: true` (`AppViewModel.swift:32-39`), activated `:56`. `setupEntitlementObservation` (`:345-354`, called from init `:87`) uses `withObservationTracking` with **manual re-registration** (SDK returns Void per doc `:341-344`): every `isEntitled` mutation → exactly one `pushAll()` then re-register.
- Other `pushAll` triggers each also carry the flag (full snapshot): skip/excluded/sort/pref hooks (`AppViewModel.swift:58-60, 69-71, 391`). **No initial `pushAll()` at iOS launch** — the first `isEntitled` context ships on the first trigger after launch.
- **Watch initialization**: `entitlementState = EntitlementState()` at init (`WatchAppViewModel.swift:41`) → `isEnabled == false` immediately; no restore path. Passed to `WatchReminderViewModel` (`:88-90`, stored `:37`).
- **Distinct flags**: watch `ReminderStore(loadsReminders: true)` (`WatchAppViewModel.swift:34-38`) uses its **own default `EntitlementStore()`** (`ReminderStore.swift:27`) — a separate StoreKit-backed instance whose `isEntitled` is not how the watch gates the UI. The synced `EntitlementState.isEnabled` is an additional view-level gate (`WatchReminderView.swift:219`). Watch service is built `sendsEntitled: false` with a throwaway `EntitlementStore()` (`WatchAppViewModel.swift:162, 165`) — watch never pushes the flag.
- **Tests depending on the lifecycle/initial values**: `EntitlementSyncTests.swift` — `pushAllIncludesEntitledWhenFlagEnabled` (`:15-37`, asserts context `["isEntitled"] == false` on a fresh store — depends on the false default), `pushAllExcludesEntitledWhenFlagDisabled` (`:39-56`, asserts `nil`), `applyDecodesEntitledAndFiresHook` (`:58-74`, delivers a context directly), `entitlementStateApplySetsIsEnabled` (`:110-121`, depends on `false` initial). Watch tests (`WatchSyncPipelineTests`, `WatchAppViewModelTests`) assert **nothing** about entitlement. If the iOS initial value or lifecycle changed, `EntitlementSyncTests:33` and the false-initial assumptions at `EntitlementState.swift:17` / `EntitlementStoreTests:15` are the tests that would catch it.

## Q6: Test seams and how UI tests drive gated vs entitled rendering

### Findings
- **Seam 1 — initializer**: `EntitlementStore(testingWithEntitled:)` (`EntitlementStore.swift:25-32`) — synchronous, no observation task; the seeded-entitled path never starts StoreKit observation.
- **Seam 2 — `--seed` JSON**: `UITestingSeed` schema documents `"isEntitled": true, // optional, defaults to false` (`SingleThreadCore/Sources/SingleThreadCore/UITestingSeed.swift:17`); `seed.isEntitled` (`:29`), decode `?? false` (`:100`), payload default (`:116`), `materialize()` (`:142`), pinned `CodingKeys` (`:153`). Parsed in `fromLaunchArguments` (`:35-42`). `resetPersistedState()` wipes the `"completionCount"` (`:69`) and `"isEntitled"` (`:70`) keys from a prior session — these are the **WatchConnectivity payload keys**, not seed persistence.
- **Wiring**: `AppViewModel.init` → `makeStore` (`AppViewModel.swift:41-44, 232-281`); seed present → `seededStore` (`:282-314`): seeds `completionCount` into App Group (`:292`), `entitlementStore = seed.isEntitled ? EntitlementStore(testingWithEntitled: true) : EntitlementStore()` (`:298-300`), sets `enableActionButtons` (`:301-302`). `--ui-testing` alone builds a deterministic single-reminder store with `loadsReminders: false` and a **production** `EntitlementStore` (never entitled on simulator) (`:244-273`).
- **Seam 3 — `InMemoryEventStore`**: the `--seed` path uses `usesInMemory = true` (`:234-236`) with `InMemoryEventStore` (`SingleThreadCore/Sources/SingleThreadCore/InMemoryEventStore.swift`) so write flows run without TCC.
- **UI tests** (`SingleThreadUITests/SingleThreadUITestsFlows.swift`, helper `launchApp(seedJSON:)` `:28-37`):
  - `testUpgradePromptAppearsWhenGated` (`:729-749`): seed `completionCount:100, isEntitled:false` → `app.buttons["upgradeButton"].waitForExistence(timeout: 5)` + frame-pill geometry asserts (`:735-747`).
  - `testActionClusterAppearsWhenEntitledAtCap` (`:751-761`): seed `completionCount:100, isEntitled:true` → `completeButton` exists — entitlement overrides the saturated cap.
  - `testSettingsHasPurchaseRow` (`:763-776`): no cap/entitlement → `settingsButton.tap()` then `settingsPurchaseRow.waitForExistence(timeout: 3)` (row label switches by `isEntitled` at `SingleThread/SettingsView.swift:101-107`).
  - `testPurchaseSheetHasRestoreButton` (`:778-791`): gated seed → `upgradeButton.tap()` then `restorePurchasesButton.waitForExistence(timeout: 3)` (restore shown only when `!isEntitled`, `PurchaseSettingsView.swift:39-51`, action `Task { await entitlementStore.sync() }`).
- **Watch flag seam**: `--ui-testing-gated` (`WatchAppViewModel.swift:24-28`) seeds `completionCount = 100` into App Group → `canMutate` false → watch upgrade prompt; consumed by `SingleThreadWatchUITestsFlows.swift:148-162` (`testUpgradeOniPhoneShowsWhenGated` asserts `staticTexts["upgradePrompt"]`).
- **Observable timing**: seeding is fully synchronous inside `AppViewModel.init` (`AppViewModel.swift:41-44`), so `isEntitled`/`completionCount` are correct **before the first frame**; the entitlement gate is read at body evaluation (`ContentView.swift:679` via `canMutate`, `ReminderStore.swift:137`). `waitForExistence` therefore observes the settled first-frame render, exercising the real build-from-launch branch including sheet presentation. **Not observable**: a mid-session entitlement flip — `isEntitled` is `private(set)`, the seam is init-only, real `sync()`/purchase is unit-test-only (and untestable on simulator per FB22237318), and there is no launch flag that flips entitlement mid-process.

## Cross-Cutting Observations
- **Single gate, three render sites**: `canMutate = isEntitled || completionCount < 100` (`ReminderStore.swift:136-138`) is the only freemium predicate; iOS bottomBar swaps the mic slot for `UpgradePromptButton` (`ContentView.swift:679-680`), the settings row is a NavigationLink (`SettingsView.swift:101-107`), and the watch swaps action buttons for the "Upgrade on your iPhone" prompt (`WatchReminderView.swift:219`). macOS renders no upgrade UI at all — mutations silently no-op at the same guards.
- **`@Observable` + re-derivation, never persistence**: `isEntitled` (phone) and `EntitlementState.isEnabled` (watch) are both in-memory `@Observable` flags; only `completionCount` is durable. The watch trusts a fresh context push per process; a watch relaunch without a push starts unentitled.
- **Derived-value async race is the norm**: auth status, product load, entitlement, isRefreshing, and the watch entitlement all settle after first render; the codebase's idioms are (a) placeholder branch (`ProgressView`/`Loading…`), (b) in-flight spinner + disabled button, (c) ghost-card hold, and only one `.onChange(of:)` for async-settled state.
- **`CompletionCounterStore.count` is not observable** — nothing notifies views when crossing 100; the bottomBar's gated branch is only re-evaluated when `isEntitled` flips or a parent re-renders.
- **Everything funnels through two seams**: `testingWithEntitled:` (compile-time, init-only) and `--seed` `isEntitled`/`completionCount` (launch-arg, synchronous at init). Real StoreKit purchase is not automatable (FB22237318), so all entitlement rendering tests use the seams.

## Open Areas
- The positive re-derivation path (`Transaction.currentEntitlements` returning a real verified transaction) is never asserted by any automated test; behavior relies on the StoreKit 2 implementation.
- `Exception: what happens if `refreshEntitlement()`'s async iteration is slow at cold launch` — the first-frame `false` window (`Q1:5`) has no test and no instrumentation; UI tests always use the synchronous seam.
- The watch's unentitled window between launch and the first context delivery (`WatchReminderView.swift:219`) has no timing guarantee; `EntitlementSyncTests` covers the receive path but no watch test asserts the initial `isEnabled == false` render.
- `CompletionCounterStore` crossing 100 mid-session (e.g. the 100th completion) — whether the upgrade prompt appears without any other state flip — is untested and depends on non-observable `UserDefaults` reads.
