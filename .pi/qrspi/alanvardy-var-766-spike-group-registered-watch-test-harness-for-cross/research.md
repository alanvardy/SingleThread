## Q1: App Group suite registration mechanics

### Findings
- **Suite construction — single production site.** `AppGroup.suiteName = "group.app.alanvardy.SingleThread"` at `SingleThreadCore/Sources/SingleThreadCore/AppGroup.swift:10`; the accessor is recomputed per access (no caching) at `AppGroup.swift:13-19`: `UserDefaults(suiteName: suiteName) ?? .standard`. Doc comment (`:13-15`) names the fallback trigger "watchOS, unregistered simulators, and previews".
- **Nil-fallback mechanics.** `AppGroup.swift:17`. `UserDefaults(suiteName:)` returns nil on this codebase's watch targets because the watch has **no entitlements**: `grep CODE_SIGN_ENTITLEMENTS` in `SingleThread.xcodeproj/project.pbxproj` matches only `:740-742` (iOS app Debug), `:790-792` (Release), `:1000`/`:1031` (widget Debug/Release). The watch app target configs (`:941-987`) and both watch test targets (`:1059-1149`) have none. `REGISTER_APP_GROUPS = YES` appears only on the iOS/macOS app target (`pbxproj:772, 822`).
- **Entitlement files** (only two in the repo): `SingleThread/AppGroup.entitlements:5-7` (single `com.apple.security.application-groups` array) applied to iOS device + simulator + widget builds; `SingleThread/SingleThread.entitlements:7-15` (macOS adds `app-sandbox`, `application-groups`, audio, calendars). No watch entitlements file exists.
- **Consequence per platform/simulator** (from code + prior QRSPI research): iOS device & iOS simulator → suite resolves (`AGENTS.md:55` "on simulator the suite always exists"; physical suite plist evidence at `.pi/qrspi/alanvardy-var-764-fix-view-in-reminders/implement.md:79`, `simctl spawn … defaults write group.app.alanvardy.SingleThread …` at `…var-765…/plan.md:103`); watchOS device & watchOS simulator → suite nil → everything collapses into `.standard` (`.pi/qrspi/alanvardy-var-721-testflight-macos/q4-findings.md:82`, `…var-747…/research.md:52`, `…var-796…/research.md:69`); macOS → sandboxed group resolves (`SingleThread.entitlements:9-11`); previews/unregistered sims → nil fallback (`AppGroup.swift:13-15`).
- **Registration is build-time only.** No runtime registration, no launch-argument registration, no device-identity logic anywhere uses the suite. Launch seams write values **through** `AppGroup.defaults` but never register a suite (`AppViewModel.swift:216-295`, `WatchAppViewModel.swift:23-198`).
- **No in-repo evidence a watchOS target/simulator holds a non-standard suite.** Every repo document asserts the opposite ("watchOS is NOT a member of the app group", `…var-721…/q4-findings.md:82`; "so `UserDefaults(suiteName:)` is nil there", `…var-747…/research.md:52`; `PendingCompletionStore.swift:8-9`; `AGENTS.md:53-57`). Apple's docs are not cited in the repo. (Apple platform docs do confirm `init(suiteName:)` is available on watchOS 2.0+, but App Group containers are same-device only — the iPhone and watch simulators are separate CoreSimulator devices with isolated `Containers/Shared/AppGroup` paths, so even a registered suite would not bridge phone↔watch; the repo only establishes that no current target/config/test/skill registers one for watchOS.)
- Watch code relies on the fallback knowingly: `WatchAppViewModel.swift:23-27` (`--ui-testing-gated` seeds `completionCount` via `AppGroup.defaults.set(…)`, comment "it falls back to `.standard` where no App Group is registered"), `:126-133` (`--ui-testing-skip-count`), `:195-198` (receive writes `completionCount`); `ShowEnableActionButtonsState.swift:5-6,14-16` ("falling back to `.standard` where the group is unavailable, e.g. a real watch"). Watch tests defensively clear **both** domains (`SingleThreadWatchTests/ShowEnableActionButtonsStateTests.swift:7-10,57-61`).

## Cross-Cutting Observations
- **One logical domain, two physical containers.** The codebase treats `AppGroup.defaults` and `UserDefaults.standard` as the same logical store on the watch (group unavailable → fallback), and `UITestingSeed.resetPersistedState` clears both (`UITestingSeed.swift:62-68`); watch test helpers and the migration (`registerDefaults`) likewise span both. `Agents.md:53-57` mandates every watch-shared value round-trip through `AppGroup.defaults`.
- **Watch sync-service stores explicitly diverge to `.standard`** (`WatchAppViewModel.swift:232-244`) — a deliberate mirror that is a no-op difference on a real watch but a real difference on any future/registered watch suite.
- **Latest-wins one-directional application-context sync** with `sendMessage` relays for imperative ops (complete/delete/reschedule: `SkippedReminderSyncService.swift:244-292`); receive side is persist-then-notify, replacement-not-union, absent-key-no-op.
- **Seam philosophy differs per platform**: iOS = rich `--seed` JSON + global reset; watch = many small `--ui-testing-*` flags + per-launch overrides, no reset (relaunch shares the same install's UserDefaults).
- **The watch has no entitlements file at all** — the "watch can't hold the suite" assumption is enforced by build configuration, not by any runtime check.

## Open Areas
- Apple platform documentation is not cited anywhere in the repo; whether a group-registered **watchOS** build/simulator could hold the suite is unverified in-repo (Q4 report's web evidence says same-device App Group sharing does work between a watch app and its own extensions on one watchOS simulator, but phone↔watch never shares — the repo's model is consistent with that only insofar as the watch never registers a group).
- `resetForTesting()` (test-only) exists on `CompletionCounterStore.swift:50-51`; no analogous reset surfaces were found for other stores.
- The exact correlate of `EXPECTED_TARGET_LITERALS` accounting for a **new** watch target (e.g. a watch UI-test variant of iOS-style subgroups) would need the literal inventory in §6 of the Q5 report.
