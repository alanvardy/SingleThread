## Q1: Visibility pipeline — how `visibleReminders` is derived

### Findings
- `visibleReminders` (`Core/ReminderStore.swift:129-135`) is a `public` computed property, derived fresh on every read: `reminders` → filter out `skippedIDs` (by `calendarItemIdentifier`) → filter out `excludedListTitles` (by `calendar?.title ?? ""`) → sort. No storage; every surface reads `visibleReminders.first`.
- **Source array**: `reminders` is `public private(set)` (`:55`), written only by `reload()` (`:358-413`, `reminders = shown` at `:398`).
- **Skip list**: in-memory `skippedIDs` (`:56`); persisted by `SkippedReminderStore` (`Core/ReminderSkip.swift:121-135`, key `"skippedReminderIdentifiers"` at `:124`, default `AppGroup.defaults`). Pure logic in `ReminderSkipLogic` (`:5-30`): `resolve` prunes IDs not in the fetched set (`:12-18`), `skipping` appends then prunes (`:19-30`).
- **Skip mutation paths**: `skipCurrentReminder()` (`ReminderStore.swift:315-330`) — `canMutate` gate, captures `skipGeneration`, then in a detached `Task` awaits `settle()` and applies via `applySkipSet(updated, generation:)` (`:495-507`), reloading only if not discarded by the generation gate; `skipCurrentReminderImmediately()` (`:346-353`) — synchronous, no settle, exists for the widget's `SkipReminderIntent` (process may be suspended right after `perform()`); `clearSkippedState()` (`:482-487`) bumps `skipGeneration`, empties, persists `[]`, fires `onSkipSetChanged`.
- **Excluded list**: in-memory `excludedListTitles` (`:57`); persisted by `ExcludedListStore` (`Core/ExcludedListStore.swift`, key `"excludedListTitles"`). `setExcludedListTitles` (`:415-424`) fires `onExcludedListsChanged` + `onRemindersChanged`; `refreshExcludedListTitles` (`:427-432`) is the WatchConnectivity receive path — fires `onRemindersChanged` only (no echo).
- **Reconciliation**: `reconcileSkipState(clearSkipped:visibleShown:)` (`:552-564`) runs inside every `reload()` — clears or re-resolves skips from `skipStore.load()`, reloads `excludedListTitles` from `excludeStore.load()`, re-persists the pruned list.
- **Undated filter**: `showsUndatedReminders` (`:122-127`), `public var` with `didSet` firing `onShowUndatedRemindersChanged`. In `reload()`, it selects the date predicate: `showsUndatedReminders == true` → nil/nil predicate; else `ReminderDateFilter.overdueCutoff()` (30 days back, `Core/ReminderDateFilter.swift:17-25`) → `endOfToday()` (`:8-15`). With undated on, `shown` is re-filtered by `ReminderDateFilter.isInCurrentWindow` (`:27-35`, nil date → in-window). Each surface sets `showsUndatedReminders` before its own reload (widget from `AppGroup.defaults.bool(forKey: "showUndatedReminders")`).
- **`hasHidden`** (`:62`): computed via `hasHiddenFor(shown:allIncomplete:)` (`:159-166`) — true when an incomplete reminder exists outside the window. In narrow (undated-off) mode `reload()` issues a **second broad fetch** to learn this (`:380-391`); in broad mode derived from the fetch already in hand.
- **`allSkipped`** (`:138-141`): `!reminders.isEmpty && visibleReminders.isEmpty` — non-empty source but everything skipped/excluded.
- **`canMutate`** (`:145-148`): `entitlementStore.isEntitled || completionCounter.count < EntitlementStore.freemiumCap`. Gates complete/delete/skip/undo. `hasResolvedEntitlement` (`:152-154`) mirrors the entitlement-store seam.
- **Sort**: `ReminderSort.areInIncreasingOrder(_:_:using:)` (`Core/ReminderSort.swift:19-37`, two-arg overload `:11-14` defaulting to `.priority`); `SortOption` = `.priority`/`.dueDate`/`.title` (`Core/SortOption.swift:5-21`); comparator tie-breaks: priority rank (high=0..nil last, via `ReminderPriority.rank` `Core/ReminderSkip.swift:82-90`) → due date (dated before undated) → title. Persisted by `SortOptionStore` (`SortOption.swift:31-40`, key `"sortOption"`).
- **`ReminderDisplay` construction**: `public struct ReminderDisplay: Equatable, Sendable` (`Core/ReminderDisplay.swift:8-73`); `init(reminder:)` (`:11-21`) maps title, `ReminderNotesFormatter.format(notes)`, `dueDate = reminder.dueDateComponents?.date`, `priorityMarker = ReminderPriority.marker(for:)`, `listName = calendar?.title`, `hasRecurrence`, `recurrenceSummary = ReminderRecurrenceFormatter.format(rules)`, `hasAlarms` — all `public let` (`:42-50`), plus `titleAttributed`/`notesAttributed` (`:53-63`) via `CodeSpanFormatter`.
- **Public surface for widget/watch**: `Package.swift:1-27` declares one `SingleThreadCore` library product with floors `.iOS("18.7")`, `.watchOS("26.5")`, `.macOS("26.5")` (`:7-9`). `ReminderStore`, `ReminderDisplay`, `ReminderSort`, `SortOption`, `ReminderSkipLogic`, `ReminderPriority`, `ReminderNotesFormatter`, `SkippedReminderStore`, `PendingCompletionLogic/Store`, `CompletionCounterStore`, `EntitlementStore`, `Show*Preference`, `SharedStrings`, `UITestingSeed`, etc. are all `public`. `Core` **never reads UserDefaults itself** — stores inject defaults (`AppGroup.defaults`), app-layer hooks do the wiring.
- **Consumers of `visibleReminders.first`**: widget `SingleThreadWidget/NextThingWidget.swift:83`; watch `SingleThreadWatch/WatchReminderView.swift:84`; iOS `SingleThread/ContentView.swift:388`.

## Q2: Widget extension architecture

### Findings
- Bundle exports exactly one widget: `SingleThreadWidget/SingleThreadWidgetBundle.swift:7-9`. `NextThingWidget: Widget` (`NextThingWidget.swift:113-131`), `kind = "NextThing"` (`:114`), families `[.systemSmall, .systemMedium, .systemLarge]` (`:128`), `StaticConfiguration` with `NextThingProvider`.

- **Provider**: `placeholder` (`:30`) and `getSnapshot` (`:40`) render canned `.reminder` entries; `getTimeline` (`:51-57`) is the live path — dispatches a `Task`, `await Self.makeEntry()`, then a **single-entry `Timeline` with fixed `policy: .after(Date().addingTimeInterval(15 * 60))`** (`:54-55`). The widget advances state only on this 15-minute cadence or an external `WidgetCenter.reloadAllTimelines()`.
- **`makeEntry()`** (`:62-110`, `@MainActor`): reads four `Show*Preference()` defaults (`:63-67`) → gates on `EKEventStore.authorizationStatus(for: .reminder)` (`:68`) → only `.fullAccess` proceeds: **fresh `ReminderStore(loadsReminders: true)` per render** (`:70`, default `EKEventStore()`), `showsUndatedReminders` from `AppGroup.defaults` (`:71`), `setSortOption(SortOptionStore().load())` (`:72`), `await store.reload()` (`:73`). Branches: `store.reminders.isEmpty` → `.empty(store.hasHidden)` (`:74`); `guard let current = store.visibleReminders.first` else → `.allDone` (`:83-86`); else `.reminder(ReminderDisplay(reminder: current))` (`:97-98`); any non-fullAccess status → `.noAccess` (`:102`).
- **View rendering** (`:134-256`): `.noAccess` → lock icon + `SharedStrings.remindersAccess` + "Open SingleThread to enable access." (`:141`); `.empty(hasHidden)` → `SharedStrings.noReminders` + `hasHidden ? nothingDueRightNow : noRemindersYet`; `.allDone` → `checkmark.circle` + `SharedStrings.allDone` (`:154`); `.reminder` → `reminderView` (`:208-238`) gating dueDate/list/recurrence/alarms on the entry's four booleans; `actionButtons` (`:166-186`) with `Button(intent: CompleteReminderIntent())` (`:168`) and `Button(intent: SkipReminderIntent())` (`:177`).
- **Intents** (`Core/ReminderIntents.swift`): both `public struct … : AppIntent`, `isDiscoverable = false`. `CompleteReminderIntent` (`:7-28`): fresh `ReminderStore(loadsReminders: true)` (`:19`), `setSortOption` (`:20`), `await reload()` (`:21`), `await completeCurrentReminder()` (`:22`). `SkipReminderIntent` (`:30-50`): same fresh-store pattern, then `store.skipCurrentReminderImmediately()` (`:49`) — the synchronous variant that avoids the 200 ms settle sleep for WidgetKit suspension safety.
- **iOS reload trigger**: `SingleThread/AppViewModel.swift:76-77` — `store.onRemindersChanged = { WidgetCenter.shared.reloadAllTimelines() }` (iOS/macOS only, `import WidgetKit` at `AppViewModel.swift:8`). Exactly five `onRemindersChanged?()` firing sites in Core: `ReminderStore.swift:336` (setSortOption), `:410` (reload — covers complete/delete/add/undo/clear/reload paths), `:420` (setExcludedListTitles), `:429` (refreshExcludedListTitles), `:502` (applySkipSet — synchronous skip). A second preference-driven reload exists at `SingleThread/SettingsViewModel.swift:22` (`showPreferenceChanged` → `reloadAllTimelines()`).

## Q3: WatchConnectivity sync

### Findings
- Service: `Core/SkippedReminderSyncService.swift` — whole file `#if os(iOS) || os(watchOS)` (`:4`); `SkipSyncSession` seaming protocol (`:8-15`) extended by `WCSession` (`:17`). Class doc (`:21-22`): "Uses `updateApplicationContext` for skip sync — latest-wins, auto-delivers on (re)connect — and `sendMessage` for interactive completion requests."
- **Payload keys** (`PayloadKey`, `:268-281`, private enum shared in source between targets): `skippedReminderIdentifiers`, `excludedListTitles`, `completeReminderIdentifier` (sendMessage), `deleteReminderIdentifier` (sendMessage), `showUndatedReminders`, `sortOption`, `showDate`, `showRecurrence`, `showAlarms`, `showList`, `showCompletionGlow`, `completionCount`, `isEntitled`.
- **`pushAll()`** (`:167-208`): one combined `updateApplicationContext` snapshot. Always: skip IDs from `skipStore.load()` (`:170`), excluded titles (`:171`), showUndated (`:172`), sortOption (`:173`), completionCount (`:174`). Conditionally (per `sends*` flags): `showDate/Recurrence/Alarms/List/CompletionGlow` (`:177-192`), `isEntitled` via `MainActor.assumeIsolated` (`:197-200`). Send at `:202`, errors logged.
- **Latest-wins semantics**: sending a single context shape avoids interleaved partial shapes (`:168-171` doc); receiving side is **replacement, not union** — `apply()` doc "Replacing (rather than unioning) local values makes a 'clear' update (`[]`) propagate" (`:309-316`).
- **Relays**: `requestCompleteReminder` (`:210-218`) and `requestDeleteReminder` (`:220-228`) send `sendMessage([PayloadKey…: identifier], replyHandler: nil)`.
- **Receive**: `session(didReceiveApplicationContext:)` → `apply` (`:233-235`); `session(didReceiveMessage:)` (`:237-246`) dispatches to `onCompleteReminderReceived` / `onDeleteReminderReceived`. `apply(context:)` (`:308-367`) decodes present keys → **persists first, then fires hook** (absent keys are no-ops); `applyFreemium` (`:369-380`) handles `isEntitled`/`completionCount`. All hooks are `public nonisolated(unsafe)` vars (`:83-154`), write-once-before-`activate()`.
- **iOS wiring** (`SingleThread/AppViewModel.swift:29-87`, guarded `WCSession.isSupported() && !usesInMemoryStore` `:29`): receive hooks → `store.completeReminder(identifier:)` (`:45-48`), `store.deleteReminder(identifier:)` (`:49-52`), `refreshExcludedListTitles` (`:53-56`); push hooks → `onSkipSetChanged`/`onShowUndatedRemindersChanged`/`onExcludedListsChanged` → `pushAll()` (`:58-60`), `onCompleteReminder`/`onDeleteReminder` → relays (inert on iOS, `:61-66`), `onSortOptionChanged` → save + `pushAll()` (`:69-72`). iOS also observes entitlement (`setupEntitlementObservation` `:359-367`) and `UserDefaults.didChangeNotification` on `AppGroup.defaults` (`setupSyncObservation` `:375-384`, `handlePreferencesChanged` `:389-406`). iOS leaves receive hooks unset (nil handlers → persists but no-op) except the three above.
- **Watch wiring** (`SingleThreadWatch/WatchAppViewModel.swift:149-199`): receive hooks — `onShowUndatedRemindersReceived` → set + reload (`:165-169`), `onSkippedIdentifiersReceived` → `reload()` (`:174-176`), `onSortOptionReceived` → `setSortOption` (`:178-180`), `onCompletionCountReceived` → `AppGroup.defaults.set(count, "completionCount")` (`:185-187`), `onExcludedListTitlesReceived` → `refreshExcludedListTitles` (`:190-192`), show-*/entitled — `wireStateReceiveHooks` (`:206-235`). Push: `onSkipSetChanged` → `pushAll()` (`:194`), `onCompleteReminder`/`onDeleteReminder` → relays (`:197-198`); **no exclusion push hook** — exclusions are phone→watch only (`:195-196`). Watch constructs the service with `.standard`-explicit stores (`:155-161`) and all `sends* = false` (`:163-164`).
- **What is NOT on the wire**: no reminder content — no title/notes/priority/due-date/list/recurrence keys exist in `PayloadKey` (`:268-281`). Each side derives its list from **local EventKit** via `ReminderStore.reload()` (`ReminderStore.swift:358-413`); wire carries only identifiers, excluded titles, scalar prefs/counter/entitlement.
- **Storage**: `AppGroup.defaults = UserDefaults(suiteName: "group.app.alanvardy.SingleThread") ?? .standard` (`Core/AppGroup.swift:11-17`). On watchOS the suite is unavailable → falls back to `.standard`, so AppGroup-defaulted stores collapse to `.standard` there; watch show-* stores are explicitly `.standard` (`WatchAppViewModel.swift:155-161`). iOS skip/exclude/sort/showUndated/counter default to `AppGroup.defaults`.

## Cross-Cutting Observations
- **One derivation, three consumers**: `visibleReminders` is a pure function of `reminders`, `skippedIDs`, `excludedListTitles`, `sortOption` (`ReminderStore.swift:129-135`); iOS app, watch, and widget all read `visibleReminders.first` and build `ReminderDisplay` identically. Every mutation path re-derives it on next read.
- **Store lifetime differs per surface**: iOS app keeps one long-lived `ReminderStore` (`AppViewModel.swift:16, 234-278`) with `onRemindersChanged` → `WidgetCenter.reloadAllTimelines()`; the widget constructs a **fresh** `ReminderStore` per render and per intent `perform()`; the watch builds one store in `WatchAppViewModel` and one lazy `WatchReminderViewModel`.
- **watchOS is EventKit-read-only**: complete/delete mutate local arrays and relay identifiers over `sendMessage`; pending-completion persistence (`PendingCompletionStore`, 5-minute expiry) is the hide-until-phone-confirms mechanism; `reload()` applies `applyingPendingCompletionFilter` on both a filter and a defensive completed-drop (`ReminderStore.swift:397, :525-534`).
- **`AppGroup.defaults` collapses to `.standard` on watchOS** (`AppGroup.swift:11-17`) — so the explicit `.standard` vs default `AppGroup.defaults` distinction matters for documentation, not behavior, on the watch today.
- **Wire protocol discipline**: single `PayloadKey` enum in shared Core source prevents key drift; `updateApplicationContext` is full-state replace (latest-wins), `sendMessage` is command-only; no reminder *content* ever crosses the wire.
- **Hook naming convention**: `on*Changed` (local state), `on*Received` (WatchConnectivity receive), `onCompleteReminder`/`onDeleteReminder` (watch→phone relay). Hooks are write-only; Core never reads UserDefaults.

## Post-Research Platform Constraints (verified via Apple docs/forums)

Three load-bearing constraints were confirmed after the Q1–Q6 synthesis; they correct two
assumptions in `design.md` and are treated as facts for design/plan:

1. **A watchOS WidgetKit complication requires a separate Widget Extension target** (`.appex`)
   embedded in the watch app — it cannot live inside the watch app target. The complication is
   delivered by a widget extension with its own `@main WidgetBundle`, bundle id, and
   `NSExtension`/Info.plist; a "single-target" watch app removes only the legacy WatchKit
   extension, not the WidgetKit extension. The iOS `SingleThreadWidget` extension is iOS-only and
   not reusable. Sources: [Creating accessory widgets and watch complications](https://developer.apple.com/documentation/widgetkit/creating-accessory-widgets-and-watch-complications),
   [TN3157](https://developer.apple.com/documentation/technotes/tn3157-updating-your-watchos-project-for-swiftui-and-widgetkit).

2. **A widget extension process is not a WatchConnectivity peer.** `WCSession` cannot be activated
   from, nor deliver `updateApplicationContext`/`sendMessage` reliably from, a WidgetKit extension —
   the process is short-lived and the session owner is the containing watch app. Frameworks
   Engineer: "WatchConnectivity is not an option for updating widgets." Interactive Smart Stack
   buttons must route mutations through the watch app. Sources: [Apple forum 745581](https://developer.apple.com/forums/thread/745581),
   [Stack Overflow 76443506](https://stackoverflow.com/questions/76443506/sharing-data-between-ios-and-watchos-application-and-widget-watchconnectivit).

3. **watch app ↔ widget extension sharing requires an App Group on both targets.** They are
   sandboxed separately; without the App Groups capability the extension reads a *different*
   `.standard` than the app. Enabling the capability on the watch targets changes `AppGroup.defaults`
   from the `.standard` fallback to the real `group.app.alanvardy.SingleThread` suite — a one-time
   storage-location shift for existing watch-side state (phone-mirrored skips/exclusions re-sync).
   Source: [Stack Overflow 73517620](https://stackoverflow.com/questions/73517620/access-ios-app-watchos-app-data-from-widgetkit-complication-watchos-9).
